# Slice 2: framework execution refs get neutral names

_Parent: `projects/mongo-defaults-codecs-prisma6-source/`. Branch `execution-ref-neutral-names` off `main`, independent of slice 1. Outcome: the framework contract's execution-default reference carries no SQL vocabulary, so the Mongo family can use the framework `Contract` type unchanged._

## At a glance

Before, in every `contract.json` with generators:

```json
{ "ref": { "namespace": "app", "table": "users", "column": "updated_at" }, "onUpdate": { "kind": "generator", "id": "timestampNow" } }
```

After:

```json
{ "ref": { "namespace": "app", "entry": "users", "field": "updated_at" }, "onUpdate": { "kind": "generator", "id": "timestampNow" } }
```

The values are unchanged: SQL still writes the storage table and column names, Mongo will write the collection and stored field names. `executionHash` changes for every contract that has generators, because the canonical JSON changes; `storageHash` and `profileHash` do not.

## Chosen design

- `ExecutionMutationDefault.ref` in `packages/1-framework/0-foundation/contract/src/types.ts:175-179` becomes `{ namespace: string; entry: string; field: string }`. `entry` is the framework's own storage word: a `StorageNamespace` holds `entries`, keyed by table (SQL) or collection (Mongo). `field` is the stored field or column name.
- SQL follows the framework: the arktype `ExecutionMutationDefaultSchema` in `packages/2-sql/1-core/contract/src/validators.ts:46-78`; authoring assembly in `packages/2-sql/2-authoring/contract-ts/src/build-contract.ts:1169-1175` and its sort at `1606-1613`; the PSL interpreter's equivalent; the runtime match in `packages/2-sql/5-runtime/src/sql-context.ts:683-705` and `MutationDefaultsOptions` in `packages/2-sql/4-lanes/relational-core/src/query-lane-context.ts:75-95`; the ORM client's create-input types in `packages/3-extensions/sql-orm-client/src/types.ts:1254-1340` (`HasExecutionCreateDefault` matches `ref.table`/`ref.column`); the framework emitter's `serializeExecutionType`; the Prisma 7 reader if it builds refs; any language-server or CLI code that reads refs.
- Every fixture carrying an `execution` section (123 `contract.json` files plus their `contract.d.ts`) is regenerated through `pnpm fixtures:check`, never hand-edited. Migration snapshots that embed contracts are regenerated by their own scripts or, if none exists, listed in the report.
- Upgrade-instructions fragments (`app` and `extension`) declare the ref rename for anyone who reads `contract.execution` directly or types against `ExecutionMutationDefault`.
- Docs that show the ref shape (ADRs, subsystem docs, `docs/reference`) are updated so examples match the code.

## Coherence rationale

One rename, applied everywhere it appears, with regenerated fixtures. A reviewer verifies it by reading the type change and confirming every other hunk is a mechanical follow-through or a regeneration.

## Scope

In: the rename and its follow-through above. Out: hoisting the generator runtime (slice 4), any Mongo change (slice 3), renaming `MutationDefaultsOptions.table` in the SQL lanes layer beyond what the ref rename forces (renaming the option key to `entry` is in scope only if the implementer finds it makes the runtime match read consistently; report either way).

## Pre-investigated edge cases

- `executionHash` moves for every contract with generators, so signed databases in test fixtures that verify the execution hash must be re-signed by their fixture scripts; `fixtures:check` covers emitted artifacts, not database markers. List any integration test that pins an `executionHash` literal.
- The `no-family-vocabulary` ratchet counts `table`/`column` identifiers in the framework; this change should lower the count. Report the before and after numbers.
