## S6. Prisma 8 CLI state — finding (known limitation, plus F1)

Logs: `S6.log`, `S6-skills-sync.log`, `S6-branch-help.log`.

- `pnpm prisma --version`: `8.0.0-rc.15` (JSON envelope, non-TTY). Exit 0.
- `pnpm prisma contract emit`: exit 2, `CLI.CONFIG_UNREADABLE`: "/…/prisma7-app/prisma.config.ts could not be evaluated: (0 , _config2.prisma7Schema) is not a function", nextAction "Fix the error in the file, then run the command again." Then a trailing stderr line: "Prisma agent skills are out of date (installed @prisma/orm-postgres 8.0.0-rc.11, synced none). Run: prisma skills sync". This is the known limitation (published `@prisma/orm-postgres` 8.0.0-rc.11 lacks `prisma7Schema`). Would a user understand? Not from this message alone: "is not a function" plus "fix the error in the file" reads as a mistake in the file init just wrote. Nothing says the installed `@prisma/orm-postgres` is too old. See F2.
- Following the trailing advice, `pnpm prisma skills sync` fails with the same `CLI.CONFIG_UNREADABLE` (`S6-skills-sync.log`), so the advice is a dead end.
- `pnpm exec prisma orm init --help` (published rc.15): does not mention `--from-prisma7-schema` at all; expected, that binary is not this branch. This branch's `node <bin> orm init --help` (`S6-branch-help.log`) has a paragraph "In a Prisma 7 project, pass --from-prisma7-schema (or answer yes when asked) to use the existing schema.prisma as the contract source.", the option line "--from-prisma7-schema <path>  Use an existing Prisma 7 schema.prisma as the contract source", and the example `prisma orm init --from-prisma7-schema prisma/schema.prisma --confirm my-app`. Clear enough; it does not say what the consent token is (the package name), and the example's `my-app` only makes sense once you know that.

## S8. Re-run on the initialised project — finding

Command: S4's command again on the S4 result. Exit 2. Log: `S8.log`.

Init never reached the re-init consent. It failed with `CLI.INIT_PRISMA7_CONFIG_UNREADABLE`: "`prisma.config.ts` failed to evaluate, so init cannot tell whether it is a Prisma 7 config to rename or a Prisma 8 config to replace: (0 , _config2.prisma7Schema) is not a function", nextAction: "Install the project's dependencies so `prisma.config.ts` can be evaluated (a Prisma 7 config imports `prisma/config`), or rename it to `prisma7.config.ts` by hand, then re-run `prisma orm init`."

Nothing was written (package.json, prisma.config.ts, prisma7.config.ts byte-identical to before; `prisma/` identical), so there was no second rename and no duplicate scripts. But the expected behaviour (consent for init's own files only) could not be observed because the new config cannot be evaluated against the published packages. The nextAction is actively dangerous here: `prisma7.config.ts` already exists, so "rename it to `prisma7.config.ts` by hand" would tell the user to overwrite their working Prisma 7 config with the Prisma 8 one (F2, second half). Root cause is the known limitation; the advice text is not.

Command (via `expect`): `node <bin> orm init --skip-install` on a fresh pre-init copy; answered "y" to the Prisma 7 question, typed the token, "n" to `.env`. Logs: `S9.log` (cleaned), `S9-raw.log`, hang checks `S9-hangcheck-*.log`.

- First prompt: "prisma/schema.prisma is a Prisma 7 schema. Use it as the Prisma 8 contract source?" with `○ Yes / ● No` (defaults to No). Note it detects via the schema, not the config, because `prisma.config.ts` imports `prisma/config`, which at that point still resolves to Prisma 7 — fine.
- Second: the same consent prompt as S7, token typed.
- Third: `.env` question, answered No.
- Result: same nine files written and the same rename as S4, `package.json` scripts rewritten and `contract:emit` added, no dependency changes (install skipped), `prisma/` identical. Next steps say "Install the project dependencies with your package manager: @prisma/orm-postgres, dotenv (and prisma@latest, @prisma/prisma7@7 plus @prisma/cli-engine at the version prisma declares as its dependency, as development dependencies)". Correct and matches S4 minus installs.
- After printing "✔ Done. Open prisma-8.md to get started." and the next steps, the process did not exit. It sat idle (0% CPU) for 10 minutes until killed (F10). Re-checked: with `--from-prisma7-schema … --confirm prisma7-app --skip-install` in the same pty harness it printed Done at 2 s and was still alive at 92 s (`S9-hangcheck-expect.log`); the plain path `orm init --target postgres --authoring psl --skip-install` in an empty project behaves the same (`S9-hangcheck-plain.log`), so this is pre-existing, not introduced by this branch. Non-TTY the same command exits in 0.38 s (`S9-hangcheck-nontty.log`), and under `script` with a pipe it exits when stdin closes (`S9-hangcheck-pty.log`). S7 (exit 5 path) exited normally, so it is the success path in a TTY that lingers. Worth reproducing in a real terminal before treating as a blocker.
