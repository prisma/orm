# Deferred

- **Marker warnings are silent by default.** The SQL runtime's default logger does nothing, so the warnings from the marker check (mismatch, missing, and now unreadable) are seen only when the application passes a `log` option. Whether the default should print warnings is a question for the runtime's logging, outside this project. Found 2026-11-24 while rechecking the code.
- **MongoDB snapshots are read without a content check.** The MongoDB family publishes no hash canonicalization hooks, with a comment that MongoDB hashes a projection of storage. The comment may be out of date. Found 2026-11-24.
- **`apps/telemetry-backend/migrations/snapshots/`** holds three snapshots in formats several releases old that nothing reads or regenerates.
- **PostgreSQL and MySQL report some connection-setup failures as statement errors.** A refused sign-in, an unknown database and "too many connections" surface as `SqlQueryError`, not `SqlConnectionError`. The runtime's marker check therefore treats them as a marker it cannot read: it warns once and uses up the check, where a connection error would leave the check for the next call. A server that is briefly out of connections at startup means that instance never checks its marker. Fixing it changes which public error type the drivers raise. Found 2026-11-24 in the second review of the marker check.
- **Changing driver will mean signing every database again.** The SQL profile hash now covers the contract's capability list. In the design for capabilities by database version, the driver declares what the connection provides, so its capabilities enter the list. A project that switches driver then gets a new profile hash and must sign each database again, although no database changed. The rule is still right; whether driver capabilities belong in the signed list is for that project to decide. Found 2026-11-26 in the review of the profile hash change.
- **Both MongoDB examples fail `db migrate` on an empty database.** `examples/retail-store` and `examples/mongo-demo` stop with `SCHEMA_VERIFY_FAILED` on a validator or an index, at the merge base with `main` as well as on this project's branches, so it is not caused by this project. Found 2026-11-24 by manual QA of the hash change.
- **Two checks hash a stored file through its raw JSON.** The snapshot store's content check (`contract-snapshot-store.ts`) and the extension self-consistency check (`assert-descriptor-self-consistency.ts`) recompute the storage hash from the parsed JSON's `storage`, not from a contract read through its format version's parser. Correct while there is one format version; the first format change that lays out `storage` differently must route both through the parser. Found 2026-11-24 in the review of the hash change.
- **`db verify` advice can name a command the database's change policy refuses.** It advises `db update` on drift and on a marker mismatch (`db-verify.ts`, around line 354) without reading the policy, and the missing-invariants advice names `db migrate`, which a policy permitting only `db update` refuses. The change-policy decision record says advice names the recovery the policy permits. This predates the hash change; `db sign` was fixed in it. Found 2026-11-24.
- **The saved-samples database test cannot see a column a release only writes.** It rebuilds Prisma's own tables in the form an earlier release left them and runs the current commands against them; a release that adds a column it reads fails the test, but one that adds a column it only writes passes, because nothing writes to the rebuilt tables in that test. Bringing Prisma's own tables up to date is project 7 of the compatibility stream; its tests should apply a migration or sign against the rebuilt tables. Found 2026-11-25 in the review of the saved samples.
