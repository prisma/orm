# Deferred

- **Marker warnings are silent by default.** The SQL runtime's default logger does nothing, so the warnings from the marker check (mismatch, missing, and now unreadable) are seen only when the application passes a `log` option. Whether the default should print warnings is a question for the runtime's logging, outside this project. Found 2026-11-24 while rechecking the code.
- **MongoDB snapshots are read without a content check.** The MongoDB family publishes no hash canonicalization hooks, with a comment that MongoDB hashes a projection of storage. The comment may be out of date. Found 2026-11-24.
- **Some saved contracts are in shapes from before `8.0.0-rc.1` that no reader of this release reads:** two snapshots under `apps/telemetry-backend/migrations/snapshots/` and the 44 contracts under `examples/prisma-8-demo/fixtures`. The published `8.0.0-rc.25` reader refuses them too. The test that reads every saved contract names each one. No script regenerates them. Six of the seven demo graph fixtures therefore fail `migration check`, which reads strictly the snapshot a ref names; no CI job runs that check on them.
- **A SQL target's schema for its operation details is not tied to the details' type.** The schema is `Type<unknown>`. Typing it as the details type works for SQLite and MySQL but not for PostgreSQL, whose details type is a union its schema does not match, and making the schema that union makes every refusal read as two alternatives.
- **PostgreSQL and MySQL report some connection-setup failures as statement errors.** A refused sign-in, an unknown database and "too many connections" surface as `SqlQueryError`, not `SqlConnectionError`. The runtime's marker check therefore treats them as a marker it cannot read: it warns once and uses up the check, where a connection error would leave the check for the next call. A server that is briefly out of connections at startup means that instance never checks its marker. Fixing it changes which public error type the drivers raise. Found 2026-11-24 in the second review of the marker check.
- **`migration status`, `list`, `graph` and `check` do not read a SQL operation's target fields strictly.** They read `ops.json` in the framework and use only the fields every target shares, so an unknown key in a target's part of an operation passes them unnoticed; the runners, the statement preview and the recorded-path checks refuse it. Covering them needs a way for the framework to ask the family to read an operation, which is a change to the framework. A refusal names the migration and the operation, but not the file's path.
- **An index's `type` and `options` are not checked when a contract is read.** They are checked only by the TypeScript builder. Checking them at read time needs the stack's index-type registry where a contract is read, in the family instance and in the runtime context, and a decision on what an index type no registered pack declares means there.
- **Nothing tests that the open places of a stored format stay as they are.** A reader that starts acting on a key inside an open place, such as a new entry in a step's `meta`, needs a new format version, and only the author of the change knows. A saved description of what each format version accepts, compared in a test, would catch it.
- **Operation readers are not given the file's format version.** The version is in `migration.json`, read in the framework; a target's part of an operation is read later, in the family. The first change to an operation format has to pass the version to the family's reader, which is a change to the framework.
- **A migration written in code can write an operation that `db migrate` then refuses.** Emitting a migration checks only the fields every target shares. Checking a target's own fields at emit needs the same way for the framework to ask the family to read an operation as the listing commands do.
- **A contract format change to content one family owns has no home for its converter.** Contract conversions live with the shared reader in the framework, which holds for steps that change fields every family's contract shares. The first step that changes family-owned content needs each family to declare its own contract format and the framework read paths to take it from the family.
- **A codec the stack does not register is skipped when a command reads a contract.** The command does not check its type parameters or its data type; the SQL client refuses the column at startup. What an unregistered codec means when a contract is read needs a decision, like the index-type item above.
- **A contract check swallows a migration it cannot load when the space has no `contract.json`** (`loadAggregateIntegrityViolations`).
- **The runner records a version 0 snapshot in the database as it is stored,** without converting it to version 1. Nothing reads those records back today. A reader added later has to read them through the format version.
- **SQLite creates an empty database file when `db migrate` refuses a migration,** because the refusal comes after the database is opened to read its marker.
- **A ledger row can name a migration hash no file has.** When no database has applied a migration whose `migration.json` is lost, the advice runs its `migration.ts`, which gives it a new hash. If a database had applied it after all, its ledger keeps the old hash. Nothing compares the two today; a check added later would report it.
- **The advice for an unreadable extension head ref does not name `contract emit`,** which now writes that file again. `migration check` says "Repair or remove the corrupt ref file", and the other commands say to make the file valid.
- **A migration whose `to` is not a well-formed hash is applied without recording its contract, and without a warning.**
- **The warning that a database command records no contract for a migration fires on targets that never record one.** Only PostgreSQL records a contract for each migration it applies; SQLite, MySQL and MongoDB do not, yet they print the warning. The sentence is true and its advice (restore the file) is right, but it is noise there. Fixing it needs the target to say whether it records contracts, which is a new framework concept.
- **Advice that cannot repeat the user's `--db` and `--config`.** The fixed advice texts (for a file no release wrote) say "the configured database"; `migration plan` and `migration check` leave out `--config` in the snapshot-rewrite advice.
- **`migration plan`'s refusal of its starting point advises `migration ref set db <contract>`,** which names a contract for the `db` ref by hand, against the rule the other advice follows.
- **The `onUnrecordedSnapshot` listener is tested only through `db migrate`,** and its types are not exported, like `UnreadableStoredFile`.
- **A project that uses `db update` without migrations fails `migration check`:** its `db` ref names a contract no migration reaches. The advice there is not false, but the finding is. Not yet checked whether this predates this work.
- **The MongoDB client does not check type parameters.** It has no registry to check them against and does not use them; the commands check them when they read a contract.
- **A SQL planning refusal's operation is named through an untyped `meta.migration` on the wrapper error.** It works, but nothing ties the field's shape to the code that reads it.
- **`migration.json`'s `from` and `to` accept a value that is not a contract hash.** A malformed one is caught later, as a snapshot that cannot be found. Making the schema strict breaks many tests that use made-up hashes.
