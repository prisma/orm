## Overhead with no middleware (N-1)

Against the database the comparison is not usable. PGlite runs in one WASM thread and the machine was busy: one `first()` took 1.8 to 7.5 ms, and runs of the same build varied by up to 4x (`bench.log`).

So I measured the ORM and runtime alone. Both builds ran with no middleware on `postgres({ binding: { kind: 'pgClient', client } })`, where `client` is an in-process fake `pg.Client` that answers every query at once with fixed rows (1 row for `LIMIT 1`, 50 otherwise). Each round runs 20 000 `first({ id })` and 2 000 `all()` of 50 rows on each build, both builds loaded in one process, alternating which goes first, 15 rounds after a warm-up. Three processes (`bench-interleaved.log`):

| Process | `first()` main | `first()` branch | median ratio | `all()` main | `all()` branch | median ratio |
|---|---|---|---|---|---|---|
| 1 | 25.1 µs | 33.1 µs | +16% | 149 µs | 172 µs | +11% |
| 2 | 48.6 µs | 57.7 µs | +21% | 242 µs | 279 µs | +14% |
| 3 | 52.0 µs | 58.7 µs | +20% | 283 µs | 285 µs | +6% |

Separate processes per build, five alternations (`bench-fake.log`), agree: median `first()` 44.1 µs on main and 59.6 µs on the branch, `all()` 240 µs and 260 µs.

So each ORM call costs about 7 to 9 µs more with no middleware: about +20% of the ORM and runtime CPU time for `first()`, and +6 to +14% for an `all()` of 50 rows. Against a real database round trip of 0.2 to 1 ms this is about 1 to 4%.

## Findings

### Q3-1. An ORM call costs about 8 µs more with no middleware registered

Severity: medium.

The slice aims to keep the no-middleware cost flat. With an instant driver, `first()` is about 20% slower than on `origin/main` (+7 to 9 µs per call) and `all()` of 50 rows 6 to 14% slower. The ORM starts an `orm-call` activity, with its context and hooks loop, for every terminal method even when no middleware is registered.

Reproduction: `wip/qa3/bench-interleaved.ts` (needs the `origin/main` worktree and the two `bench-*` folders; see "What I ran").

Recommendation: profile the call path. If the activity cannot be skipped when the runtime has no middleware, say in the ORM README what an ORM call costs.

### Q3-2. A cache store that fails in `set` makes the ORM read fail, every time

Severity: medium.

With the README's serializing store and plain JSON, an annotated `Post.first()` that selects `impressionCount` reads the row from the database, then the cache's `set` throws "Do not know how to serialize a BigInt", and the caller gets that error. The tracer shows the call ended `succeeded` and finalized `committed`. Nothing is stored, so every later call fails the same way: the cache turns a working read into a failing one.

The README warns that `JSON.stringify` throws on a `bigint`, but does not say the read then fails. "Store errors propagate" is written only for `invalidate`.

Reproduction: `wip/qa3/serializing-store.ts`, second part (`run-serializing-store.log`).

Recommendation: either say in the `CacheStore` section that an error from `get` or `set` fails the read, or have the middleware log a failed `set` and still return the result.

### Q3-3. The demo's README and `db.ts` still describe ORM caching as statement caching

Severity: low.

The branch changed the demo's two cached ORM files, but not these:

- `examples/prisma-8-demo/README.md`, "Cache Middleware Examples": the cache "only acts on plans whose `meta.annotations` carry a `cacheAnnotation`", and "The default cache key is `ActivityContext.contentHash(exec)`". ORM annotations are no longer on plans, and an ORM call's key is `activity.contentHash()`.
- `examples/prisma-8-demo/src/prisma/db.ts`, the comment on `createCacheMiddleware()`: a hit "skips only the driver call", `lints` and `budgets` have already run, and "The cache stores raw rows". On an ORM hit no statement runs at all, so `lints`, `budgets` and the slow-query warning see nothing.
- The comment on `slowQueryWarning` in the same file: "Cache hits flow through it too". Not for ORM hits.

Recommendation: update the three passages.

### Q3-4. A hand-built runtime still compiles, and the ORM README still calls it valid

Severity: low.

`orm({ context, runtime: { query(plan) {...}, execute(plan) {...} } })` typechecks with no cast (`wip/qa3/handbuilt-types.ts`), then every terminal fails at run time. The ORM README's "Runtime surface" lists `[activitySource]?` as optional, and the next paragraph says "Runtimes that don't expose them are still valid `RuntimeQueryable`s and are used for single-statement execution". That is no longer true for `[activitySource]`.

Recommendation: fix the paragraph. If possible, make `[activitySource]` required on the type `orm()` takes, so the mistake shows at compile time.

### Q3-5. A user key shared by a builder query and an ORM call makes each evict the other

Severity: low.

K-8: a builder query stores its rows under `shared`. An ORM call with the same key misses, as documented, and then stores its result under `shared`, replacing the rows. The builder query then misses too (K-8c). The README says "under one key, an ORM call's result is a miss for a statement", but not that the miss overwrites. It already says a key belongs to one query, so this is about one more sentence.

### Q3-6. Carried over: the demo's `pnpm emit` and `pnpm db:init` still fail

Severity: low. This is slice-1 Q-7, still open: `sh: prisma: command not found`. The workaround is `node ../../packages/1-framework/3-tooling/cli/dist/bin.mjs contract emit` (and `db init`).
