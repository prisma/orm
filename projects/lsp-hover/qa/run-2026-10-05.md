## Exploratory notes

Ran the full charter against the real, unmodified `examples/prisma-8-demo/src/prisma/contract.prisma`, read-only, against its own real `prisma.config.ts` (postgres + the `pgvector` and `engagement-stats` extensions; `DATABASE_URL` set to a syntactically valid placeholder in the environment — config loading never connects to it). 14 probes, beyond anything the scripted scenarios covered:

- `pgvector.Vector(1536)` → `pgvector.Vector(length: number)` (no documentation; the extension's descriptor declares none) — confirms contributed-type hover works for an actual *extension*-contributed type, not just the bare family's `sql.String`.
- `enum user_type` / `enum Priority`, at both declaration and a field reference → both resolve identically, matching the project's cross-cutting hover/diagnostics-agree requirement, with no `///` (neither enum has one in the real schema, so no documentation section — correctly fence-only).
- `@@type("pg/text@1")` on `user_type` → identical rendering to the scripted scratch-project row.
- `Low` (an enum-member constant used as `@default(Low)`) → `` ```prisma\nLow\n``` `` + "The `Low` member of enum `Priority`." — a `constant` resolution kind arising from `enumDefaultArms`'s per-member `identifier(name, {...})`, a different code path from the referential-action constants scripted in Scenario 7, exercising the same binder case from a different spec.
- `name` key in `@@fullTextIndex([title], name: "post_title_search")` → `name?: string` + its real documentation — a second, independent `parameter`-kind confirmation beyond the scripted `references` row.
- `@@fullTextIndex` itself → its full real signature (a long `language?:` string-union of 27 locale options) renders completely and legibly, with no truncation.
- `` sql`(now() + '7 days'::interval)` `` tagged literal's `sql` tag name → `null`. This is **expected, not a finding**: `tryBindExpression`'s `taggedLiteral` case (added in D4) only reports whether the literal's *shape* matches; it never calls `references.set(...)` for the tag name, so there is no `Resolution` for the binder to have recorded in the first place, the same as hovering any other token no `Resolution` kind ever reaches. Neither the project spec nor the hover-arguments slice spec lists a tag name as a hoverable position.
- `BigIntNumber` / `UnboundedInt` named-type references → both resolve to their full real documentation (the multi-sentence comments explaining int8-vs-numeric storage), confirming long, realistic `///` prose renders intact through hover, not just the short synthetic strings used in the scripted scenarios.
- `@@discriminator(type)` → `@@discriminator(field name)` + documentation.
- `Task` inside `@@base(Task, "bug")` on the `Bug` model → resolves to `model Task` (no documentation; `Task` has none) — an `entityRef`-typed attribute *argument* resolving to a full entity hover, a combination the scripted scenarios never exercised (they only used `entityRef` for field-type references, not for an attribute argument value).

No defect, diagnostic mismatch, or unexpected rendering turned up. `window/logMessage`/`textDocument/publishDiagnostics` for the demo file stayed empty throughout — the real schema parses and binds clean, as expected of a shipped example.
