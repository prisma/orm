## F8 status: resolved

New scenario (10) against a real `policy_select` block, added to `wip/qa-scratch/lsp-hover-qa/main.prisma`:

```prisma
namespace public {
  model Profile {
    id      Int @id
    ownerId Int

    @@rls
  }

  /// Restricts row visibility to the row's own owner.
  policy_select ReadOwn {
    target = Profile
    roles  = [app_user]
    using  = "ownerId = current_setting('app.uid')::int"
  }
}
```

Verbatim driver output:

```json
"struct-entry-key-using": {
  "hover": {
    "contents": { "kind": "markdown", "value": "```prisma\nusing?: string\n```\n\nA SQL predicate controlling which rows this policy permits." }
  }
},
"struct-entry-key-target": {
  "hover": {
    "contents": { "kind": "markdown", "value": "```prisma\ntarget: model reference\n```\n\nThe model protected by this policy; it must declare @@rls." }
  }
},
"policy-block-keyword": {
  "hover": {
    "contents": { "kind": "markdown", "value": "Defines a row-level security policy controlling which rows can be selected." }
  }
}
```

`using` (optional) renders `using?: string`; `target` (required) renders `target: model reference` with no `?`, confirming the optional/required distinction carries correctly for a struct-block parameter, not just an attribute argument (Scenario 5). The `policy_select` keyword renders fence-free, matching Scenario 4's `enum` keyword shape. All three documentation strings match `packages/3-targets/3-targets/postgres/src/core/authoring.ts` verbatim (`policyUsingParam.documentation`, `policyTargetParam.documentation`, and the `policy_select` descriptor's own `documentation`). The addition produced no new diagnostics on `main.prisma` (still exactly the same 3, from the pre-existing `Oddity` model).

The script's § Scenarios deliberately not in this script now carries a correction note rather than a silently-edited false claim, naming the five real block keywords the premise missed, and the sign-off coverage map's S2-3 row points at Scenario 10 instead of "(CI only)".
