## Findings

### F-1 — ⚠️ High — a real-target `@default(...)` function call's name never gets a `function` hover, because an earlier literal arm in the same `oneOf` always "matches" first

**Scenario:** 6 — Function-name hover
**Step:** 1, 2 and 3 (`autoincrement()`, `now()`, `uuid()`)
**Oracle:** `spec.md`'s table row for `function`: `autoincrement()` + `FuncCallSig.documentation`.

**Observed** (verbatim driver output, hovering the real postgres target's registered default functions in a real multi-file project against the real `@prisma/orm-postgres/config` stack):

```json
"function-autoincrement": {
  "position": { "line": 13, "character": 36 },
  "hover": null
},
"function-now": {
  "position": { "line": 12, "character": 31 },
  "hover": null
},
"function-uuid-corroboration": {
  "position": { "line": 10, "character": 36 },
  "hover": null
}
```

Positions land squarely inside each function name (verified against the exact source text, reproduced below); the server published **no diagnostic** for any of these three lines, so the value did bind successfully — it just never carries a `function` resolution on its name token.

**Expected (per script):** a fence with the function's signature (`autoincrement()`, `now()`, `uuid(version?: 4 | 7)`) and its documentation from `packages/3-targets/6-adapters/postgres/src/core/control-mutation-defaults.ts` (`autoincrementSig`, `nowSig`, `uuidSig`).

**Root cause** (read, not fixed — out of this dispatch's scope):

`scalarDefaultArms` in `packages/2-sql/2-authoring/contract-psl/src/sql-attribute-specs.ts:204-233` builds the `@default` value's `oneOf` alternatives in this order:

```ts
: [str(), numLiteral(), bool(), nullLiteral(), ...funcArms, ...tagArms(), listArm()];
```

`tryBindExpression` in `packages/1-framework/2-authoring/psl-parser/src/binder.ts` only specially handles `oneOf`, `list`/`record`, `funcCall`, `identifier`, `entityRef`, `fieldRef` and `referencedFieldRef` (confirmed by listing every `case` in the function). Every other `ArgType` kind — including `str`, `num`, `bool` and `null`, all **not** kind-specific-narrowed to the written expression's actual shape — falls to the function's final branch:

```ts
default:
  return { matched: true, references, diagnostics };
```

(`binder.ts:663-664`.) This is the same "unconditional no-op" shape documented for an unrestricted `identifier()` with no fixed name — but here it means `str()` reports `matched: true` for **any** written expression, including a `FunctionCallAst` like `autoincrement()` that is not textually a string at all.

`oneOf`'s loop (`binder.ts:531-539`) returns on the **first** `matched: true` trial:

```ts
for (const alternative of rule.alternatives) {
  const trial = tryBindExpression(alternative, expression, ctx, modelContext);
  if (trial.matched) return trial;
  ...
}
```

Since `str()` is the first alternative in `scalarDefaultArms`'s list and it unconditionally matches, the loop returns immediately after trying `str()` — the later `funcCall('autoincrement', ...)` / `funcCall('now', ...)` / `funcCall('uuid', ...)` alternatives are never even tried, so the `function` resolution `tryBindExpression`'s `funcCall` case would have recorded on the call's name node (`binder.ts:573`) never gets recorded at all. No diagnostic appears because `str()`'s trial also reports no diagnostic — the value is simply, silently treated as if the trivial no-op arm had "validated" it.

This is a **binder correctness gap**, not a hover-rendering bug: `providePslHover` and `renderFunctionContent` are never reached for these three names because `binder.symbolForNode` has nothing recorded for them at all. The existing `hover.test.ts` unit tests for function-name hover (`'shows a function name without args and its documentation'`, `'shows a function name with args and its documentation'`) do not catch this because their synthetic `defaultSpec` fixture uses `oneOf(autoincrementFunc, dbgeneratedFunc)` — two `funcCall`s only, with no pass-through literal arm placed before them. The real postgres target's `scalarDefaultArms` is the first spec in the whole codebase (that this run found) to mix a pass-through-kind arm ahead of a `funcCall`/`identifier` arm in the same `oneOf`.

**Blast radius:** every postgres (and, by the same `scalarDefaultArms` code path, every other SQL-family target's) schema using the ordinary, extremely common `@default(now())`, `@default(autoincrement())`, `@default(uuid())`, `@default(cuid())`, `@default(ulid())` or `@default(nanoid())` pattern loses function-name hover. It does not affect diagnostics, completion, or the emitted contract (those presumably use a different resolution path, or are also silently affected — this run did not check), only this new hover kind.

**Reproduction:**

- `git rev-parse HEAD` → `318e44654dd261a597210318d600ba6ae750fe6e`
- `git status --porcelain` at observation time → only the pre-existing, unrelated `projects/lsp-hover/trace.jsonl` modification; nothing under `packages/`.
- Exact scratch schema (`wip/qa-scratch/lsp-hover-qa/main.prisma`, line 13): `  views     BigInt   @default(autoincrement())` — position `{line: 13, character: 36}` lands on the `c` of `autoincrement`.
- Driver: `wip/qa-scratch/driver/qa-driver.mts` (throwaway, not committed), run via `packages/1-framework/3-tooling/language-server/node_modules/.bin/tsx wip/qa-scratch/driver/qa-driver.mts`, driving the real `startServer` from `packages/1-framework/3-tooling/language-server/src/start-server.ts` over injected LSP streams, against the real `@prisma/orm-postgres/config` stack with no extensions and no live DB connection.
- Full captured JSON (22 scenarios) available in this run's session output; the three relevant entries are quoted verbatim above.

**Notes:** this is a real-target interaction the project's own synthetic `hover.test.ts` fixtures structurally cannot surface, because no existing fixture in the repository places a pass-through-kind (`str`/`num`/`bool`/`null`) arm ahead of a discriminating (`funcCall`/`identifier`/`entityRef`) arm inside the same `oneOf`. The fix most consistent with the slice's existing design-decision trail (D1 R2/R3, which hardened `identifier` and `oneOf` for exactly this class of correctness issue) likely belongs in `tryBindExpression`'s handling of pass-through kinds (`str`/`num`/`bool`/`null`/etc.) inside a `oneOf` — e.g. only treating them as matched when the written expression's shape actually agrees with the kind — rather than in `scalarDefaultArms`'s arm ordering, since the arm ordering (literal checks first) is otherwise a reasonable, common pattern. This dispatch does not fix it, per scope ("do not fix product code").
