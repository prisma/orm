### F-3 — 📝 Follow-up — ADR 269 says column order follows the source; the emitted contract and the database do not show it — ✅ resolved by the ADR wording change

**Check after the rewrite (working tree at `183278ac73`; the ADR change was not yet committed when read):** the paragraph "Position decides order" no longer contains "and with it column order". The sentences checked against scenarios 2 and 7:

> "That order is what the symbol table, the binder and the interpreters read, and it shows where order is kept: in enum member lists and in `contract print`."

This matches scenario 2: `contract print` and the enum's member list followed the moved inclusions.

> "It does not change the emitted `contract.json` or the order of columns in the database, because the contract's keys are sorted and tables are created with their columns in that order, with or without mixins."

The part about columns matches scenarios 2 and 7 (no line under `columns` or `fields` differed; the DDL lists columns alphabetically). The part "does not change the emitted `contract.json`" does not match for an enum; that is recorded as F-5. Project spec decision 5 carries the same new text. What follows is the first run's record.

**Scenario:** 2 and 7.
**Oracle:** ADR 269, "Position decides order": "Field order, and with it column order, follows the source."
**Observed:** moving `+Timestamps` in `Profile` changed nothing under the table's `columns` or the model's `fields` in `contract.json` (keys are sorted); the planned DDL and the migrated table list columns alphabetically:

```
CREATE TABLE "public"."Profile" (
  "createdAt" timestamptz DEFAULT (now()) NOT NULL,
  "id" int4 NOT NULL,
  "ownerName" text NOT NULL,
  "role" text NOT NULL,
  "updatedAt" timestamptz DEFAULT (now()) NOT NULL,
```

The source order is `id`, `createdAt`, `updatedAt`, `ownerName`, `role`. The inline schema gives the same DDL (its contract is byte-identical), so this is how the product treats every model and not an effect of mixins.
**Expected (per ADR):** a column order that follows the source, or an ADR sentence that claims only what is observable.
**Notes:** the position of an inclusion is observable in `contract print` and in an enum's member list, and both followed the move (scenario 2). Only the words "and with it column order" are not borne out. The project spec, decision 5, has the same sentence.

## Exploratory notes (scenario 18)

The two probe files were run at 18:33 UTC after about fifteen minutes of probing while they were written; the budget was kept. One case was added to `explore-cases.json` during the session (E.16).

Through `contract emit`:

- Emitted with no diagnostic: a field named `mixin` in a mixin (E.1); two models whose whole body is `+WithId`, each with primary key `id` (E.2); an empty mixin (E.3); `model User { id Int @id +Stamp }` on one line (E.4); a `///` comment before and a `//` comment after an inclusion (E.5); a relation mixin with a back relation on the target, and the same mixin in two models (E.12, E.13); a hyphenated mixin name `+time-stamps` (E.15).
- E.6, a mixin with `@@map("shared_table")` in two models: exit 2 with `why: buildSqlContractFromDefinition: duplicate table "shared_table" in namespace "public".` and no source position. The inline control E.6c gives the same output, so the missing position is not specific to mixins.
- E.7, an unused mixin with `thing Nope`: `PSL_UNRESOLVED_REFERENCE: Cannot find type "Nope"` at 4:9, once. The binder checks a mixin nothing includes, as the ADR says.
- E.8, `+Stamp` at the top level: `PSL_UNSUPPORTED_TOP_LEVEL_BLOCK: Unsupported top-level declaration "+"`. E.9, in a `types` block: `PSL_INVALID_TYPES_MEMBER: Invalid types declaration "+"`. Both point at the `+`. Neither mentions mixins.
- E.11, a lone `+`: `PSL_INVALID_MODEL_MEMBER: Expected a mixin name after "+"`.
- E.14, `@@index([tenantId])` in the mixin and again in the model: one index in the contract, no diagnostic. The inline control E.14c behaves the same.
- E.16, the mixin schema without `// use prisma-8`: `PSL_NO_OPTED_IN_SCHEMA_FILES: None of the matched files carry the "// use prisma-8" directive`.
- `contract print` on the mixin schema prints the inline schema; it never prints a mixin (a stated non-goal).

Through the language server:

- X.1: renaming `namespace auth` to `identity` edits the qualifier of both `+auth.Timestamps`, in a file that is not open.
- X.2: renaming a mixin to `9x` is an error response, `"9x" is not a valid PSL identifier`. X.3: `prepareRename` on the word `mixin` is `null`.
- X.4, X.5, X.27, X.28: definition, references and hover inside a mixin body work as in a model.
- X.6: renaming a mixin to the name of another mixin returns the edit, as rename does for every other declaration.
- X.8: completion after `model ` at the top level offers nothing, so `mixin` is never suggested as the next word. X.10: at the start of an empty top-level line the block keywords are offered; `mixin` is not one of them, which is right.
- X.12 to X.14: LSP formatting turns `+   SoftDelete` and `      +  Tenanted` into `  +SoftDelete` and `  +Tenanted`; a second format returns no edit.
- X.17: typing `createdAt DateTime` above `+auth.Timestamps` in `Invoice` gives `PSL_DUPLICATE_DECLARATION Mixin "Timestamps" provides "createdAt", which "Invoice" already has` with the range `<<+auth.Timestamps>>`.
- X.20, X.21: `+Tenanted` typed inside `model mixin SoftDelete` gives `A mixin cannot include another mixin` in `shared.prisma`; go-to-definition from it still opens `Tenanted`.
- X.24: F-1 and F-2.

Things that are not findings against this project but that a user of mixins will meet:

- Completion after `+` offers a mixin whose members the block already has. In `document_any_read` (which has `+ToAppUser` and its own `using`), `OwnerRead` is offered (12.21); accepting it gives two duplicate-member errors. The slice spec filters by keyword and by "already included" only, so this is as specified.
- Field-type completion does not offer the enum `Role`, in a mixin body and in an ordinary model alike (13.2, 13.28).
- Inside `roles = [ ]` the role `app_user` is not offered, only the namespace `unbound`, although the schema refers to the role as `app_user`; same in a mixin and in a policy (13.24, 13.31).
- An empty line in an enum body or an enum mixin body offers nothing (13.17, 13.34).

Ideas not explored: mixins in a MongoDB project; a mixin for `native_enum` or `role`; a schema of an earlier Prisma version containing `model mixin { }`; two contract spaces; a mixin with `@@id` included by a model that also has `@id`.
