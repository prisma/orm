# Deferred

Items found during the project that are out of its scope. Each says what to do later and why it was not done here.

- **Two deferred-at-lowering callbacks for indexes have different shapes.** In `packages/2-sql/2-authoring/contract-ts`, `DeferredIndexExpression` carries its own `fields`, while a deferred `options` function on `IndexConstraint` receives the columns of the index's `fields`, and no source code produces a deferred expression any more. Later: unify them into one `resolve(columns)` that returns `{ options?, expression? }`, or remove `DeferredIndexExpression` if no extension package uses it. Not done because unifying them changes an exported authoring interface the weighted full-text index does not need.
- **The SQL family builds a wrong intermediate schema node for a `fullText` index.** `contractNamespaceToSchemaIR` in the SQL family turns a `fullText` index into an index over its columns with the definition as storage options. It is correct only because the Postgres conversion replaces the node. No other caller exists today. Later: let the family conversion take an index conversion from the target, so the target builds the node once. Not done because it changes the family's conversion interface for every target.
- **Two checks that a full-text index covers text columns.** `@@fullTextIndex`, the TypeScript `fullTextIndex` helper and loading a contract check the `textual` trait against the Postgres target's built-in codecs; the index type registry's `columnTraits` checks the contract's composed codec lookup at contract build. They agree today, and would disagree if an extension package added a textual codec. Later: have the two authoring surfaces rely on `columnTraits`, keeping their own message only for a better source location. Not done because nothing registers an extra textual codec today.
- **A member on the ORM client collides with a contract namespace of the same name.** The client object returned by `orm()` holds one member per namespace next to its own methods, so a contract with a namespace named `scope` shadows the client's `scope` method and the application cannot make a scope for any model. Every future client member has the same problem. Later: put namespaces or the client's methods under their own member so names cannot collide. Not done because no contract names a namespace `scope` today and the change touches every call site that reads `db.orm.<namespace>`.
- **Resolved: `Scope` named two different things in the public Postgres facade.** The ORM client's type is now `QueryFragment`, so only the SQL builder's `Scope` and `ScopeField` remain.
- **A scope for one model does not carry the receiver's type through a body that keeps the row.** `Post.scope((p) => p.orderBy(...))` applied to a custom class after a `where` is typed as an ordered plain `Post` collection, without the class and the filter, although both still run. Later: when the body's row equals the model's full row, return the receiver's type with the facts the body established, as a scope for any model does. Not done because ADR 259 settles the simpler rule and documents it.
- **The `{ codecId, nullable }` field declaration has no consumer yet.** A fragment for any model accepts it for packages that do not import the facade. Slice 4 no longer builds package helpers (ADR 270), so nothing in this project consumes it. Later: keep it for packages that offer fragments, and add a fixture that is generic over the contract and uses only public names when the first such package exists; collection scopes built from indexes are the likely first consumer. Not done because the consumer does not exist yet.
- **One definition of a scope for any model costs about 18,000 instantiations on a large contract.** On a generated 200-model contract, one `db.orm.scope` definition costs 19,732 instantiations, while its first use costs 1,136 and each later use about 890, because each use checks the declared fields against the receiver's model only (ADR 259). What in the contract's type drives the definition cost was not measured. Later: if large applications see editor latency, find what the definition instantiates and reduce it. Not done because the per-use cost, which grows with the number of call sites, is already small.
- **A search document is not an expression of its own.** `fullTextMatches` and `fullTextRank` in `packages/3-targets/3-targets/postgres` take an index reference, a `fullTextDocument(...)`, or one textual column as their document, and the descriptor still declares a textual receiver: `searchDocument` in `query-operations.ts` makes the first column the operation's receiver and appends the others after the fixed arguments. Slice 4 (ADR 270) needs nothing more, because it passes index references. Later: make the search document a first-class `tsvector` expression built by a receiver-less operation through the same renderer, if a feature needs to select or combine documents. Not done because no feature needs it yet.
