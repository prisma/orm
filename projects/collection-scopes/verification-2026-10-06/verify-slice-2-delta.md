## Defects

### 1. Bulk writes still ignore a cursor, and a scope for one model can add one where the call site cannot see it

`src/collection.ts` 2651–2665 (`#assertNoLimitOrOffset`), called at 2472, 2549, 2645, 2790. `updateAll`, `updateAndCount`, `deleteAll` and `deleteAndCount` compile their statement from `state.filters` only, so a `cursor` is dropped like the limit and offset were. `Post.where((p) => p.views.gte(777)).orderBy((p) => p.id.asc()).cursor({ id: 4242 }).deleteAll()` deletes the matching rows before the cursor too; the read with the same chain applies `id > 4242`. A scope for one model has the full collection, so `Post.scope((p) => p.orderBy(...).cursor(...))` hides the cursor exactly as F02's limit case did. `deleteAll` with an include also returns only the rows after the cursor (the snapshot read uses the whole state, 2740–2747) while it deletes all of them. ADR 259 line 91, README 108 and the upgrade entry say "an order does not change which rows they change"; with a cursor the order does. The nested `update` path is safe: `cursor()` requires an order (1171), which it refuses.

Probe: `zz-delta-runtime.test.ts` R1 (line 26, all four writes carry the filter 777 and not the cursor 4242) and R2 (line 44, a `Post.scope` hides the cursor). Recommendation: refuse a cursor in the same check (it is the same class as the limit and offset), add it to the upgrade entry and the three docs, and add a test row.

### 2. A list of value objects can satisfy neither check: compile time and run time read the list kind from different places

Compile time reads it from the model's domain field (`src/scopes.ts` 111 and 125, `FieldMany<FieldsOf<...>[K]>`). Run time reads it from the storage column (`src/scopes.ts` 434, `column?.many === true`). For a scalar list both say list. For `addresses Address[]` the domain field has `many: true` but the storage column is one `jsonb` column without `many` (`storedAsListColumn`, `packages/2-sql/2-authoring/contract-ts/src/contract-definition.ts` 241). So `{ addresses: { codecId: 'pg/jsonb@1', nullable: false } }` is refused at compile time and accepted at run time, and the same with `many: true` is accepted at compile time and throws `ORM.FIELD_UNKNOWN` at run time ("Cannot apply a scope to Person: its field addresses does not match the declaration"). No declaration passes both. The commit message and ADR 259 line 99 say the two checks agree.

Probe: fixture `vo-list-fixture/contract.prisma` (emitted with the CLI); `zz-delta-a.ts` line 38 (compile-time refusal) and 45 (compile-time acceptance); `zz-delta-runtime.test.ts` R3, lines 63 and 71 (the reverse at run time). Recommendation: read `many` from the model's domain field at run time too, as the compile-time check and the body's typing do; add a value-object list to the soft-delete fixture with a test each way; say in ADR 259 which fields count as lists.

### 3. `upsert` ignores the filter a scope adds, so a tenant or soft-delete scope does not protect its update — needs a ruling

`src/collection.ts` 2217–2330. `upsert` is callable on any collection, including after `apply(scope)`, and compiles its statement from the input alone: the chain's filter, limit, offset and order are dropped without an error. `db.orm.public.Post.apply(forTenant(id)).upsert({ create, update, conflictOn: { id } })`, with the README's own `forTenant` example, updates the conflicting row whatever its tenant. This is not new, but it is the class the F02 ruling addressed (a write ignoring what a scope added), and the new principle "writes refuse what they would ignore" does not reach it. `create`, `createAll` and `createCount` also ignore the filter, but they change no existing row.

Probe: `zz-delta-runtime.test.ts` R4, line 87 (one insert statement with neither the filter value nor a limit). Recommendation: refuse `upsert` on a collection with a filter, order, limit or offset, with an upgrade entry. This changes `upsert`, which the F02 ruling did not name, so it needs Will's ruling.

### 4. Low: an undecided list kind is read as a list on a builder and as one value on an object

`src/scopes.ts` 44–48 (`BuiltMany`: `true extends Many`) and 65 (`Declaration extends { readonly many: true }`). A builder whose type says `many?: boolean`, which is any value typed as `ScalarFieldDeclarationBuilder` (public, framework components `codec` entry) or `ScopeFieldBuilder`, declares a list, so a library that takes the builder as a parameter gets a scope that refuses every single-value field at compile time, while run time reads the real builder and accepts them. An object with `many: boolean` declares one value, and run time reads the real value. Probe: `zz-delta-a.ts` line 50 (`DeclaredField<"pg/text@1", false, true>`, `Post.title` refused) and line 58 (`DeclaredField<"pg/text@1", false, false>`, `Tag.labels` refused). Recommendation: treat both the same way (one value unless the type says `true`), and add a type test.

## Not caused by this round

Postgres rejects `text[] LIKE`. The scope copies the model accessor, so this is a gap in the accessor, worth its own ticket.
