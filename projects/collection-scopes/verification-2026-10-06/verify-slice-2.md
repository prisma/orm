## New defects

1. **`update()` now refuses an offset it used to honour, while `delete()` still honours it.** `src/collection.ts` line 2379. `update()` on the plain path finds its row with `#findFirstMatchingRowIdentityWhere` (line 2420), which clones the collection and calls `first()` (line 2856); `first()` keeps the order and the offset and sets the limit to 1 (line 1399). So `Post.where(...).orderBy((p) => p.views.desc()).offset(2).update({ title: 'x' })` updated the third post by views before the fix round, and now throws `ORM.ARGUMENT_INVALID`. `delete()` uses the same lookup (line 2601), has no refusal, and still runs that chain with `OFFSET 2`. Only `update()`'s nested-mutation path (line 2399, filters only) ignores the order and offset. ADR 259 line 91, README line 108, the skill and the upgrade entry all say `update` "changes every row that matches the filter"; it changes one row. Probe: `zz-verify-runtime.test.ts`, block R1 (the delete lookup plan contains `"offset":2`; the update is rejected). This needs Will's ruling, because the F02 ruling named `update`. Recommendation: keep the refusal for `updateAll`, `updateAndCount`, `deleteAll` and `deleteAndCount`; for `update`, refuse only on the nested-mutation path, or make that path honour the order and offset; correct the four texts.
2. **When TypeScript cannot infer a field scope's type parameters, a valid collection is refused, and the error names a field the model has.** `src/scopes.ts` lines 151–162 put the check in the call signature over inferred `ModelName`, `NsId` and `ReceiverContract`. When these are erased to their constraints, `ModelName` is `string` and every declared field is reported missing.
   - `notDeleted.call(undefined, plain.Post)` and `notDeleted.apply(undefined, [plain.Post])` fail with "Property 'the model has no field with the codec and nullability the scope declares' is missing … : "deletedAt"", though `Post` has `deletedAt` (`zz-verify-a.ts` line 65, `zz-verify-c.ts` lines 27–28). `.bind` works.
   - `plain.Post.apply(flag ? notDeleted : deletedLast)` is refused; the second overload's message again says `Post` has no `deletedAt` (`zz-verify-a.ts` line 33). Choosing inside a function works.
   - I did not check whether 3cb751a92d accepted these. Impact is low, because there are workarounds, but the message is false. Recommendation: when the receiver's model cannot be read (`ModelName` is `string`), report that instead of listing fields, and add a type test for a conditional choice between two scopes, which ADR 259's "control flow stays in the language" invites.
3. **ADR 259 line 97 and the skill describe custom classes as they behaved before the F10 change.** Recorded under F05 above. Probes `zz-verify-b.ts` and `zz-verify-c.ts` line 38.
4. **The soundness test for explicit type arguments was weakened.** `test/field-scope.types.test-d.ts` line 187 became `(rows: unknown) => rows` in 212dcbfc9e, whose title mentions only the namespace test. The `@ts-expect-error` is now satisfied by the `unknown` return alone: the same body with facts that claim nothing is refused too (`zz-verify-c.ts` line 41). So the test would pass even if explicit facts were not checked. The original body still gives the intended error, "Type 'boolean' is not assignable to type 'true'" (`zz-verify-a.ts` lines 25–28). Fix: restore `(rows) => rows`.
