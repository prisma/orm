# Plan: capabilities by database version

Delivers [spec.md](spec.md). Each slice is one pull request. The order is the recommended one; the building session may change it with a reason.

## Before the first slice

Confirm two things in the code and record the answers here:

- How the tooling builds the capability list it hands a contract source (`context.capabilities`), and so what must change for a version to select the target's capabilities.
- Whether the signing check can be built on interfaces the framework already has. If it needs a framework change, raise it with the operator before building.

### Answers (2026-11-25, read from the code)

**How the tooling builds the capability list.** The framework builds it from the config's component descriptors, and does so twice:

- `createControlStack` (`packages/1-framework/1-core/framework-components/src/control/control-stack.ts`) merges the `capabilities` of the target, the adapter and the extensions, in that order, later ones winning on the same key. The driver is not included. `askSource` hands the result to the contract source as `context.capabilities`.
- After the source returns, `enrichContract` (`packages/1-framework/3-tooling/cli/src/control-api/contract-enrichment.ts`) merges the same descriptors over the contract's own list. This runs for both authoring routes, so a list a source narrowed would get the descriptors' flags added back.

What follows for the design:

- **The facade resolves the capabilities once and hands them to the contract source. The framework stays as it is.** The facade looks up the version's row in the target's table, merges the `capabilities` list over it in order, keeps the flags that are on, and gives the result to whichever source reads the contract: `defineContract` for a TypeScript contract, the Prisma schema provider, or the Prisma 7 schema provider. Every control descriptor of the target, the adapter and the driver declares no capabilities, so the framework's two merges add nothing. An earlier version of this plan had the version produce a target descriptor that carries the row. The first build showed that was a second mechanism beside the one the TypeScript route already needs, and the two disagreed: a flag turned off in the list came back on, a client built without the facade's config emitted a contract with no flags and no error, and the Prisma 7 route needed a side table. One path removes all three.
- **The `capabilities` list** is an array of capability sets, each the nested object a component declares. It defaults to the sets of the adapter and the driver the facade's client uses at runtime. A list the user writes replaces the default. A later set overrides an earlier one, and `false` turns a flag off, the same in every authoring route.
- **A config built without the facade's `defineConfig`** (the Supabase package, tests) passes the same resolved capabilities to the source itself, through a function the facade exports. Nothing can refuse a source that was given none without the SQL family knowing about one target, so such a config that forgets them gets a contract with no database flags. This is recorded as a known limit.
- **Correction to the design notes:** `defineContract` has no `capabilities` input today. It was removed, and the PostgreSQL facade also removes `target` and `adapter` from the input and binds its own. The facade's `defineContract` gains `databaseVersion` and the connection capabilities as new inputs.
- **Correction to the design notes:** the SQL profile hash does not cover capabilities today. `buildSqlContractFromDefinition` passes an empty set, so every PostgreSQL contract has the same profile hash. For a signature to mean "this database was checked for these capabilities", the SQL profile hash must cover the contract's capability list. That is a change to a hash rule. The pull request that fixes the hash rules for Prisma 8 (prisma/orm#31203) makes it, so each rule changes once; this project's slices do not change hash rules. Slice 1 is built on main after #31203 merges, and only changes which capabilities a contract lists.
- **No PostgreSQL flag differs between versions 15 and 18 today.** Every flag the adapter declares holds on 15. The table is built and tested, with rows that are equal at first. The slice's "16 does not type-check a feature that needs 17" is shown in tests with a table that has such a row, until a real feature needs one.
- **Flags nothing reads**, beyond the three extension flags: `postgres.orderBy`, `postgres.limit`, `postgres.lateral`, `postgres.jsonAgg`, `sql.enums`. They are removed with the extension flags.

**Whether the signing check fits the framework's interfaces.** The check and the refusal to sign do. Two things around it do not:

- The check goes in the PostgreSQL target's schema diff (`diffPostgresSchema`), which the SQL family's `verifySchema` calls. It already receives the contract and the introspected database node, whose `pgVersion` the adapter reads during introspection. `db verify`, `db sign` and the runner behind `db migrate`, `db update` and `db init` all call `verifySchema`, so all refuse. The result type has room for the failure (an issue with its own text, and a result code).
- **The advice the CLI prints** for a failed verification is framework code (`schemaDriftNextActions`), and always offers `db update`, which cannot upgrade a server. The operator approved, on 2026-11-26, a target-neutral data type for a database that does not provide what the contract requires, rendered by the framework, which the CLI prints with no drift advice. The wording names the first version that provides each missing capability, so the contract need not store the stated version. Signing checks only the capabilities the target's table knows; a capability neither the database nor the client's adapter and driver provides is reported by the client, at compile time and at start, because signing cannot tell an unknown capability from one the application's driver provides. Built in [slice-refusal-as-data.md](slice-refusal-as-data.md).
- **`orm init` writing the list** needed a framework change, because the CLI wrote `prisma.config.ts` from its own template. The init contribution has one optional member that returns the config's `contract:` entry as a node written with the tools migration files use (`TsExpression` and `renderImports`), with one more method that returns the entry's real value for the check of a kept Prisma 7 schema. A JSON structure the CLI printed and ran was built first and deleted: it was a second way to write TypeScript and could not express an entry that names an import. `init` writes the newest version's list, because it writes the config before the driver is installed and so cannot ask the server; writing the list for the server's version is in [deferred.md](deferred.md).

## Slices

1. **Each component declares its own capabilities, and the version selects the target's (PostgreSQL).** The target holds the table of versions. The database flags move from the adapter to the target; the driver declares what the connection provides, including interactive transactions; the adapter declares what it can write. The unread extension flags are removed. `defineContract` and the config's contract entry take the required version and the optional connection capabilities. `orm init` writes the version. Fixtures, examples and their hashes are regenerated. Done when a project on version 16 does not type-check a feature that needs 17, and a project on 17 does.
2. **The client goes by the contract.** The runtime stops merging the stack's capabilities over the contract's. The stack is checked against the contract at compile time and at start, reported as a signature mismatch is. Done when an HTTP driver with a contract that requires interactive transactions fails to type-check and is reported at start.
3. **Signing checks the database.** The shared verification compares what the database provides with what the contract requires, and the error speaks in versions. The minimum server version constants become the first row of the table. Done when signing a PostgreSQL 15 database with a contract for 17 fails with the message in the spec, shown against a real database.
4. **The other targets.** MySQL, MariaDB, SQLite and MongoDB, each checked against its own code. Settings such as `sql_mode` and topology such as a MongoDB replica set are read at signing. GA does not wait for this slice.
5. **Syntax in the Prisma schema language.** The design is required before the project closes. Building it is preferred.
6. **`contract emit` warns when the contract leaves out the driver's capabilities.** A user who writes `requiredCapabilities: [...postgres17]` without the driver's list gets a contract with no connection capabilities, so features such as `transaction()` are unavailable although their driver provides them, and nothing tells them why. Emit compares the contract's list with what the config's driver provides and, when the contract leaves some out, prints a warning that names them and shows the line to change, built from the same contribution `init` uses to write the list (`requiredCapabilities: [...postgres17, ...postgresDriver]`). If that proves too hard, a warning that the contract leaves out capabilities the driver provides, and that adding them enables more features, is a start. A user who left them out on purpose, such as behind a pooler that cannot hold a transaction open, needs a way to keep the warning quiet; deciding that is part of this task. Not needed for GA.
7. **Records and close-out.** Before the records, the evidence for spec section 5.1: the real message at signing, at client start against a database that was never checked or was checked for another contract, and for a contract whose capabilities the installed table does not know, each judged for whether a user can act on it. If one can only name capabilities, the contract stores the version, decided and built before `8.0`, and the decision record that says the contract never stores it is changed in place. The subsystem docs, the capability ownership rule and the decision records are updated in place. The upgrade instructions and the upgrade skill are updated. Each of the thirteen scenarios has its evidence.

Slices 1 to 3 are what GA waits for. Slice 1 changes hashes, so it is coordinated with the stored-format work on contract hashes.

## What the hash rule means for this project

The pull request that fixes the hash rules (prisma/orm#31203) makes the SQL profile hash cover the contract's whole capability list. Its decision record adds that, within a major version, the list Prisma writes for an unchanged contract source and configuration does not change. For this project:

- **A supported version's row is fixed for the major.** Adding a flag to the row of PostgreSQL 17 would change the hash of every contract for 17, and every signed database would have to be signed again. So a feature that needs a newer database can arrive in a minor release only with a new version row, such as PostgreSQL 19. A new flag on an existing row waits for a major. A test in the target pins each row as literals.
- **The connection's capabilities are in the signed list.** Switching to a driver with a different set changes the profile hash, and each database is signed again with `db sign`. Signing checks only the database's flags, so the hash could cover only those. That would need the hash function to know which flags are the database's, at emit and wherever a contract's hashes are verified, through a hook the hash rules have just removed. One rule over the whole list is simpler, a change of driver is rare, and signing again is one command. A driver's set is fixed for the major for the same reason a row is.

## Direction settled on 2026-11-27 (built in [slice-required-capabilities-list.md](slice-required-capabilities-list.md))

- **Where the requirements are written.** The aim is that the author writes them in the contract's own source: `defineContract` for TypeScript, and syntax in the Prisma schema language. The config's contract entry is a stopgap for a Prisma schema until that syntax exists, not the destination. Every design choice is judged against the authoring source, not the config.
- **The author writes one visible list.** `requiredCapabilities: [...postgres17, ...postgresDriver]` replaces `databaseVersion` and the optional `capabilities` list. `init` writes the whole list, so a new project's requirements are visible. The facade has no default: the list must be present and not empty, and that is the only check. The refusal shows no example; the docs say what to write.
- **Keys are prefixed by the expected provider:** `db.` for the database, `conn.` for the connection. Signing then refuses a `db.` key its table does not know, and the client checks only `conn.` keys, which closes the gap where an unknown key was signed unchecked. This and the stored field's rename are the pull request after the list, before `8.0`. **Before starting it, check in with the session that versions the stored file formats** (alexvanhalen-55, "ga-compat-2-stored-files", session id `local_22c4a41c-ae0e-4329-a257-43b6e9a18a23`, prisma/orm#31200): the rename changes what `contract.json` contains, so it must fit that work's format version and its rule for reading files written by earlier releases.
- **Three words:** a capability is *provided* by a database version or a connection and *required* by a contract. The contract's field is `requiredCapabilities`; providers keep `capabilities`.
- **Two messages,** in one form everywhere: a required capability that is not provided, and a feature that is unavailable because the contract does not declare the capability it needs. `missingCapabilityRemedy` goes.
- **Records to update with the build:** the glossary ("Capability", "Adapter", "Driver"), the capability ownership rule, the decision records on capabilities (ADR 031, 065, 117, 335), the subsystem docs (Data Contract, Adapters & Targets, Runtime & Middleware Framework, Migration System, CLI), the error reference, the upgrade instructions, and [psl-syntax-design.md](psl-syntax-design.md), which was designed for `databaseVersion`.

## Must not be lost

- By the end of the project the Prisma schema language syntax is at least designed.
- The destination is the contract's own source, in TypeScript and in the Prisma schema language. The config entry is a stopgap.
