# Slice 3, dispatch a: values and the codec's four methods

Dispatch a of `projects/data-types-completion/slices/3/plan.md`. Read the slice plan, ADR 254 sections "At a glance", "Decision", "Values", "Codecs", "Casts" and "Reading a written default", and decisions 1, 2, 15, 21, 22 and 23 in `design-notes.md` under "A data type owns its values". The map of every codec, interface and caller is `projects/data-types-completion/slices/3/notes/inventory-codec.md` sections 1 to 3, 6 and 7.

This dispatch changes how values are represented and what the codec methods are called. It does not change what any contract stores, what any DDL writes, or what any query returns.

## Build

1. **`DataTypeValue`** in `framework-components` (`src/shared/`): `{ type, params, value }`, where `type` is the data type id, `params` the type's parameters (an empty object for a type without any) and `value` the JSON form `contract.json` stores. It is generic over the JSON type so the type-level channel in item 7 can follow it. It is frozen, and nothing outside the data type module can construct one: no exported constructor, no object literal that type-checks as one.
2. **Data types construct values.** `DataType` gains `fromContract(json, params): DataTypeValue`, `toContract(value): JsonValue` and `withParams(value, params): DataTypeValue`. `DataTypeSpec` gains what a type declares to make these work: a reader of its stored JSON under its parameters, and where parameters change a value's spelling, how they change it. A reader refuses with the same error convention the built-in `decodeJson` methods use today (`refuseJsonValue`, `RUNTIME.DECODE_FAILED`, `meta.received`), and its message names the type, not a codec. Two values are equal when their types and parameters are equal and their JSON is equal as canonical JSON; add one exported function for that.
3. **Every data type declares its reader**, in every package: Postgres, SQLite, the SQL family's `sql/expression`, pgvector, postgis, arktype-json's type if it has one, and Mongo's. For this dispatch each reader accepts exactly what the codecs of that type accept in `decodeJson` today, including the database's spellings that includes still hand them (for example a Postgres timestamp in the session time zone). Dispatch b narrows the date and time readers. Where the codecs of one type accept different JSON today, stop and report the type and the difference.
4. **Parameter limits move from codecs to types.** `pg/int4`'s range, `pg/int2`'s range, the `pg/char` and `pg/varchar` lengths (a bare `character` is `character(1)`), `numeric(p,s)` and `vector(n)` are checked in the type's reader against `params`, and the codec checks only parameters it keeps for itself, such as `arktype/json@1`'s schema. Find every other parameter check in a codec's `decodeJson` and move it the same way; list them in your report.
5. **`withParams`.** It gives a value the column's parameters: it refuses a value they exclude and writes the spelling they give it. `numeric(10,2)` turns `"1.5"` into `"1.50"` and refuses `"1.234"` (refused, not rounded) and `"123456789.5"`. PSL lowering (`contract-psl/src/data-type-default.ts` and the value-object default path) calls it after the cast and before the codec, as ADR 254 "Reading a written default" step 4 says. The TypeScript builder's `.default()` path reaches it through `toDataTypeValue`. This closes TML-3479: add a test that a `Decimal(10,2) @default(1.5)` column stores `"1.50"`, and one that `@default(1.234)` is refused with `PSL_INVALID_DEFAULT_LITERAL`. Check against PGlite that PostgreSQL prints `1.50` for that column's default and for a row.
6. **The codec's four methods.** `Codec`, `CodecImpl`, the SQL `Codec` (`relational-core/src/ast/codec-types.ts`), `MongoCodec` and the `mongoCodec()` factory have `fromDataTypeValue(value: DataTypeValue): TInput`, `toDataTypeValue(input: TInput): DataTypeValue`, `fromWire(wire, ctx): Promise<TInput>` and `toWire(input, ctx): Promise<TWire>`, and no other value methods. `fromWire` and `toWire` are `decode` and `encode` renamed, with their bodies unchanged. `fromDataTypeValue` is `decodeJson` without the checks that moved to the type in items 3 and 4; it keeps checks of the application value's own limits (`pg/int8number@1` refusing digit text past 2^53). `toDataTypeValue` is `encodeJson`, finished by constructing the result through the codec's data type with the codec's parameters, so it cannot return a value its type does not hold. Convert every codec the inventory lists, including the SQL family templates as each target adapts them and the subclasses that call `super`, and every test file that defines a codec. Rewrite the doc comments on `Codec` and `CodecImpl` to describe the four methods in two sentences each; drop the old "JSON methods" text.
7. **The type-level channel.** `DescriptorCodecJson` and `ExtractCodecTypes`'s `json` member follow `toDataTypeValue`'s value type. The member keeps its name, so no committed `contract.d.ts` changes.
8. **Every caller** of `encodeJson` or `decodeJson` (inventory section 3, plus anything #30628 added: `enumRefusalOf`, `db.enums`, the enum read-backs) calls the new methods. Where a caller holds contract JSON, it builds the value with the column's data type's `fromContract(json, params)` and passes it to `fromDataTypeValue`. The ORM's include and aggregate decoding (`sql-orm-client/src/collection-dispatch.ts`, `aggregate-empty-result.ts`) does the same for now; dispatch b moves it to `fromWire`.
9. **Test kits.** Both codec test kits assert, for every case, that `toDataTypeValue(fromDataTypeValue(v))` equals `v`. Their projection assertions keep their current meaning with the renamed methods; dispatch b rewrites them.

`toCanonicalForm` and `canonicalFormOf` stay in this dispatch; dispatch e deletes them. Do not change any JSON projection, any DDL default rendering, or the Prisma 7 reader.
