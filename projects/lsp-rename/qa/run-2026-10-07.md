## Findings

### F-1 — 📝 Follow-up — after a rename onto an existing name, renaming back does not restore the project

**Scenario:** 9 — Rename to a name already declared
**Step:** 9.5 (and 9.6)
**Oracle:** project spec non-goal "Collision checks": "Renaming to a name that is already declared, or to one that changes how another reference resolves, is not rejected. The result is reported by the existing diagnostics (`Duplicate declaration of "…"`), and the user undoes the edit." The spec gives no expectation for a second rename.

**Expected (per script):** none written; the script asks for the responses to be recorded.
**What it means for the user:** before 9.2, `posts Post[]` in `auth.prisma` referred to `model Post` in `post.prisma`. After `Member` was renamed to `Post`, the project has two top-level `Post` models and the reference resolves to the one in `extra.prisma`. A user who then presses F2 on the new `Post` and types `Member` again, instead of using the editor's undo, gets `posts Member[]` in `auth.prisma`: the first rename changed one place, the second changes two, and the project does not return to its starting text. 9.6 shows the same from the reference: it now belongs to the renamed model, and the original `model Post` in `post.prisma` is in neither edit.
**Reproduction:**

- `git rev-parse HEAD` → `8540f84b63bc00aad66e2fefaccb9c6139d14316`
- `git status --porcelain` at observation → ` M projects/lsp-rename/trace.jsonl` (the orchestrator's file) and `?? projects/lsp-rename/qa/`
- Mutated files: none (edits are applied in the driver's and the server's memory only)
- Exact command: as above

**Notes:** Each response is correct by the project's rule "Edits equal references": the edit is what find references returns from that position in the text the server holds. The behaviour is the consequence of the non-goal the operator decided on 2026-10-07 (no collision check), and the spec already says the user undoes the edit. What the spec does not say is that undo is the only way back. Which of two same-named declarations a reference resolves to was not investigated; here it was the one in `extra.prisma`, which sorts before `post.prisma`.

### F-2 — 📝 Follow-up — the duplicate-declaration diagnostic is on the declaration that was there before, with a second diagnostic elsewhere

**Scenario:** 9 — Rename to a name already declared
**Step:** 9.3
**Oracle:** same non-goal: "The result is reported by the existing diagnostics (`Duplicate declaration of "…"`)".
**Observed:**

```
  extra.prisma: (none)
  post.prisma:
    2:7 PSL_DUPLICATE_DECLARATION Duplicate declaration of "Post"
  session.prisma: (none)
```

**Expected (per script):** a `PSL_DUPLICATE_DECLARATION` diagnostic, `Duplicate declaration of "Post"`. That is met.
**What it means for the user:** the file they renamed in, `extra.prisma`, shows no diagnostic. The duplicate is reported at `model Post` in `post.prisma`, a file they did not touch, and `auth.prisma` reports an orphaned backrelation, because `posts Post[]` now resolves to the renamed model, which has no relation back to `User`. With `post.prisma` and `auth.prisma` closed, the only sign in the editor is the Problems view.
**Reproduction:** same command, HEAD and status as F-1.

**Notes:** These are diagnostics that existed before this change; this change did not touch the code that produces them. It is recorded because the spec's sentence reads as if the user sees the conflict where they made it.

- Demo schema (`examples/prisma-8-demo`, postgres target with pgvector, one file): 306 positions, 80 with a non-null rename result, 54 distinct edit lists, no violation. 80 and 54 are the numbers the find-references sweep reported for the same file on 2026-10-06, which is what "Edits equal references" predicts.
- The sweep checks consistency (rename against find references and against `prepareRename`, own token present, range text, new text). It does not check completeness: a usage neither request returns would not be noticed. Scenarios 1 to 4 and scenario 8 are the completeness checks.
- Step 8.0 printed no file at all: with no document open yet, the server had published nothing 1.5 s after `initialized`. Diagnostics for all five files were present at 8.2, after the first `didOpen`. Rename is not involved at that point.
- The `changes` object lists files in path order (auth, post, session), not in the order of `inputs` in the config. Keys of a JSON object carry no order for the client; noted because the find-references run filed the same ordering as its F-1.
- 6.8: an invalid name on a position that cannot be renamed is an error response, not `null`. The slice spec says the name is checked before find references is called, so this follows; a client that sends `prepareRename` first never gets there.
- Message wording (scenario 6, judgement): `"My Model" is not a valid PSL identifier` quotes the input and says what kind of thing was expected. It does not say what an identifier may contain.
- Not explored for lack of a suitable real schema: a model and a namespace of the same name, a generic block that is not an enum, a cross-space reference. All three are covered by fixtures in `rename.test.ts`.
- Not explored: a rename requested while another file has unsaved edits that add or remove a usage. Scenario 8 covers edits made through the rename itself; the find-references QA covered unsaved edits for the underlying lookup.
