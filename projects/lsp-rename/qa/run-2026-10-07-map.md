# Manual QA report — lsp-rename (rename with map attributes) — 2026-10-07, second run

> **Script:** `projects/lsp-rename/qa/manual-qa.md` (revised for the map attribute; committed together with this report)
> **Runner:** Claude Opus 5.5, the session that implemented the change (not a fresh context; see Summary)
> **Environment:** Linux 7.2.8, Node v24.21.0, branch `psl-rename` at `ccfbf12e45`, CLI rebuilt with `pnpm turbo run build --filter=@internal/cli` after that commit (26 tasks, none cached)
> **Started / finished:** 2026-10-07T15:50Z / 2026-10-07T15:54Z
> **Verdict:** ❌ Fail

## Summary

Renaming a Postgres `native_enum` block breaks the schema: the block is renamed and gets `@@map`, but the `pg.enum(OrderStatus)` field type that names it is not edited, so the project has an unresolved reference and `contract emit` fails (F-1). The cause is in what find references returns, not in the map attribute. Everything else the script expects was met: a model and a scalar field renamed from a reference in another file get the map attribute in the declaration's file, diagnostics stay empty, the formatter leaves the attribute in place, and `contract emit` produces the same storage hash before and after; eight kinds of rename that must get no attribute get none; the earlier scenarios 1 to 9 match their revised expectations; three sweeps over 475 identifier positions found no violation. F-2 records that even with the `pg.enum` usage corrected by hand, the storage section of the contract differs after a `native_enum` rename in one entry key. F-3 and F-4 are the two observations of the first run, seen again. The operator sections were not run. The runner is the session that implemented the change.
