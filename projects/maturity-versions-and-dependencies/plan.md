**Spec:** [spec.md](spec.md). The design it implements is on the branch `ga-compatibility`, in `projects/ga-compatibility/designs/6-maturity-versions-and-dependencies.md`.

In this plan, "our packages" means the 22 packages this repository publishes under `@prisma/orm-*`.

## Slices

Slices 1 to 4 are in the order of what cannot be changed after release `8.0`; slices 5 and 6 were added later.

- Who lists whom comes first. Once applications exist that list only a facade, moving the platform packages to peers would break every one of them.
- The suffixes in a version come second. `-ea.0` and `-preview.0` cannot be renamed once a package has been published with them.

### 6. Apps that create-prisma generates list the platform packages

Added on 2026-11-25. **After this slice:** an app generated by create-prisma, under every package manager it supports and with every template, lists the platform packages and their required peers, and installs and emits its contract under Yarn.

Why: from the release that contains slice 1, the package for a database names the platform packages (framework, family, target package, toolchain) as peers instead of installing them. `prisma orm init` writes them into an app's `package.json`, but create-prisma writes that file itself and does not run `init`. Yarn installs no peers, so a Yarn app would get none of them and fail to load; npm, pnpm and Bun apps would fail the same way where installing peers is turned off.

What create-prisma has today, checked on its `main`:

- `src/constants/dependencies.ts` pins `@prisma/orm-postgres` and `@prisma/orm-mongo` at an exact release candidate, and `prisma`, `@prisma/composer` and `@prisma/composer-prisma-cloud` beside them.
- `yarnPeerDependencies` lists, per package it writes, the required peers a Yarn app must list (`@prisma/orm-postgres`: `@types/pg`, `pg`, `temporal-polyfill`; `prisma`: `@prisma/cli-engine`). `writeYarnPeerDependenciesEffect` in `src/tasks/install.ts` adds them for Yarn only, and `bun run check:pins` checks each list against the registry.
- `writePrismaDependenciesEffect` writes the database package; the `turborepo` template also writes it into `packages/database/package.json`.

What changes:

- Every generated `package.json` that lists the package for a database also lists the platform packages that package names as peers, at the same version, and every other required peer they declare, such as `@prisma/cli-engine` and `temporal-polyfill`. For every package manager, not only Yarn: the app's own lines are what give it one copy, as ADR 329 records. The list comes from the database package's published `peerDependencies`, through the existing check against the registry, so it cannot drift from the release.
- Whether Deno needs the same lines is checked, not assumed.
- CI builds, installs and emits a Yarn PostgreSQL app; today it builds a Yarn MongoDB app only.
- From release `8.0`, the lines follow what an application writes under ADR 330: a caret for a GA package, a tilde on every line for an app on a package below GA, such as MongoDB's. That is a later change in create-prisma, made when it moves to release `8.0`.

It lands in the create-prisma pull request that moves it to the first release of prisma/orm containing slice 1, because the pins are exact and nothing changes before that move.

### 5. Every release's notes have a "How to upgrade" section

Agreed with the operator on 2026-11-25, through the stream. From the next release candidate, each GitHub Release body (`docs/releases/v<version>.md`, which the publish workflow uses) carries numbered steps a person can follow. Today a release links to recipes written for an agent and lists the breaking changes, with nothing that says what to do. Starting before release `8.0` is deliberate: it puts pressure on each release candidate to carry few changes a user must make by hand.

- The steps for people, the agent's recipe and the list of changes come from one source, never written separately. The likely source is the fragments each pull request adds under `upgrade-instructions/pending/`, which the release-preparation skill already assembles.
- Whether the fragment system is retired later is another project's decision; this slice does not remove or redesign it.
- To work out, checked against the release-preparation skill and the publish workflow: how the section is generated at release preparation, how the check on release notes requires it, and what it says when a release needs no action.

### 1. The application lists the platform packages, and our packages name each other as peers

**After this slice:** a new application's `package.json` lists the facade and every platform package the facade needs. None of our packages brings a copy of another: each names the others as peer dependencies. Versions are still `8.0.0-rc.N`, written exactly.

**First, in the other repositories.** Three packages carry their own `@prisma/orm-toolchain`: `prisma` (prisma/prisma-cli), `@prisma/composer-prisma-cloud` (prisma/composer) and this repository's test command (`test/prisma-bin`). Today the toolchain brings the framework with it. Once the framework is a peer of the toolchain, each of the three must list `@prisma/orm-framework` itself, or it cannot load under Yarn, which installs no peers. Adding the line is harmless today. So it is added, and released, in prisma/prisma-cli and prisma/composer **before** this slice merges. This matters because a release of this repository starts a `prisma` release automatically.

**Then, in this repository:**

- **Manifests.** Every dependency between two of our packages becomes a peer dependency. The list of who names whom is computed from `packages/0-shared/publish-surface/src/shells.ts`, and `validateShellManifest` in `packages/0-config/tsdown/shell-build.ts` fails the build when a manifest disagrees. That check changes from "one dependency per sibling" to "one peer per sibling, and no dependency on a sibling".
- **`prisma orm init`.** It adds each platform package by name, with the version written out. It reads the names from the peer dependencies of the facade it installed, and follows them until no new `@prisma/orm-*` name appears, so the manifests stay the one list. MariaDB shows why it follows them: its facade names the MySQL facade and the MySQL target, so a MariaDB application lists those too.
- **What follows the manifests.** The examples and apps, the test applications, `test/prisma-bin`, the packaging tests (`facade-tarball`, `extension-tarball`, `orm-better-auth-tarball`, `standin-target`, and the init journey's harness), each package's README, `docs/reference/Package Naming Conventions.md`, the `prisma-8` skill (`quickstart.md`, `build.md`, `upgrade-app.md`, `upgrade-extension.md`, `build-a-target-package.md`), `skills/DEVELOPING.md`, and the sentence in `.agents/rules/use-timeouts-helper-in-tests.mdc` that says an example depends on one facade and nothing else.
- **The check.** A packaging test installs packed packages in an application that lists the facade, the platform packages and an extension, and requires one copy of each platform package. A second case packs one platform package at a different version from the facade and requires the install to report the mismatch. The existing tests of that kind for extensions and for Better Auth stay.
- **Upgrade instructions** for applications (add the platform packages to `package.json`) and for extension authors (move the framework, family and toolchain from dependencies to peers).
- **Decision record.** A new record on how our packages depend on each other. It amends the record on the published packages (ADR 242), whose rule that an application lists one facade it replaces, and the record on library integrations (ADR 328). It names the Supabase extension's peer on the PostgreSQL facade as the one exception to "an extension is never tied to a facade", and records the monorepo limit below.

**With the release candidate that carries it, in prisma/web:** the install instructions of the Prisma 8 docs list the platform packages. The release procedure already opens a prisma/web pull request for each release.

### 2. Each package declares its level, and its version, ranges and tag follow from it

**After this slice:** the release number is `major.minor`. Each of our packages declares its level in one place. One function gives each package its version, the range it writes on each other package, and its tag. Until release `8.0` is cut the result is what is published today: `8.0.0-rc.N`, exact, under `latest`.

- **Level declaration,** and a build failure when a GA package of ours names a package of ours below GA.
- **Versions.** GA: `X.Y.Z`, with its own patch number. Below GA: `X.Y.0-<level>.<n>`, with its own counter. At release `8.0` every package starts at patch 1 instead: `8.0.1`, `8.0.1-<level>.<n>`. ParadeDB: `0.x`. A development build, published on every push to `main` under the `dev` tag, keeps today's form: the package's version followed by `-dev.N`, with every package of one build naming the others exactly.
- **Ranges,** written when a package is packed and never by hand, on the release's first version (`X.Y.0`, or `8.0.1` at release `8.0`): `~X.Y.0` between a facade and the platform packages and among the platform packages; `^X.Y.0` from an extension or a library integration to the platform packages; a tilde on the dependency's own version when the dependency is below GA.
- **Tags.** A GA release goes under `latest`. A release below GA goes under `latest` when the package has never had a GA release, as the design's section 5 says, and under a tag named after its level otherwise.
- **`prisma orm init`** writes a caret for a GA facade and a tilde on every line for a facade below GA.
- **Scripts and checks that assume one version:** `set-version.ts` and its helpers, `determine-version.ts` and its helpers, `bump-version.ts`, `publish-packages.mjs`, `publish.yml`, `check-publish-deps.mjs` (which gains the rule for ranges between our packages), `check-upgrade-coverage.mjs`, `check-release-notes.mjs`, `check-conformance.mjs`, the skill's version stamp, the Supabase extension's version stamp in contracts, and the tests of each.
- **The check.** A dry run of the publish scripts prints a table of package, version, ranges and tag, and a test compares it with a committed expectation for three releases: the next release candidate, `8.0.1` and `8.1.0`.
- **Decision record.** A new record: a maturity level is written in a package's version and an API's name. It holds:
  - the four levels, each defined by the least we do for a package at it (see "Decisions made in this project" for the points the working definitions left open);
  - one release number, the suffix, and each package's own patch number or counter;
  - how a level is written on an API, a command-line flag and a config option, and what happens to the name when the API reaches GA (the design's section 5);
  - no feature flags;
  - how the levels relate to the support categories of prisma/orm#25843: that scale says where the maintainers spend effort on each database, and a level says how finished a package is. Neither decides the other.
  - Notes on the record on extension compatibility (ADR 017, whose version matrix was never built) and on SQL lowering (ADR 016, no feature flags).
- **Docs.**
  - `docs/oss/versioning.md` rewritten for the release number and levels.
  - The glossary gains the levels, "facade" and "platform package".
  - Every maturity label in the repository becomes one of the four levels: "experimental" (ParadeDB and Supabase in `README.md`), "first-class" and "proof of concept" (`README.md`, the skill's migrations reference), "support is early" (six MySQL and MariaDB files), "release candidate" as a label for one package (Better Auth).
  - For extension authors, in the `prisma-8` skill and the extension docs: how to number a package maintained outside this repository and what range to declare (the design's section 1.2), and that a package using an API below GA declares a range within one minor.
  - The capability docs say a capability has the level of the package that publishes it.
- **Five corrections that are true today** ride along: the capability stability scheme that was never built comes out of the Ecosystem subsystem doc and `docs/reference/capabilities.md`; the note on ADR 017; "early-access install" in `docs/oss/versioning.md`; the pin bullet that names an unpublished package; "prototype" in the decision record index and `AGENTS.md`.

### 3. Cutting release `8.0` as `8.0.1`, one package alone, and an older major

**After this slice:** a maintainer can cut release `8.0`, published as `8.0.1`, release a fix to one package, and release a fix to an older major, each with one command and a dry run that shows what will be published.

**Two pull requests, in this order.**

1. **Small corrections to the upgrade flow and the release policy.** In review. It fixes a rule in the application flow that let an install jump past a step, and states the policy on fixes.
2. **Cutting `8.0.1`:** the command that leaves the release candidates, the list of old release candidates to deprecate, the written procedure, and how long a major receives fixes.
**Not built: a fix to one package, and a release of an older major.** Decided by the operator on 2026-11-27: the team works on the expectation that anything on `main` can be released at any time, so a fix ships in the next release, cut early when it cannot wait. A fix to one package would need a branch per minor, because a fix published from `main` carries whatever else has merged; that machinery is revisited only if the expectation about `main` changes. The bullets below that describe a fix to one package, a release of an older major, their dry runs, and a correction shipped as a fix release are therefore not built. Two small parts of them move to the second pull request: `check-upgrade-coverage.mjs` stops requiring a guide for every release after `8.0.1`, and the skills say that such a step may have no guide.

What the first pull request found, which changes the bullets below:

- **Nothing is built for a guide corrected after its release.** Decided by the operator on 2026-11-27: `prisma skills sync` is the only thing that moves skill files into a project, and the problem is not worth a mechanism or a process. The answer is to write the guides correctly. The bullets below about where the guides are read from, reading before installing, projects that cannot install the releases in between, and the test with two packed releases are therefore not built.
- **The procedure for `8.0.1` goes in `docs/oss/releasing.md`,** not `versioning.md`: slice 2 moved the maintainers' procedures there.
- **How long a major receives fixes is a section of ADR 330,** not a new record: the draft's number was taken by the record on peers.
- **Where ParadeDB's removal comes in the order of release `8.0`** is settled in the second pull request: the design says to remove it before GA, and the levels file still publishes it.

- **Cutting `8.0.1`** and any later minor or major, from the release skill. The repository's version, the git tag and the GitHub release are `8.0.1`; no package is published as `8.0.0`.
- **Packages that move down from `rc`** (the design's section 2.1): at `8.0.1` each is published at its level, and every earlier release candidate of it is marked deprecated on the registry with a message that says where the package went. The trial showed that Yarn and Bun do not print that message, so the release notes and the upgrade instructions say it too.
- **A fix to one package:** its patch number or counter rises, it alone is published, and the release notes say which package.
- **A release of an older major always names its own tag,** so it cannot take `latest` back.
- **Upgrade skills.** From release `8.0`, the `prisma-8` skill says an upgrade within Prisma 8 needs no change, keeps the per-release instructions for the release candidates only, and says how a user of a package below GA moves to the next minor, including what their lines should read after their package manager has rewritten them. `check-upgrade-coverage.mjs` stops requiring a guide for every release after `8.0.1`.
- **A corrected upgrade guide reaches the user** ([TML-3942](https://linear.app/prisma-company/issue/TML-3942)), in the same pull request as the upgrade skills, because both rewrite `upgrade-app.md` and `upgrade-extension.md`. Today the flow installs each step and then reads that step's guide from the package it just installed (`upgrade-app.md`, steps 2 and 3). A published package never changes, so a guide corrected after its release is never read: after `8.0.0-rc.25` shipped, its guide gained an entry on the `arktype` and `bson` ranges that no one following the flow will see. Step 0 claims the opposite.
  - **Where the guides are read from.** Every step's guide comes from the newest published release of the major, not from the release the project installs. The skill ships only in the five database packages (`SKILL_ANCHOR_PACKAGES` in `scripts/sync-package-skills.ts`), each of which carries every step's guide, so the flow fetches the app's own database package at that release without installing it and reads the guides from it. The newest published release, not the newest the project can install: a project whose other pins hold it back, such as a Composer version that requires one exact ORM release, still reads the corrected text.
  - **Read before installing.** A step's guide is read before the step's install, so a guide that says to change `package.json` first can be followed.
  - **Pinned toolchains.** When the project's pins do not allow the releases in between, the flow raises the packages once to the target, then applies each step's guide in order, with a typecheck and a commit after each, without installing again.
  - **A correction that cannot wait for the next release** ships as a fix release of the newest release: the five database packages at their next patch or counter (`8.3.0` to `8.3.1`, `8.3.0-ea.0` to `8.3.0-ea.1`), through the fix to one package this slice builds, widened to the packages that carry the skill. An older release is never republished, because the flow no longer reads from it. Before release `8.0` there is no fix to one package, since the release candidates move together, so there the next release candidate carries the correction.
  - **Done when** an agent upgrading across two releases reads the corrected text of the older step's guide, shown by a test that serves two packed releases and checks which text the flow reads, or by a recorded run.
- **The procedure for releasing `8.0.1`** in `docs/oss/versioning.md`, with the list of docs to rewrite on that day, the removal of the ParadeDB extension from the repository, and the levels at release `8.0`, where no package is Preview. A package promoted to Preview later needs, in its reference documentation, the list of what it does not yet support, which the level's definition requires. A draft exists on the branch `docs/compatibility-policy-records`.
- **How long a major receives fixes:** fixes go to the latest minor; the previous major receives critical and security fixes for 12 months after a new major. Recorded in a decision record, from the draft on the same branch, and stated in `SECURITY.md` and `docs/oss/versioning.md`. Prisma 7 keeps the 18 months already promised for it; the 12 months apply from Prisma 8 on.
- **The check.** Dry runs, in CI, of: `8.0.1`; a fix to one GA package; a fix to one package below GA; a release on an older major.

### 4. The public docs

**After this slice:** the Prisma 8 docs on prisma.io say what this project changes for a user. It is a pull request in prisma/web, written from the decision records of slices 1 and 2. It has two parts, published at different times.

**What an application installs,** published with the release that ships slice 1. From that release an application lists the platform packages beside the package for its database, because the package for its database names them as peers and Yarn installs no peers. Every page that tells a user what to install changes: the install column of the supported-databases page (today `npm install @prisma/orm-postgres pg`), each quickstart, each extension's page, and the upgrade guide from Prisma 7. Each says that `prisma orm init` writes these lines, and shows them for a user who adds a database to an existing application. The pages for extension authors say an extension names the platform packages as peers and not the package for a database.

**The levels,** published with release `8.0`:

- A page that defines the four levels and says how to read one from a version and from an API's name.
- Every page that introduces a database or an extension says its level. At release `8.0`: PostgreSQL and its packages, pgvector, PostGIS, citext, arktype JSON, the cache middleware and Better Auth are GA; MongoDB, Supabase, MySQL, MariaDB and SQLite are Early Access. No package is Preview.
- The five undefined labels used there today are gone. MongoDB keeps "Early access"; MySQL and MariaDB ("Early preview") and SQLite ("Experimental") become Early Access; PostgreSQL ("Release candidate") becomes GA.
- A short section says what a user of a package below GA does at each new minor: write a tilde on every `@prisma/orm-*` line and edit the lines by hand, because a package manager's update command rewrites them. It also says that a monorepo keeps its applications on one minor unless its package manager keeps each workspace's packages apart.
- The release-status page states how long a major receives fixes.
- The ParadeDB extension's page, if there is one, says its team now maintains it outside this repository.

**The check:** each page's install lines are run against packages packed from the release, under npm, pnpm, Yarn and Bun, before the pull request is merged.

## Proposed split: the command-line tool's rules as their own project

The design's section 4 is the size of a project and is better run as one:

- **In prisma/orm:** the tool compares the major and minor of the toolchain it carries with the library installed in the project and stops when they differ. What crosses from the project's config file into the tool is accepted by its shape. Today some values are recognised by which copy of the framework made them: a literal default value carries a private field, and a release candidate once failed on exactly this. The docs currently tell users the tool and the application must share one copy. Finding every such value and changing how it is recognised is an investigation of its own.
- **In prisma/prisma-cli:** the `prisma` package keeps its own version numbers; it brings together several tools. When it runs an ORM command it compares the toolchain it carries with the ORM packages installed in the project, and stops when they are on different minors. Still to design there: what a user does when an update of `prisma` brings a toolchain from a newer ORM release than their application can move to. It reports newer versions within the ranges the user has written.
- **`init`'s `prisma` line.** `init` leaves the `prisma` line as the package manager writes it. `prisma` keeps its own version numbers (decided by the operator on 2026-11-27), so no range on it can follow the ORM's release.

It is required for GA. Once packages have their own patch numbers, the tool and the library will often be different copies. It builds on slice 2 of this project.

## Decisions made in this project

The design left these to the project. Each is recorded in the pull request of the slice that builds it.

| Point | Decision | Why |
| --- | --- | --- |
| How the platform packages name each other | As peers | The trial: as ordinary dependencies they gave two copies under Bun and Yarn |
| How an application on a facade below GA writes its lines | A tilde on every line | The trial: the only form that stayed consistent under every package manager |
| Who writes the ranges in a new application | `prisma orm init`, explicitly | The trial: pnpm writes an exact version for a pre-release, and Yarn installs no peers |
| Ranges before release `8.0` | Exact, as today | A release candidate may break, so a range between release candidates would promise something false |
| The first version of every package at release `8.0` | Patch 1 at every level: `8.0.1`, `8.0.1-rc.0`, `8.0.1-preview.0`, `8.0.1-ea.0`, with the repository, git tag and GitHub release at `8.0.1`. Decided by the operator on 2026-11-25; every later release starts at patch 0 | The third trial: `8.0.0-ea.0` sorts below the old `8.0.0-rc.N`, and a range on it installed an old release candidate under Bun always, Yarn unless deprecated, and npm and pnpm once `latest` moved on. Patch 1 for every level, not only below Release Candidate, is one rule for the release in place of three |
| Which package carries a database's level | Both the facade and the target package, at the same level | A GA package depends only on GA packages, so a facade cannot be above its target |
| The framework's level | GA, with the PostgreSQL facade | It is what the PostgreSQL facade depends on |
| Which release a failing test blocks | While our packages are released together, a failing test of a GA, Release Candidate or Preview package blocks the release of all of them. Early Access is the one level at which we may release with a failing test; CI does not have to allow it | A level is the least we do. Today every test blocks, which meets every level |
| Who decides what a Preview package supports | The maintainers, in the list its reference documentation carries | The working definition already requires that list |
| Release Candidate for a single API | `rc_foo`, by the same rule as `preview_foo`. Decided by the operator on 2026-11-26 | One scale and one way of writing it |
| A level in names other than lower-case function and property names | A type is `Preview_Foo`, a PSL attribute `@preview_foo`; a command-line flag and an error code carry none. Decided by the operator on 2026-11-26. An environment variable carries none either, for the same reason as a flag, and a PSL default function follows the lower-case rule; both decided in this project | A flag belongs to its command and an error code to the function that throws it |
| A GA package going below GA | Never within a major; allowed at a new major. Decided by the operator on 2026-11-26 | Within the major it would break what GA promises |
| Maturity levels and the First-Class, Supported and Unofficial scale | Independent. Decided by the operator on 2026-11-26 | One says where effort goes, the other how finished a package is |
| The Supabase extension's dependency on the PostgreSQL facade | Becomes a peer, named as an exception | See the spec's non-goals |
| Where the upgrade flow reads each step's guide | From the newest published release of the major, before installing the step; a correction that cannot wait ships as a fix release of the newest release, never of an older one | A published package never changes, so reading from the installed step's package never sees a correction; reading from the newest release makes one fix enough, and a project held back by its pins still gets it |
| Prisma 7's support period | Stays at 18 months after release `8.0` | Already promised in `SECURITY.md` and the record on Prisma 7. The 12 months are the rule from Prisma 8 on |

Two findings of the trial limit what the design promises. Both are told to the operator when slice 1 is handed over:

- **A monorepo with applications on different minors.** Under npm workspaces and Bun's hoisted linker, an extension that both applications use is placed once, beside one application's platform packages, and the other application then has two copies with no warning. No arrangement of ranges changes where a package manager places a package. The docs say to keep the applications of a monorepo on one minor, or to use a package manager that keeps each workspace's packages apart. The run-time check the design's section 6 mentions would turn the silent case into an error.
- **An extension released at a later minor.** Our own extensions are released with every release, so `orm-extension-pgvector@8.5.0` declares `^8.5.0`. An application on `8.4` that updates that extension alone gets a refused install under npm and a warning elsewhere. The user updates the platform packages too.
