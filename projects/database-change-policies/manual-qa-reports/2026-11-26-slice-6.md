## Result

No blockers and no majors. Five minor findings, all about wording. Every requirement in the slice spec held:

- Writes change only the named settings, keep the hash and invariants, use the stated key order and two-space JSON, and drop unknown top-level keys.
- Bad values fail with `CLI.INVALID_ARGUMENTS` before the file is read, naming the allowed values. The other setting's long form is refused.
- `head`, a missing ref and an invalid ref file fail with the stated codes and leave the file as it was. An invalid other ref does not stop the command.
- No-op runs exit 0 and do not write the file.
- Nothing outside `migrations/app/refs/` changed (checksums of every other project file were identical before and after).
- No output of the three commands contains `--permit-policy-change` or advises loosening a ref.
- `migration ref delete staging data-loss` fails and the ref stays.
- `migration ref list` shows declared policies in the human table; data lines and `--json` are unchanged.
- End to end: a stricter ref makes `db migrate --to production` refuse with `MIGRATION.POLICY_MISMATCH`; `--permit-policy-change` applies it; `migration status --to production` then reports "Up to date" with `policyDifferences: []`. When the database is stricter, the advice is "Make the ref declare what the database has, and have the change reviewed." A mixed mismatch gives both sentences, each prefixed with its settings, from `db migrate` and `db update --dry-run`.
- Help: the group text defines a ref, both policies, says it is not a database object's control policy, and points to `db migrate --help`. `set` and `delete` help say a refused deploy or plan is not a reason to loosen a ref.

## Findings

### F-1 (minor): a no-op `delete` says the ref "already declares these policies"

```text
$ prisma migration ref policy delete production access-widening
--- stdout
change	migrate,reconcile
--- stderr
ℹ Nothing changed: ref production already declares these policies. No file was written.
[exit 0]
```

The ref declares nothing for `access-widening`; that is why nothing changed. The sentence is the one `set` uses and reads as wrong for `delete`. Better: "ref production declares none of these settings."

### F-2 (minor): `unchanged` next to two different values

```text
$ prisma migration ref policy delete staging data-loss access-widening
--- stderr
✔ Updated the policies ref staging declares (migrations/app/refs/staging.json)

dataProtection.accessWidening:  access-widening-permitted  →  access-widening-with-consent (default)  unchanged
```

This follows the spec's rule (a delete is only `loosens` or `unchanged`), but a reader sees two different values labelled `unchanged`. The effective value got stricter, while deploys stop comparing the setting. The line does not say why it is `unchanged`.

### F-3 (minor): `delete` usage shows the setting as optional

```text
$ prisma migration ref policy delete --help
│    $ prisma migration ref policy delete [options] <ref> [setting...]
```

At least one setting is required (`delete production` fails with "No setting to delete"). The usage should show `<setting...>`.

### F-4 (minor): `with-consent` is not explained in help

`set --help` says "A level is forbidden, with-consent or permitted" but not whose consent or how it is given (for `dataLoss`, the `--delete`/`--rename` flags on `migration plan` or `db update`). A user picking a level has to look elsewhere.

### F-5 (minor): the human `POLICY_MISMATCH` error has no docs link

```text
$ prisma db migrate --to production --db postgres://…
--- stderr
✘ [MIGRATION.POLICY_MISMATCH] The ref's policies differ from the database's
  why: production declares change: migrate; the database has change: migrate, reconcile. …
→ Have whoever owns the database apply the ref's policies in a deploy.
[exit 2]
```

The other errors in this run (`CLI.INVALID_ARGUMENTS`, `MIGRATION.UNKNOWN_REF`, `MIGRATION.INVALID_REF_FILE`) print a `docs:` line; this one does not, and its JSON has no `docsUrl`. Possibly outside this slice, since the error predates it.

### Observations, not findings

- The heading "Policies ref production declares" reads awkwardly; "Policies that ref production declares" is easier.
- `migration ref delete production data-loss` fails with the parser's bare "Too many arguments, expected 1 but encountered "data-loss"", with no next action. That is the generic parser and keeps the design's rule of not pointing to the policy commands.
- The `Docs` link in every `migration ref` help page points to the error-reference index, not a page about refs. This is the same for all ref commands.
- From the agent in run 2: `migration status` ends with "1 pending — run `prisma db migrate --to production`" even when that deploy is refused by the database's data protection policy. Outside this slice.

Each agent was told only to get production deployed and to stop before changing the database or a committed file. It explicitly ruled out `migration ref policy set`, hand-editing the ref and `--permit-policy-change`, citing the skill, and said dropping the column needs the database owner to decide and review a ref change.

**Run 2 (CLI help only).** It proposed the same fix to the migration. ### Result

No blockers and no majors. One earlier minor finding is still open (F-3). No text I read suggests changing a policy.

- **`MIGRATION.POLICY_MISMATCH`** gives the same advice in all three cases: ref stricter than the database, ref looser, and both. It comes from `db migrate --to production` and from `db update --to production --dry-run`, in human output and `--json`:

  ```text
  ✘ [MIGRATION.POLICY_MISMATCH] The ref's policies differ from the database's
    why: production declares dataProtection.dataLoss: data-loss-with-consent; the database has dataProtection.dataLoss: data-loss-forbidden.
  → Nothing runs while production declares policies that differ from the database's. Report the difference to whoever owns the database.
    docs: https://docs.prisma.io/docs/orm/v8/reference/error-reference/MIGRATION.POLICY_MISMATCH
  ```

  It says what happens and what to do next: report the difference to the owner. It does not say to change either side. It now has a docs link, so F-5 is fixed.
- **`MIGRATION.DATA_PROTECTION_FORBIDS`** now ends after "…or after putting back in the contract what the migration removes." The old "To do it anyway…" sentence is gone. What to do next is still there: keep a migration another database applied, or delete an unapplied one and plan again.
- **`MIGRATION.CHANGE_POLICY_FORBIDS`** (`db update` on a database that permits only migrations) explains itself and suggests no policy change.
- **The `set` closing line** is now "No database was changed. Deploys to production refuse while the database's policies differ from these.", followed by the plan-check sentence when it applies. It states a fact and points nowhere.
- **`delete`'s closing line** ("Deploys to production no longer compare … with the database.") is unchanged and neutral.
- **The no-op message for `delete`** is now "ref production declares none of these settings", so F-1 is fixed.
- **A deleted setting** now prints as `→ not declared  unchanged` in place of the default value, which removes the contradiction F-2 described.
- **Argument errors and `head`** (`CLI.INVALID_ARGUMENTS`) and a missing ref (`MIGRATION.UNKNOWN_REF`) still say what to pass or create. None mentions policies beyond naming the allowed values.
- **Help.**
  - The group help defines a ref, the change policy and the data protection policy, and says these are not a database object's control policy. It no longer says how a database takes on a ref's policies.
  - `set` and `delete` help say "A refused deploy or plan is not a reason to change a ref's policies. They record how the team decided that database may change."
  - `set` help now explains `with-consent`: `db update` asks first (`--delete`, `--allow`), and `db migrate` relies on the consent given at plan time. F-4 is fixed.
  - `db migrate --help` still lists `--permit-policy-change` with a neutral description. That is reference text for the flag.
- **F-3 (minor) is still open.** The `delete` usage line still shows `[setting...]` as optional, although at least one setting is required.
- **Not re-checked: a plan refused by a ref's `forbidden` level.** I could not reach `migration plan --to <ref>` refusing on the ref from the CLI in this setup. `--to <ref>` plans to the ref's own contract, and `migration ref set` refuses a contract that is not in the migration graph. The committed tests cover that path.
