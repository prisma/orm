# System-design review: deploy shows Prisma ORM's own migrate errors

Branch `tml-3726-show-orm-migrate-errors` against `origin/main` (merge base, three-dot diff), four commits from `947ba149` to `94c67b15`. Expectations come from the slice spec `wip-slice-spec.md` (untracked, at the clone root) and Linear TML-3726. Prisma ORM source was read at tag `v8.0.0-rc.24`, the version Composer depends on, and at the ORM's current `origin/main` where noted.

What I read before judging: `AGENTS.md`, `CLAUDE.md` and the architectural principle "a layer does not know what is built on it", `.agents/rules/README.md` and `user-facing-surface-changes.mdc`, `.drive/CODE-REVIEW.md`, `docs/design/README.md`, the ADR index, ADR-0022 (data dependencies carry an ORM contract), ADR-0044 (errors are structured envelopes), ADR-0050 (Composer runs as `prisma deploy` and `prisma dev`), `05-prisma-cloud/build-reporting.md`, the glossary entries for the database owner and markers, the framework CLI's `converge-in-process.ts`, `deployment-summary.ts`, `execute-deploy-destroy.ts`, `execute-dev.ts`, `family/translate-error.ts`, the `@prisma/cli-engine` 0.10.0 renderer (`writeDiagnostic`, `renderNextAction`, `substituteBinName`), and the ORM's `printed-command.ts`, `cli-errors.ts` and `marker-mismatch.ts`.

## Verdict

**Concerns.** The direction is right and fits the recorded design: the ORM is the component that knows why a replay refused and which recovery is safe, and Composer's own text over it (`noPathRefusal`) was wrong in ways ADR-0022's own history shows. Removing it is a real improvement. But the slice passes through advice written for a person who ran `prisma db migrate`, and in Composer the person ran `prisma deploy`. Two of the three example errors tell the user to apply migrations by hand, one of them against the wrong database, while the guide on the same page says to commit and deploy again. The shape also has three smaller structural problems: the ORM's error code reaches no consumer as data, the renderer is a hand copy of the CLI engine's that lives in the target extension, and the error class now labels Composer's own failures "Prisma ORM migrate" and the ORM's failures without it.

No credential leak: `<url>` is a literal placeholder in the ORM at rc.24 (details under question 3).

## What the change does to the system's shape

- Removes a Composer-owned translation of ORM migrate failures (`noPathRefusal`, codes `MIGRATION_PATH_NOT_FOUND` and `RUNNER_FAILED`) and replaces it with a pass-through: the ORM's failure is flattened into `OrmMigrationError.message` in the ORM CLI engine's diagnostic layout.
- Changes what Composer tells the ORM about the caller (`invocation.dbGiven: true`, `invocation.configPath` from the database resource), so the ORM's printed commands carry `--db <url>` and `--config`.
- Substitutes the host binary name (`{bin}` → `prisma`) inside the Prisma Cloud target extension.
- Raises the framework CLI's cap on an engine failure's cause from 1000 to 4000 characters.
- Rewrites one Decision bullet of ADR-0022 in place, and updates two guides and the skill.

## Answers to the orchestrator's questions

### 1. Is flattening the ORM's envelope into the message the right place and shape?

Partly. The message is the only channel today: a converge failure becomes `ConvergeFailureReason { tag, message }` in `failureReasonOf` (`packages/0-framework/3-tooling/cli/src/converge-in-process.ts` lines 155–167), and that pair is all that reaches the terminal summary, `meta.reasons`, `meta.engineCause`, the `--report` file, the platform build's `errorMessage` and `dev`'s rebuild messages. So the advice has to be in the message text for users to see it, and the spec's reasoning on that point holds.

What the flattening loses is the code as data. ADR-0044's reason for codes is that "hosts driving `@prisma/composer/control`, agents, and CI branch on `failure.code` instead of parsing message strings". There is an existing structured path for exactly this: `failureReasonOf` already reports a structured error's `code` as the reason's tag when `CliStructuredError.is(error)` is true, and ADR-0044 says recognition is structural so copies of the foundation interoperate. `OrmMigrationError` is a plain `Error` with `_tag = 'OrmMigrationError'`, so every reason's tag is `OrmMigrationError`, and the ORM's code survives only as `[MIGRATION.MARKER_MISMATCH]` inside the message. The new `code` and `why` fields on `OrmMigrationError` are read by nothing in production code (only by tests). See finding F2.

On duplicating the engine's formatting: yes, it duplicates it, and it already differs. `migrateFailureText` and `nextActionLine` (`orm-migrate.ts` lines 89–121) copy `writeDiagnostic` and `renderNextAction` from `@prisma/cli-engine` (`dist/engine-*.js`, around lines 3134–3164). Differences today: no severity glyph; a `fix` fallback the engine does not have (the engine's diagnostic has no `fix` field, as `family/translate-error.ts` explains); and no handling of a next action's `commands` list, which the ORM's `NextAction` type has and the engine's Markdown renderer prints. The engine does not export its renderer (`index.d.ts` and `protocol.d.ts` export neither), so a copy is the only option inside Composer today. The copy also lives in the wrong layer: see F3.

### 2. Is Composer the right owner of `{bin}` → `prisma`?

The host CLI owns the binary name: `createCli({ name })` sets it, and the engine substitutes `{bin}` in a diagnostic's summary, why and next actions. Composer's own strings already rely on that (`family/family.ts`, `family/commands/dev-url.ts`). The substitution has to happen inside Composer for this text only because the text leaves through channels the engine never sees (report file, platform `errorMessage`, `meta.reasons`, `dev`'s rebuild events). Given that, Composer substituting is necessary, and `prisma` is correct by ADR-0050, which makes the `prisma` CLI Composer's only command line.

The placement is the problem: the knowledge "Composer runs inside the `prisma` host" belongs to the framework CLI (`packages/0-framework/3-tooling/cli`), which is the family that the host mounts and which already rewrites foreign advice into Composer terms in exactly these channels (`withComposerAdvice` in `deployment-summary.ts`, applied in `execute-deploy-destroy.ts` line 682 and `execute-dev.ts` line 273). The Prisma Cloud target extension should not need to know what binary mounts it. See F3.

### 3. Is advice to run ORM commands against a deployed database consistent with ADR-0022? What does `<url>` render as?

`<url>` renders as the literal text `<url>`. At rc.24, `cliCommand` in `packages/1-framework/3-tooling/cli/src/utils/printed-command.ts` appends `['--db', '<url>']` when `invocation.dbGiven` is true, and its doc comment says "The URL stays a placeholder because it can hold credentials." `dbGiven` is a boolean; Composer never passes the connection string into the invocation. The connection string goes only to `createPostgresControlClient`. The integration tests assert whole advice lines containing `--db <url>` (`orm-migrate.integration.test.ts` lines 252–253, 278–279, 301–302, 338). None asserts that the full message never contains the real connection string; the principal-engineer pass may want that test, since an ORM `why` can carry driver text.

On consistency with ADR-0022, the answer differs by error:

- `MIGRATION.MARKER_MISMATCH`: consistent. The ORM's advice already says "Unless this database changes only through migrations, as production does, move it with db update" and its other branch ends "and deploy again" (`marker-mismatch.ts`, `applicationAdvice`). That reads correctly for a Composer user, and in `dev` the `db update --db <url>` branch is the right local step.
- `MIGRATION.PATH_UNREACHABLE`: inconsistent. At rc.24 the advice is "Apply it: `{bin} db migrate --to <hash>`" with no `--db` and no `--config`, because `planThenApply` in `cli-errors.ts` builds literal strings and ignores the invocation. Run as printed, it migrates the database `prisma.config.ts` names (in the examples, `postgres://localhost:5432/placeholder`), the wrong-database case the spec gives as the reason for `dbGiven: true`. ADR-0022 and the guide say a planned migration reaches a deployed database by committing it and deploying again. The guide shows both on one page: its example block prints `→ Apply it: prisma db migrate --to <hash>` (`docs/guides/building-an-app.md` line 225) and three lines later says "To apply a migration you planned, commit it and deploy again" (line 228).
- `MIGRATION.EXECUTION_FAILED`: inconsistent in the same way. "re-run `prisma db migrate --db <url>`" applies migrations to a deployed database outside the deploy, which skips the deploy's ordering (ADR-0022, amended 2026-10-02: services that use a database deploy only after its migration) and the build record. For Composer the re-run is `prisma deploy`.

The ORM's `origin/main` already passes the invocation into `planThenApply` (so the apply step will gain `--db <url>` and `--config` on the next ORM upgrade), but the apply step is still `db migrate`. The root cause is in the ORM's contract with its callers: `CliInvocation` describes a person typing an ORM command, and has no way for a caller to say "migrations reach this database by `prisma deploy`". Composer is filling the fields of that description (`dbGiven: true` means "the user typed `--db`") to steer the output, which works only because the ORM reads `dbGiven` for nothing else. See F1.

There is also no documented way for a Composer user to get a deployed database's connection string: `docs/guides/deploying.md` lines 259–263 say a database's connection string is deliberately never printed. The guide and skill tell the user to "supply the deployed database's connection string" without saying where it comes from. For `dev`, `prisma dev url <address>` gives it. See F1.

### 4. Does raising the cause cap from 1000 to 4000 belong here, and what else does it protect?

It belongs here. The commit message gives the original reason for 1000: a log tail the Alchemy child process used to write. ADR-0066 and ADR-0068 removed that child, so the limit's reason is gone, and without the change the slice's outcome (advice visible) fails for the path and schema errors. What the cap still protects: the length of the terminal summary of `DEPLOY.ENGINE_FAILED`, and `meta.engineCause`, the report file's failure cause. The platform's 5000-character `errorMessage` is protected separately, by `truncate(outcome.message, 5000)` in `finishReporters` (`execute-deploy-destroy.ts` line 294), so "fits the platform's errorMessage" is not what keeps the platform safe. `dev` is not capped at all. Two design notes in F5: the doc comment in a framework file names one consumer (Prisma ORM), and the cap cuts the joined text of all reasons from the end, so when several resources fail, the ORM's advice can still be cut.

### 5. Naming and vocabulary

See F4 and F6. The docs and skill use the repo's terms (deploy, environment, `prisma deploy`, migration graph, marker). No coined terms. "Recovery commands" and "advice" are plain words, used consistently.

## Findings

### F1. The ORM's advice tells a Composer user to apply migrations by hand, and once against the wrong database

- **Location:** `packages/1-prisma-cloud/1-extensions/target/src/orm-migrate.ts` lines 312–329; `docs/guides/building-an-app.md` lines 219–228; `skills/prisma-composer-core-concepts/SKILL.md` line 364; `docs/design/90-decisions/ADR-0022-data-deps-carry-a-prisma-orm-contract.md` line 70.
- **Issue:** The ORM writes its advice for a person who ran `prisma db migrate`. For `PATH_UNREACHABLE` the apply step at rc.24 is `prisma db migrate --to <hash>` with no `--db`, which runs against the database `prisma.config.ts` names. For `EXECUTION_FAILED` the step is "re-run `prisma db migrate --db <url>`". In Composer, a planned migration reaches a deployed database by `prisma deploy`, which is what ADR-0022 and the guide say. So the error contradicts the guide on the same page, and the ADR-0022 edit ("Prisma ORM's own error, unchanged ... and its recovery commands") records that contradiction as the decision. The guide and skill also tell the user to supply a deployed database's connection string that Composer documents no way to obtain. `dbGiven: true` describes a CLI flag the user never typed; it works only because the ORM reads it for one purpose today.
- **Suggestion:** Keep the pass-through, and fix the owner. The ORM's `CliInvocation` (or the `migrate` options) needs a way for a caller to state how migrations are applied, so that `planThenApply` and the `EXECUTION_FAILED` advice print the caller's apply step (`prisma deploy`, or "commit and deploy again") instead of `db migrate`. The ORM already has the extension point internally (`PathUnreachableAdvice`, "the caller knows better than a plan-then-apply"); it is not exposed through `ControlClient.migrate`. Until that ships in a release Composer depends on, record the gap in the project's `deferred.md` and make the guide and skill say plainly that for a deployed database the apply step is to commit and deploy again, whatever the error's `db migrate` line says, and where the connection string comes from (or that `--db <url>` lines apply to `dev` and to databases the user can reach). Reword the ADR-0022 bullet so it does not claim the ORM's commands are right for a deployed database unchanged.

### F2. The ORM's code reaches no consumer as data

- **Location:** `orm-migrate.ts` lines 126–142; `packages/0-framework/3-tooling/cli/src/converge-in-process.ts` lines 155–167.
- **Issue:** The spec says "the error's `code` is the ORM's code". It is a property on `OrmMigrationError`, but `failureReasonOf` reads only `_tag` and `message` from a non-structured error, so `meta.reasons[].tag` is `OrmMigrationError` for every migration failure. A host, agent or CI that branches on the reason, as ADR-0044 intends, must parse `[MIGRATION.MARKER_MISMATCH]` out of the message. The user also sees the class name `OrmMigrationError:` in front of the ORM's own code, which is a mechanism name on a user surface. ADR-0044 already provides the path: a structurally recognised structured error has its code as the reason's tag.
- **Suggestion:** Make the reason's tag the ORM's code. Either make the error thrown for an ORM failure structurally a `CliStructuredError` (dotted code, `toEnvelope`) so `failureReasonOf` tags it with the code, or have `failureReasonOf` read a `code` it can trust. Then drop the `[CODE]` prefix from the message, since `convergeReasonsText` already prints `tag: message`. ADR-0044's closed namespace list covers Composer's codes; it should say in one line that a reason's tag can be a foreign code (Alchemy tags already are), so an ORM `MIGRATION.*` tag is not read as a new Composer namespace. If this is judged out of scope, remove the unread `code` and `why` fields rather than keep fields that suggest a structured surface nothing reads.

### F3. The diagnostic renderer and the binary name live in the target extension, as a copy of the engine's renderer

- **Location:** `orm-migrate.ts` lines 81–121.
- **Issue:** Rendering a structured error to text in the `prisma` CLI's layout, and knowing the host's binary name, are presentation concerns of the framework CLI, which is the family the `prisma` host mounts, already depends on `@prisma/cli-engine`, and already owns the other transforms on these exact channels (`withComposerAdvice`, `redact`, `capFailureCause`, `convergeReasonsText`, `toEngineError`, and `withHelp` in `execute-dev.ts` line 207). Composer now has three different text renderings of a structured error: `withHelp` (summary, why, fix), `toEngineError` then the engine, and `migrateFailureText`. The copy already differs from the engine (F1 question 1 notes: no glyph, a `fix` fallback, no `commands` list), and nothing will tell anyone when the engine's layout changes.
- **Suggestion:** Move the rendering to the framework CLI, applied where converge reasons become text, as a rendering of any structured error an extension throws (never as ORM-specific code: the principle "a layer does not know what is built on it" forbids the framework holding anything that exists for the Prisma Cloud target), and have the target extension throw the structured failure (which F2 also wants). Ask the `@prisma/cli-engine` owners to export the plain-text diagnostic renderer and the `{bin}` substitution, so Composer calls the engine's code instead of copying it; record that request in `deferred.md` if it does not land with this slice. If the copy stays for now, a test that renders one diagnostic through both the engine (via `@prisma/cli-engine/testing`) and Composer's copy and compares them would make drift fail loudly.

### F4. `OrmMigrationError` now labels Composer's failures "Prisma ORM migrate" and the ORM's failures without it, and one field holds two code vocabularies

- **Location:** `orm-migrate.ts` lines 66–79 and 126–142; raise sites at lines 157 and 186 and `orm-migration-resource.ts` lines 110 and 118.
- **Issue:** The string-code constructor still writes `Prisma ORM migrate (CONTRACT_IDENTITY_MISMATCH): ...` for failures Composer finds before the ORM runs, while the ORM's own failures now start `[MIGRATION.…]`. Read cold, the label now marks exactly the failures the ORM did not raise. The class has two construction modes with two message layouts, and `code` is typed as a union of Composer's underscore codes (`CONTRACT_INVALID`, not dotted as ADR-0044 requires) and the ORM's dotted codes. The type `OrmMigrationFailureCode` is now documented as "a failure Composer finds before Prisma ORM runs", which its name does not say; next to the new `OrmMigrateFailure` (the ORM's failure) the two names differ by one syllable and mean opposite owners.
- **Suggestion:** Split by owner. Composer's own pre-migration checks become structured errors with dotted codes in an ADR-0044 namespace (they are deploy-time failures Composer finds; `DEPLOY` is the obvious owner, which is an edit to ADR-0044's registry), with no "Prisma ORM migrate" label. The ORM's failure is passed through as F2 describes. If the split is out of scope for this slice, at least rename `OrmMigrationFailureCode` to say what it is (for example `ContractCheckFailureCode`) and drop the "Prisma ORM migrate" prefix from its message, and record the dotted-code move in `deferred.md`.

### F5. The cause cap's comment names one consumer, and the cap can still cut the ORM's advice

- **Location:** `packages/0-framework/3-tooling/cli/src/deployment-summary.ts` lines 30–31 and 63–67.
- **Issue:** The framework CLI's comment justifies a generic limit by one target extension's error ("such as Prisma ORM's next actions"). The architectural principle "a layer does not know what is built on it" says a lower layer holds nothing that exists for a concept a higher layer owns; Prisma ORM migrations belong to the Prisma Cloud target, so the framework should not name them, even in a comment; the limit's real job is to bound the terminal summary and `meta.engineCause`, since the platform's 5000-character limit is enforced separately at `execute-deploy-destroy.ts` line 294. The cap is applied to all reasons joined, from the end, so when another resource's failure comes first, the ORM's advice is cut regardless.
- **Suggestion:** Say in the comment what the limit bounds (the summary and the report's failure cause) without naming a consumer. If keeping every reason's advice matters, cap each reason separately rather than the joined text; otherwise state that only the first 4000 characters of all reasons survive.

### F6. ADR-0022 is edited in place without an amendment note, and its index entry is now stale

- **Location:** `docs/design/90-decisions/ADR-0022-data-deps-carry-a-prisma-orm-contract.md` line 70; `docs/design/90-decisions/README.md` line 46.
- **Issue:** The design docs treat ADRs as append-only (`docs/design/99-process/README.md` line 11), and amendments are recorded as dated notes and in the index (ADR-0022 itself has "Amended 2026-10-02"). This slice rewrites a Decision bullet in place: the earlier decision ("a structured refusal naming the two exits") disappears with no note, and the index entry still says "a missing authored path is a refusal naming the fix (`prisma db update` locally, `contract emit` + `migration plan` to ship)". The new bullet also carries history ("text Composer wrote over it ... once told users to run `prisma db update` against any database"), which belongs in a reasoning note, not in the decision.
- **Suggestion:** Restore the bullet and add a dated amendment note ("Amended 2026-11-20: a failed `migrate` fails the deploy with Prisma ORM's own error ...") with the reason, worded to match the outcome of F1. Update the index entry's amendment list.

## Test strategy at the architectural level

The property this slice must prove is: a failed ORM migrate reaches every consumer (terminal, `meta.reasons`, report file, platform `errorMessage`, `dev` rebuild message) with the ORM's code and advice intact, `{bin}` replaced, and no connection string. Today the renderer is unit-tested (`orm-migrate-failure.test.ts`), the real ORM output is tested at the extension (`orm-migrate.integration.test.ts`), and the cap is tested with a fake reason (`operations.test.ts` lines 719–748). Nothing joins them: no test drives a real `OrmMigrationError` through `failureReasonOf` and the deploy operation's failure. A test at the framework CLI that throws a real `OrmMigrationError` from a fake converge and asserts on `meta.reasons`, `meta.engineCause` and the reporter's `errorMessage` would prove the property end to end, and would also pin F2's tag once it changes.

## Out of scope for this lens

- Whether an ORM `why` (for example a driver error text in `EXECUTION_FAILED`) can carry a connection string, and whether redaction catches it: principal-engineer pass.
- Readability of the skill's "`prisma db update` only for a database that does not change only through migrations" (a double negative) and of the guide's long paragraph at `building-an-app.md` line 228: a devrel concern; flagged for the code-review pass's wording check.
- Exact-line assertions in the integration test will change on the next ORM upgrade, since the ORM's `origin/main` already adds `--db <url>` and `--config` to the path advice: principal-engineer pass.
