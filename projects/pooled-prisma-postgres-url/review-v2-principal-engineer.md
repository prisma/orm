# Principal engineer review of design v2: stop forcing `lc_monetary=C`

Verdict: **sound with changes.** Removing `lc_monetary` from the target's session settings is the right fix for the pooled URL, and every runtime read of `money` refuses loudly on a locale it cannot read. But the design understates the silent cases on locales without two fraction digits, misses a new failure in migrations, and proposes error advice that does not work in two common setups. All code references are to the base commit `234d27acb2`. All experiments ran against a throwaway local `postgres:17` (Debian, glibc 2.36) container with locales generated by `localedef`, and one `postgres:17-alpine` container; both are removed. Scripts and output are in `probe/` next to this file.

## Findings, most important first

### 1. On locales with zero or three fraction digits, writes and filters are silently wrong, and following our own error's fix makes the wrong rows look correct

What the design says (sections 3 and 7.1): reads fail loudly; "a `money` write there can be stored scaled or rounded by that locale before the first read fails".

What is missing: three things.

- **Filters, not just writes.** Every `money` parameter is rendered `$1::numeric::money` (`packages/3-targets/postgres/2-adapter/src/core/sql-renderer.ts:112-114` and `:155-157`), including in `where`, `update ... where`, `delete ... where`, `count`, cursors and increments. Under `ja_JP` a filter value of `1234.56` becomes 1235 stored units, so it matches nothing that was written in cents, and matches the wrong rows among values written under `ja_JP`. A `count`, `updateMany` or `deleteMany` with a `money` filter reads no `money` value back, so nothing ever refuses. Measured: rows written in cents, filtered under `ja_JP` and `ar_KW` with a `numeric`-cast parameter, matched 0 of 1 expected row (`probe/binary-money.out`).
- **Our fix advice turns the corruption permanent.** Measured: `1234.56` written under `ja_JP` is stored as 1235 units; read back under `C` or `en_US` it prints `$12.35`, which the codec accepts. `0.07` reads back as `$0.00`. Under `ar_KW` (three fraction digits) `1234.56` reads back as `$12,345.60` (`probe/locale-money-2.out`, `probe/locale-table.out`). So the user who sees `RUNTIME.LC_MONETARY_NOT_C` and runs the `ALTER ROLE ... SET lc_monetary = 'C'` the error tells them to run gets every row written since the upgrade read back 100 times too small (or 10 times too large), with no error, and no way to tell those rows from correct ones afterwards.
- **The upgrade mixes units in one column.** Before this change, every Prisma write ran under the forced `C`, so existing rows are in cents. After it, new writes on a `ja_JP` database are in yen units. A `create()` commits its row before its `RETURNING` read refuses (`errors.ts:160` says so already), so at least one wrong row lands per create, and any write that returns no `money` value lands silently.

Within a single session, there is no locale where a wrong write is read back and accepted: I scanned all 350 glibc locales that `SET lc_monetary` accepts, writing seven values each (`probe/all-locales.out`). The codec never accepted a value different from the one sent. The silent case always needs two sessions with different `lc_monetary`: the fix, an upgrade, two roles with different settings, or a per-transaction pooler carrying another client's `SET` (finding 4). 39 of the 350 locales scale writes, among them `ja_JP`, `ko_KR`, `vi_VN`, `is_IS`, `fa_IR`, `sq_AL`, `sr_RS@latin` and 17 Arabic locales.

There is a concrete way to close writes and filters entirely, with no per-connection cost and nothing for the user to configure: **send `money` parameters in binary.** `money`'s binary input reads the stored 64-bit count of cents directly and ignores `lc_monetary`. `pg` sends any `Buffer` parameter in binary format (`node_modules/.pnpm/pg-protocol@1.15.0/node_modules/pg-protocol/dist/serializer.js:72-78`), and the serverless client and the control driver both use `pg` clients over TCP (`9-facade/src/runtime/postgres-serverless.ts:210-211`, `3-driver/src/exports/control.ts:72-77`). Measured: an 8-byte big-endian count of cents bound as `$1::money` stored exactly `$1,234.56` under `C`, `de_DE`, `ja_JP` and `ar_KW`, and a filter with it matched every row under every locale (`probe/binary-money.out`). This also shows that the data-types record's sentence "PostgreSQL has no conversion to `money` that ignores the setting" is wrong: the binary input is one. The cost is real but bounded: the codec's wire value becomes bytes, `money[]` parameters need the binary array format or keep the `numeric` cast, and `POSTGRES_PARAMETER_READ_AS` loses its one entry. It is not "cheap" enough to fold into this change.

What I would do:

- In this change: make the error and the upgrade note say plainly that on a locale with no or three fraction digits, values written since the upgrade are stored in that locale's units, and that changing `lc_monetary` afterwards makes them read back as wrong amounts without an error. The codec can tell this case from the text it refused: a form with no two-digit fraction (`￥1,235`, `1.235 kr`) or a three-digit one (`1,234.560`). It can say so in the error at no runtime cost.
- Correct the data-types record's sentence about there being no locale-free conversion when it is amended.
- Record binary `money` parameters as follow-up work. This needs Will's explicit acceptance, because he accepted "writes can be stored scaled", not wrong filters and a fix step that hides the damage.

### 2. Migrations with a `money` default now fail on every database whose locale does not print the `C` form, and introspection does not pin `lc_monetary`

The design does not mention this path. Section 7.3 lists "the control plane reading `money` defaults" as unchecked.

The DDL renderer writes a literal `money` default as quoted text cast to the column type: `pgInlineLiteral` (`2-adapter/src/core/control-adapter.ts:1847-1863`) calls `inlineLiteral` (`1-target/src/core/sql-utils.ts:166-173`), and a string value for a non-text type gets `::money` (`sql-utils.ts:135-139`). So `@default(12.34)` becomes `DEFAULT '12.34'::money`, which PostgreSQL parses with `money`'s text input, under the session's `lc_monetary`, and folds into a constant at `CREATE` time. Today the control driver forces `C` (it gets the target's settings through `control-stack.ts:712-720` and `3-driver/src/exports/control.ts:72-77`), so this is exact. After the change, measured (`probe/locale-money-2.out`):

| Locale at `CREATE TABLE` | `DEFAULT '12.34'::money` stores | `DEFAULT '1234.56'::money` stores |
| --- | --- | --- |
| `de_DE` | `$1,234.00` | `$123,456.00` |
| `ja_JP` | `$0.12` | |
| `en_GB` | `$12.34` | |

This does not corrupt data, because the runner verifies the schema inside its own transaction and rolls back (`1-target/src/core/migrations/runner.ts:216-232`, `:279-296`). Introspection reads the default with `pg_get_expr`, which prints it in the session's locale (`'1.234,00 €'::money`), the codec refuses it (`2-sql-family/9-family/src/core/reported-defaults.ts:34-50`), and the diff treats an unreadable default as different (`2-sql-family/1-core/schema-ir/src/ir/sql-column-default-ir.ts:150`). But `db init`, `db update` and `migration apply` of any contract with a `money` default now fail with `MIGRATION.SCHEMA_VERIFY_FAILED` on a `de_DE`, `fr_FR`, `en_GB`, `ja_JP` or similar database, where they work today. And `contract infer` on such a database silently prints the raw locale expression as the default instead of the number (`1-target/src/core/psl-infer/infer-read-defaults.ts:92-96`).

Introspection already pins the settings that shape printed defaults, by statement, and restores them afterwards: `TimeZone`, `DateStyle`, `IntervalStyle`, `bytea_output` (`control-adapter.ts:1771-1811`, `:1825-1844`). `lc_monetary` is not among them because the forced setting covered it.

What I would do: two small control-plane changes, adopted together or not at all.

- Add `lc_monetary: 'C'` to `INTROSPECTION_OUTPUT_SETTINGS`. This uses the existing mechanism and makes `db verify`, `migration plan` and `contract infer` read `money` defaults the same on every server.
- Run `SET LOCAL lc_monetary = 'C'` right after the runner's `BEGIN` (`runner.ts:938-941`). This makes the folded default exact under every locale, including `ja_JP`. It is local to the migration transaction, so it does not leak, and the probe showed `SET LOCAL` works and stays in its transaction through the pooled address (`probe/probe2.out`, "SET LOCAL in tx").

Why both: with only the introspection pin, a `de_DE` migration would still store `1234.00` and fail verification, now with the message "default differs: 1234.00 vs 12.34", which names no locale and is worse than today's text. Cost: one statement per migration run, and one more `set_config` call inside the statements introspection already sends. Both are in the control plane only. This is not the "settings by statement on every connection" that Will rejected, but it is close enough that the design should name it and say why it differs. A cheaper alternative for the DDL half is to write `money` defaults as bare numerals (`DEFAULT 12.34`, as Prisma 7 did; `contract-prisma7/test/fixtures/native-type-defaults/migration.sql`). The codec already reads that form (`codecs.ts:1201-1203`), and the catalog prints it as `12.34` under every locale. But the default is then applied at insert time with the inserting session's scaling, so it is wrong under `ja_JP` like any runtime write.

### 3. Section 7.2 settled: `en_US.UTF-8` prints exactly the `C` form; the Prisma Postgres measurement shows a musl C library, not missing locales

Settled by experiment on glibc 2.36 (`probe/locale-money.out`, `probe/locale-table.out`):

| `lc_monetary` | `1234.5` | `-1234.5` | `0` | `0.07` | upper bound | Codec reads it |
| --- | --- | --- | --- | --- | --- | --- |
| `C`, `POSIX`, `C.UTF-8`, `en_US.UTF-8` | `$1,234.50` | `-$1,234.50` | `$0.00` | `$0.07` | `$92,233,720,368,547,758.07` | yes, exactly |
| `en_GB.UTF-8` | `£1,234.50` | `-£1,234.50` | `£0.00` | `£0.07` | | refused |
| `de_DE.UTF-8` | `1.234,50 €` | `-1.234,50 €` | `0,00 €` | `0,07 €` | | refused, writes exact |
| `ja_JP.UTF-8` | `￥1,235` | `￥-1,235` | `￥0` | `￥0` | | refused, writes scaled |

Across all glibc locales, 17 print the `C` form for every value: `C`, `POSIX`, `C.utf8`, `en_US`, `en_AU`, `en_CA`, `en_NZ`, `es_US`, `en_AG`, `en_ZW`, `chr_US`, `ik_CA`, `iu_CA`, `mi_NZ`, `niu_NU`, `niu_NZ`, `shs_CA`. Three (`en_SG`, `zh_SG`, `unm_US`) print positives in the `C` form and negatives as `($1,234.56)`, so positives read and negatives refuse.

Section 7.2 explains the Prisma Postgres result (every locale name printed the `C` form) as "those locales are not installed there". That is not what happens on glibc: `SET lc_monetary` to a locale that is not installed fails with "invalid value for parameter". On musl, the C library of Alpine images, `setlocale` accepts any name and the monetary data stays `C`. Measured on `postgres:17-alpine`: `SET lc_monetary = 'xx_YY.UTF-8'` succeeded and printed `$1,234.56`. So "money works on Prisma Postgres" is an assumption about its C library, not about its locale setting. It holds today. It would break for any role there whose `lc_monetary` is, say, `de_DE` if the service moved to glibc. Write that down as an assumption. The manual check in section 6 ("a `money` round trip" on Prisma Postgres) proves nothing about locales, for the same reason.

### 4. The reworded error's fix is wrong or incomplete in four situations that can now raise it

Section 4.2 proposes the fix "the `ALTER ROLE` or `ALTER DATABASE` statement, or a session `SET` on a direct connection the application owns".

- **A session `SET` does not hold.** The Supabase extension runs `RESET ALL` when it releases a role scope (`3-extensions/supabase/src/runtime/supabase-runtime.ts:163-167`), which drops a session `SET`. A `url` binding creates its own pool, so the application has no connect hook in which to run one. On a direct connection, the working per-connection fix is a startup option in the URL, `?options=-c%20lc_monetary%3DC`. The driver keeps the URL's options and appends its own after them (`3-driver/src/session-settings.ts:47-50`), and a startup option survives `RESET ALL`. Behind the Prisma Postgres pooler that URL is refused, which is the original failure, so the text must say "direct connections only" or leave it out.
- **`ALTER ROLE` and `ALTER DATABASE` reach only new server connections.** Measured: after both, a new direct connection had `C` but the pooled address still served `en_US.utf8` from its existing server connection (`probe/probe2.out`, "pooled after alter"). The fix must say that existing pooled and application connections keep the old value until they are replaced.
- **Another client can cause it through a per-transaction pooler.** The probe set `lc_monetary` on the pooled address and later, unrelated connections saw `de_DE.UTF-8` on the same server process (`probe/probe.out`, `probe/probe2.out` first line). "Do not change `lc_monetary` on a connection Prisma uses" should become "on any connection that shares the pooler with Prisma".
- **On zero- or three-digit locales** the fix must carry the warning in finding 1.

Two existing test assertions constrain the wording: `1-target/test/xml-oid-money.test.ts:167-172` expects `fix` to contain `lc_monetary` and `why` to contain `already committed`.

### 5. The CLI through a per-transaction pooler: introspection outside a transaction sets session settings that do not stay on one server connection

This is newly reachable, because the CLI could not connect through the pooled address before. `readWithDefaultOutputSettings` (`control-adapter.ts:1825-1844`) first tries `set_config(..., true)`. Outside a transaction, that does not outlive its statement, so it falls back to session-level `set_config(..., false)`, runs the reads, and restores the caller's values. Behind a per-transaction pooler, each of those statements can run on a different server connection. The reads can then run without the pinned settings, and the pinned or "restored" values are left on server connections other clients use. The probe saw one server process only because it was the only client. The runner's own verification runs inside its transaction, so `migration apply` is safe. `db verify`, `migration plan` and `contract infer` are not.

What I would do: when introspection is not already inside a transaction, wrap it in `BEGIN ... ROLLBACK` so the pinned settings are always local. That is one round trip per command, and it removes the session-level path. At minimum, make the manual check in section 6 run `db verify` and `migration plan` through the pooled URL with a second client active, not only `db push`, and list this in section 7.5.

CI already starts one compose service because the plain service container could not run a custom command (`.github/workflows/ci.yml:250-255`, `examples/prisma-8-cloudflare-worker/docker-compose.yml`). - **The pooler stand-in.** `startStartupParameterRecorder` (`test/utils/src/startup-parameters.ts:26-75`) already parses the startup message, answers `SSLRequest` with `N`, and exposes a URL. Extend it, or add a sibling, as follows:

- **If finding 2 is adopted:** extend `2-adapter/test/migrations/schema-verify.session-output-settings.integration.test.ts`, which pins the four introspection settings today, and add a runner unit test that `SET LOCAL lc_monetary` follows `BEGIN`.
- The design's unit test "the guard's statement sets one setting" is fine. The codec conformance cases (`4-codec-testkit/test/codec-conformance/cases.ts:507-512`) and the aggregate matrix (`4-codec-testkit/test/aggregate-matrix.ts:199`) pick up the target's settings through `4-codec-testkit/test/runtime-connection.ts:11`. ## Checked and found correct

- The target declares both settings at `descriptor-meta-runtime.ts:26`. The driver sends them as `-c DateStyle=ISO -c lc_monetary=C`, after the URL's options or `PGOPTIONS`, on every pool and client it creates (`3-driver/src/session-settings.ts:25-29`, `:47-50`, `:57-79`). On a supplied pool or client it applies them with one `set_config` statement (`:92-113`). The control stack passes them to the control driver (`framework-components/src/control/control-stack.ts:712-720`, `:766`).
- The probe measurements support every pooler claim in section 1: `lc_monetary` with any value is refused, `DateStyle`-only connects, there is one shared server process, and a statement-level `lc_monetary` leaks to other clients.
- The codec reads only `-?$d,ddd.dd` and bare numerals (`codecs.ts:1189-1211`). Every `money` parameter goes through `numeric`, in every position, including lists (`sql-renderer.ts:150-157`, pinned by `sql-renderer.cast-policy.test.ts:422-446`). `numeric` to `money` is exact under every locale with two fraction digits (all 350 glibc locales checked), and so is `de_DE` despite its separators.
- Within one session, no glibc locale makes the codec accept a wrong value (finding 1). So "reads fail loudly" in section 3 is true as stated.
- The Supabase extension's `RESET ALL` raises no new issue. After the change, it returns `lc_monetary` to the role or database default, which is what every other connection now has (`supabase-runtime.ts:163-167`).
- Section 5's account of what the change reverses in the two decision records is accurate, apart from the sentence about there being no locale-free conversion (finding 1).
- The design does improve one existing silent case. Today, rows that a non-Prisma writer stores in yen units on a `ja_JP` database read back through Prisma under the forced `C` as a hundredth of their value, without an error. After the change, those reads refuse.
