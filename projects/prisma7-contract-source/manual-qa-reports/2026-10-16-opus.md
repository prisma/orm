## Findings

### Q01: `CONTRACT.PRINT_UNSUPPORTED` tells the user to add an extension that is already configured

When a configured extension registers a default function but has no `printArguments` for its generator, `contract print` refuses with the next action "Add the extension that registers the default function to the config". The extension is already in the config. The real fixes are for the pack to declare `printArguments`, or to keep the current contract source. The `why` text is also written as if no function declares the generator, though one lowers to it.

Reproduce:

1. Copy `test/integration/test/authoring/parity/default-pack-slugid/packs.ts` and delete the `printArguments` line.
2. Compose it with `extensions: [...extensions]` in `defineConfig` from `@prisma/orm-postgres/config`, with a Prisma 8 PSL contract containing `id String @id @default(slugid())`.
3. Run `prisma contract emit` (succeeds), then `prisma contract print`.
4. The error is `CONTRACT.PRINT_UNSUPPORTED` with the next action above.

### Q02 (QA script): the section 1 schema is not valid Prisma 7 PSL

`datasource db { provider = "postgresql" }` on one line makes `prisma7 migrate dev` fail with `Argument "provider" is missing in data source block "db"`, ten validation errors in all. Prisma 7 needs each block's fields on their own lines. Fix the script by writing `datasource` and `generator` on several lines.

### Q03 (QA script): no real preset sets its own database default

Section 4 asks for a preset that sets its own database default, written with `@default(...)`. No preset in `packages/3-targets/3-targets/postgres/src/core/authoring.ts` sets `output.default`, and none does outside tests. The script should test the branch a user can reach: a preset with an `onCreate` generator and a generating `@default(...)`, such as `id.uuidv4Native() @default(uuid())` (step 4.6).

## Observations

- `time(0)` with `@updatedAt`: Prisma 8 rounds the clock down to the second, as `date-time-now-generators.ts` documents, so the column never reaches `24:00:00`. Prisma 7 sends milliseconds and PostgreSQL rounds to the nearest second: at the same moment Prisma 7 stored `22:32:43` for `22:32:42.639`, while Prisma 8 stores `22:32:42`. The two can differ by one second. This is a design choice, not a failure of the script's checks.
- The second branch of `PSL_PRESET_AND_DEFAULT_CONFLICT` (4.6) offers two fixes, using a database default or another preset, but not the most common one, removing `@default(...)`. The first branch's message does offer it.
