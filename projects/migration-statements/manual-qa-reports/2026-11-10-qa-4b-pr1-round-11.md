# Manual QA — slice 4b, PR 1, round 11

Date: 2026-11-10. Branch tip `7a03502b31`. Script: `projects/migration-statements/slices/mongo-convert-backfill/manual-qa-pr1.md`. Earlier rounds: `2026-11-06-qa-4b-pr1.md`, `2026-11-10-qa-4b-pr1-final.md`, and rounds 2 to 10 of 2026-11-10.

The design changed before this round: the separate `checkDocuments(...)` early check is gone, and only the validator change checks the documents, as its own precheck. A migration that stops partway leaves earlier operations applied, and a re-run finishes it. I treat that as expected and do not report it as a problem. I do judge whether the messages say truthfully what happened and what to do.

## Problems, ranked

### Data loss

None found.

### A partial apply whose message does not say what it left behind

1. **After a partial apply, the failure no longer names the operations that ran or the state they left.** Partial applies are now expected, so the message is the user's only account of what happened. `p1` (`db update`): `Account.code` loses `@unique`; `User` gains a required `plan String` (filled) and a required `born DateTime` (no temporary value). The index drop and the fill ran, then the users validator change stopped. The why ends with `The operations that ran before the failure stay applied.` It does not say:
   - which operations ran. The unique index `code_1` is gone, so the app can now insert duplicate codes; I inserted one. Round 9's message listed the operations that ran; this one does not.
   - that the filled `users` documents now fail every update. They hold `plan`, which the old validator does not allow; I confirmed "Document failed validation". The cast and data transform failures still carry this warning ("Until it does, a document already cast … so updates to it fail"); the validator failure does not.

   The same holds in `M1` to `M4` and `M7`, `M8`, `M11`, `M12` in `multi.log`. Each re-run after the fix finished the migration and verify was clean, as the new design intends.

### Wrong or misleading advice

2. **The validator failure suggests `--backfill` for a field the plan already filled.** `M1` to `M4`, `p1`: `This validator change makes "born" and "plan" required. … To give "born" and "plan" values you choose, plan the change with migration plan --backfill User.born --backfill User.plan.` The plan had already given `plan` its temporary value `""` in every document, so only `born` is missing. The named document `That document has no "born"` is right; the summary and the `--backfill` advice point at a field that is not the problem.
3. **Adding a required unique field to a collection with documents no longer mentions `--backfill`.** `x9`: with the early check gone, `db update` fails at the index build: `the unique index slug_1 cannot be built, because two documents in collection users hold the same value { slug: null }` and `Give each document its own value of the indexed fields`. That is true and works, but the planned way, `migration plan --backfill User.slug`, is no longer named.

### Unclear text

4. **A failed cast that ran first says "The operations that ran before the failure stay applied"** when nothing ran before it (`x7b`, scenario 2). Harmless.
5. **The Mongo failed-cast advice under `db migrate` says "replace that cast with a conversion of your own there"** (`x7b`). On MongoDB the file holds `castField(...)`; replacing it means writing a `dataTransform`, which nothing explains. The second advice (re-plan with `--convert`) is concrete. Fixing the value and re-running, which also works, is not mentioned.
6. **A value that fails an enum gets no "That document …" reason.** `w1`: `status: "gone"` failed the new enum; the why says `This validator change changes what "status" accepts. It has _id …` and stops there.
7. **The W1 warning has no `⚠` under `db update`** (`s8`), while `migration plan` prints it with `⚠`. The text itself is good (see below).
8. **"This change is not a statement"** in the W1 warning uses the project's term "statement" without explaining it. A user who has only seen `--rename`/`--delete` may not connect the two.

## Messages that changed, judged

- **Type change question** (Mongo `q1`, Postgres `pg1`): `--convert writes a conversion for you to fill in; --delete keeps the field and lets the database cast its values, which can change or lose some.` True and now says what each flag does. Under `db update` it lists only `--delete`, correctly.
- **Temporary values**: after `db update`, `Field "User.f" got the temporary value 0 where existing data has none. To choose the value, …`; at plan time (Mongo `x7b`, Postgres `pg1`), `Field "User.plan" gets the temporary value "" where existing data has none. To choose the value, plan again with --backfill User.plan.` True on both targets.
- **Generic re-run advice**: `→ Resolve the cause the failure names, then re-run prisma db update` / `prisma db migrate`. No `--to <contract>` any more. Clear.
- **Failed cast under `db migrate`** (Postgres `pg1`): `replace that cast with a conversion of your own there, run node …/migration.ts, and re-run prisma db migrate`, then the re-plan with `--convert`. On Postgres, with a `using` clause to edit, this is clear; `The failed apply changed nothing` is true (the alter is transactional). On MongoDB see problem 5.
- **W1 warning through `migration plan`** (`w1`, `s8b`): `⚠ Field "User.status" gains enum "Status". This change is not a statement, so the plan does not rewrite the documents. Write a dataTransform in migration.ts, before the validator change, that rewrites them to fit; until they fit, the validator change checks the documents and fails the apply. With db update, plan the change with migration plan instead.` Also present in `--json` as `warnings`. Following it for the value object case (`s8b`, a hand-written `dataTransform`) worked.
- **Applied count**: `Applied 2 of 3 operation(s) across 1 contract space; the other 1 had nothing to do, since their postchecks already held` on an empty collection, and the same form after re-runs. Fixed.
