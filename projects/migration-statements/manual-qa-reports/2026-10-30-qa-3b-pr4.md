After each successful step the rows read back as expected, a further plan was empty, and `db verify --schema-only` was clean. Every failed apply left the database unchanged. No data was lost without a statement asking for it.

## Defects

1. ⚠️ **F1 (high) — On SQLite, `db migrate` applies a `--backfill` migration whose placeholders were never filled, and the rows are left without the required field.** Steps, on a fresh SQLite project with three `Site` rows holding `GeoPoint { lat, lng }`:
   1. Add `country String` to `GeoPoint`. `prisma contract emit`, `prisma migration plan --from <init> --name country --backfill GeoPoint.country`. It prints `⚠ Planned migration with placeholder(s)` and writes `ops.json` as `[]`.
   2. Do not edit `migration.ts`. Run `prisma db migrate`:
      ```
      ✔ Applied 1 migration(s) (0 operation(s)) across 1 contract space(s)
      App space
      ├─ (no operations)
      └─ marker 8d7f491d…
      ```
   3. The rows still read `{"lat":1,"lng":2}`, with no `country`. `db verify --schema-only` says `✔ Database schema satisfies contract`, and the marker says the database is at the new contract.
   A user who forgets the placeholder ends up with rows that break the contract and no tool that notices. On Postgres the same `[]` is applied, but the new shape checks catch it (see F3). For a column backfill the schema check catches it too (`missing: database/site/column:code`), so value object fields on SQLite are the case with no safety net. `db migrate` should refuse a migration with unfilled placeholders.
2. ⚠️ **F2 (medium) — On Postgres, a hand-written `renameStoredKey` on a `Json` column fails with an unexpected error.** `model Doc { id Int @id; points Json }` makes a `json` column. In a planned migration I added `this.renameStoredKey({ schema: 'public', table: 'doc', column: 'points', path: '$.*.lat', to: 'latitude' })`. `node migration.ts` accepted it. `prisma db migrate`:
   ```
   ✘ [CLI.UNEXPECTED] Unexpected error
     why: Unexpected error during migrate: function jsonb_path_exists(json, unknown) does not exist
   ```
   Nothing changed. The same operation on a `Jsonb` column worked. Either the operation should refuse a `json` column when `migration.ts` runs, with a message that says it needs `jsonb`, or it should cast.

## Message problems

3. **F3 — On Postgres, applying an unfilled backfill migration gives advice about the contract, not the placeholder.** `db migrate` says `MIGRATION.SCHEMA_VERIFY_FAILED … missing: database/public/site/check:site_history_shape_7eabe8b7 …` and suggests changing the contract source or the operations. It should say the migration still has `placeholder(...)` calls to fill, and name the `node … migration.ts` command. The plan's own hint says `Replace each placeholder(...) call … with your query`, but the value is a value, not a query.
4. **F4 — The refusal of a value object rename gives advice this PR makes wrong.** `--rename GeoPoint:Geo`: `why: "GeoPoint" is a value object, and value object renames are not supported in this release.` `→ Leave value objects and their fields out of the statements.` Value object fields are now statements. It should say only that the value object itself cannot be renamed.
5. **F5 — A field named through a model path gets an unrelated reason.** `--rename Site.location.lat:Site.location.latitude`: `why: The destination contract has no namespaces.` It should say that a value object field is named through its value object, `GeoPoint.lat`.
6. **F6 — `migration plan` and `db update` ask different questions for the same rename, and `db update` offers a delete that fills zeros.** With `lat` renamed to `latitude` and no statement:
   - `migration plan`: `Value object field "GeoPoint.latitude" is required, and existing objects at path "$[*]" in column "history" of "site" may have no value for it`, then `If it is a field renamed, add --rename GeoPoint.lat:GeoPoint.latitude. Otherwise add --backfill GeoPoint.latitude`. It names one column and path of the three, and does not mention that `lat` would be lost.
   - `db update`: `"GeoPoint.lat" needs a statement`, offering `--rename GeoPoint.lat:GeoPoint.latitude` or `--delete GeoPoint.lat`.
   Both lead to the rename, which is good. But following `db update`'s second hint, `--delete GeoPoint.lat`, removes every `lat` and writes `latitude: 0` in every object, with only a warning afterwards. The `--delete` hint should say the new field `GeoPoint.latitude` will get the temporary value `0`.
7. **F7 — A removed variant with a new sibling is offered `--rename 'Bug:<new name>'`.** Renaming `Bug` (value `defect`) to `Issue` (value `issue`): the hint is `--rename 'Bug:<new name>'`, though `Issue` is a new variant of the same base. Value object fields get the concrete pair (`GeoPoint.lat:GeoPoint.latitude`); variants should too.
8. **F8 — The enum question lists every path in one sentence.** Renaming `ARCHIVED` and removing `DRAFT` on a value object held three ways with three enum members gives a `why` of 18 clauses, such as `remove value "archived" at path "$[*].kind" in column "history" of "site", remove value "archived" at path "$.kind" …`. A count of columns and paths, or one line each, would read better.
9. **F9 — The failure for a removed enum value in a required field works, but each route has a rough edge.** `MIGRATION.PRECHECK_FAILED 1 row of "site" holds "draft" at path "$[*].kind" in column "history", a member that takes no null, so the value cannot be removed.` Nothing changed. Both routes it gives kept the data when I followed them (by hand on Postgres, `replaceStoredValue` to `active`; a new member `LEGACY` with `--rename Status.DRAFT:Status.LEGACY` on SQLite). The rough edges:
   - The summary names only the first path; `$.kind` in `location` held `draft` too. The `migration plan` advice does list both.
   - The by-hand advice quotes `this.removeStoredValue({ schema: "public", … })` with double quotes and on one line, while `migration.ts` has single quotes and one key per line, so searching the file for the quoted text finds nothing.
   - The `db update` advice says `change the stored value "draft" to one the enum keeps in the database yourself`, with no query. Inside a list this needs `jsonb_agg` over `jsonb_array_elements`, which few users will write unaided.
   - It suggests adding a new member, but not mapping `draft` onto an existing one, which is what I wanted.
10. **F10 — The temporary value warning is printed once per column.** `db update` adding `country String` prints `⚠ Existing rows got "" in field "GeoPoint.country". To choose the value, plan a migration with prisma migration plan --backfill GeoPoint.country instead.` three times, identically. Once per field is enough.
11. **F11 — `migration plan --backfill` does not list the fill operations.** On Postgres the tree shows the three check drops and three check adds but not the three `fillStoredKey` calls. On SQLite the tree is empty. `db update` lists them as `Fill key "country" at path "$[*]" in column "history" of "site"`.
12. **F12 — A wrong-typed backfill value names the codec, and the message is printed twice.** `value 5 at path "$[*].country" is not one the data type of codec "pg/text@1" accepts`, once with `CONTRACT.ARGUMENT_INVALID:` and once without. Saying `GeoPoint.country is a String` would tell the user what to write. No `ops.json` was written, as promised.
13. **F13 — The `db update` refusals for backfill are vague.** For a `DateTime` field: `db update cannot choose a value for a field that holds a value object or an enum value, or whose codec has no temporary value.` It should say which of the three applies. `db update --backfill GeoPoint.seen` gives `--convert and --backfill ask for a migration file`, but `--convert Bug` now works under `db update`; it should name only `--backfill`.
14. **F14 — SQLite variant questions always carry the foreign key paragraph.** Every SQLite variant question adds `SQLite migrations run with foreign keys off, so deleting these rows does not delete the rows of other tables that reference them: the apply then fails at PRAGMA foreign_key_check. Delete or change those rows first.`, even when no other table references the rows. For a variant with its own table whose value changed (`Chore`), the operation reads `Delete the rows of "task" that hold value "chore"` and does not say that the rows of `chore` go too, although they do (`cascade` in `migration.ts`). SQLite also writes `Drop table epic` and `Drop column severity on task` without quotes, where Postgres quotes them.
15. **F15 — The wildcard precheck rewrites the path and blames drift.** With `path: '$.*.lat'` and a row holding both `lat` and `latitude`: `ensure no object at path "$[*]" in column "points" of "doc" has both key "lat" and key "latitude"`, then `The database has drifted from its migration history`. I wrote `$.*`, not `$[*]`, and nothing drifted: one row holds both keys. The advice should say to remove one of the two keys from that row. After I deleted the row, the rename applied on both targets, over objects of objects and over a list, and left a scalar member (`"a": 5`) alone.
16. **F16 — A SQLite foreign key failure says "the listed tables" and lists none.** `--delete Bug` with a `comment` row referencing a `bug` task: `MIGRATION.FOREIGN_KEY_VIOLATION … rows of the listed tables reference rows that a recreate-table or deleteRows operation removed`. The human output lists no table; the violations are only in `--json` `meta`. The advice says `reconcile schema drift if needed`, which does not apply. Nothing changed.
17. **F17 — The Postgres DDL preview leaves out the data rewrites.** For the `lat` rename the preview shows the three `DROP CONSTRAINT` and three `ADD CONSTRAINT` statements but not the three `UPDATE`s that rename the keys. The preview is where a reviewer reads the SQL, and the rewrites are the part that touches the data.
18. **F18 (minor) — The applied count is lower than the planned count without saying why.** The enum migration planned 24 operations; `db migrate` printed `Applied 1 migration(s) (16 operation(s))`. The other 8 had nothing to do, I assume, but the output does not say so.

## Not this PR

19. **F19 — A data-only hand-written migration cannot be applied.** `prisma migration new` from the current hash, with only a `renameStoredKey`, is refused by `db migrate`: `MIGRATION.CONTRACT_SPACE_VIOLATION … has source equal to target … with no data invariant — a true no-op self-edge`, with advice to restore the directory from version control. I had to make a contract change (add `note String?`) to carry the operation. The PR says every operation is a method a user can call by hand; for a `Json` column the user has no contract change to attach it to.
20. **F20 — `db migrate` does not advance the `db` ref**, so every later `migration plan` needs `--from` (`MIGRATION.PLAN_ORIGIN_UNKNOWN` otherwise). Known from earlier slices.

## Scenario notes

1. **Value object field rename.** Contract: `GeoPoint { lat Float, lng Float }`, `Place { name String, point GeoPoint }`, `Site { location GeoPoint, history GeoPoint[], place Place? }`. Rows: one with every path filled, one with an empty list and SQL `NULL` in `place`, one with JSON `null` in `place`.
   - Postgres, `migration plan --rename GeoPoint.lat:GeoPoint.latitude`: 9 operations (three check drops, three `renameStoredKey` with `$.lat`, `$[*].lat`, `$.point.lat`, three check adds) and `Statements applied … rename value object field "GeoPoint.lat" to "GeoPoint.latitude" (3 operations)`. `migration.ts` matches the PR example. Re-running `node migration.ts` reproduced `ops.json` byte for byte. Rows renamed everywhere; SQL `NULL` and JSON `null` kept apart.
   - `db update` with the statement: the same 9 operations and summary. SQLite: 3 operations (no checks), same result. Without a statement see F6.
2. **Field removal.** Without a statement: `"GeoPoint.lng" needs a statement`, offering `--rename 'GeoPoint.lng:GeoPoint.<new name>'` and `--delete GeoPoint.lng`. With `--delete GeoPoint.lng`: three `⚠ Remove key "lng"` operations, the destructive warning, `delete value object field "GeoPoint.lng" (3 operations)`. Same on all four runs.
3. **Enum values.** `Status { ACTIVE, ARCHIVED, DRAFT }` (`@@type(".../text@1")`) held by `GeoPoint.status Status?`, `kind Status` (required) and `tags Status[]`, at three paths. One row held `draft` in the required `kind` in `location` and `history`. The plan and failure are in F9. After the fix: `archived` became `retired` everywhere, `draft` became JSON `null` in `status`, left `tags`, and an absent optional key stayed absent. The SQLite run through a new member `LEGACY` turned every `draft` into `legacy`.
4. **New required field.** Without `--backfill`: `Add --backfill GeoPoint.country to write the value the plan fills them with.` Clear. With it: `fillStoredKey` per path with `codecRef: { codecId: 'pg/text@1' }`. `value: 5` (Postgres) and `value: true` (SQLite) refused (F12); `'NO'` applied and filled every object, including list elements, and left `NULL` and JSON `null` alone. `db update`: `""` for `String`, `[]` for `String[]`, `false` for `Boolean`, with warnings (F10); `DateTime` and a value object typed field refused (F13); nothing changed on refusal.
5. **Variants.** `Task` (`@@discriminator(type)`) with `Bug` (shared, `severity`), `Epic` (own table, `points`), `Story` (no columns), `Chore` (own table, `size`); seven rows, own-table rows in `epic` and `chore`. In order:
   - `bug` → `defect`, `--convert Bug`: `Replace value "bug" with "defect" in column "type" of "task"` between the old and new `task_type_check` on Postgres.
   - `Bug` → `Issue` with value `issue`, `--rename Bug:Issue`: the same rewrite, `rename model "Bug" to "Issue"`. See F7.
   - `Chore` value `chore` → `job`, `--delete Chore`: base rows and `chore` rows deleted, `chore` table kept, on both targets.
   - `Epic` removed, `--delete Epic`: `Drop table "epic"` then the base rows. On SQLite, with rows in `epic`, the table was dropped and the base rows deleted.
   - `Issue` removed, `--delete Issue`: `Drop column "severity"` and the base rows.
   - `Story` removed, `--delete Story`: the base rows only.
   Every question offered `--convert` first for a changed value, and asked one question per model.
6. **Wildcards.** `$..lat` is refused when `node migration.ts` runs: `path "$..lat" is not a JSONPath of member names (.name or ['name']) and wildcards ([*] or .*) from $`. Clear, and it says what is allowed (printed twice, as in F12). `$['x'].*.lat` was accepted. See F2 and F15 for `$.*.lat`.
7. **Exploratory.** Wrong statements: `--rename GeoPoint.lat:Place.latitude`, `GeoPoint.nope:…`, `GeoPoint.lat:GeoPoint.lng` and `--backfill GeoPoint.lat` each name the value object and list its fields. Clear. `--convert GeoPoint.lat` says a convert names a model or variant field. `--delete GeoPoint` is `CLI.CONSENT_UNUSED`. `--convert Epic` (unchanged) and `--convert Bug.severity` (same type) are refused with the reason. `db update --convert Bug` on SQLite rewrote the value. F4, F5, F6 and F16 came from here.
