## Problems, ranked

### Data loss

None found.

### Wrong advice

1. **The docs say the document check stops a new required unique field; the index build stops it first.** The upgrade fragment (`upgrade-instructions/pending/mongo-validator-changes-check-documents/app/instructions.md`, last paragraph) says: "on a collection with documents, the validator change's document check stops the apply until they have values, so plan it with `--backfill`". The skill reference (`skills/prisma-8/references/migrations.md`, the "On MongoDB" item) says such a field "is left to the document check". In `x9`, adding `slug String @unique` to two documents failed at the index build, before any document check: `the unique index slug_1 cannot be built, because two documents in collection users hold the same value { slug: null }`. The advice in that error is good (see below), and the docs' conclusion (use `--backfill`) is right; only the named step is wrong.

### Unclear text

2. **The W1 warning still has no `⚠` under `db update`.** `s8`, `w2`: `db update` prints `Field "Address.zip" of a value object changes type. No statement …` as a plain line on stderr; `migration plan` prints the same text with `⚠`. Round 11 problem 7, not fixed.
3. **On MongoDB, "replace that cast with a conversion of your own" still does not say what a conversion is there.** `c7` (`db migrate` after `--delete User.age` met `"abc"`): the first advice says to replace the cast in `migration.ts` with "a conversion of your own"; on MongoDB that means swapping `castField(...)` for a `dataTransform`, which the message does not say. The new advice `Change the value the failure names so the database's cast accepts it, then re-run prisma db migrate` works (I followed it), and the re-plan with `--convert` is concrete, so the user has two working routes.
4. **The upgrade fragment's layout breaks its list.** Under `mongo-validator-change-checks-documents`, the sentence "When `db migrate` or `db update` stops … because documents do not fit:" is followed by a separate paragraph ("Operations of the migration that ran before the validator change stay applied; a re-run skips them.") before the numbered steps. The colon then leads to the wrong paragraph.

## Round 11 fixes, checked

- **`--backfill` only for fields that need it** (`M1` to `M4`): `This validator change makes "born" and "plan" required. … That document has no "born". … To give "born" values you choose, plan the change with migration plan --backfill User.born.` The advice no longer names the already-filled `plan`. The first sentence still lists `plan` as something the change touches, which the docs describe as intended.
- **Required unique field on a collection with documents** (`x9`): `The documents that collide lack "slug" or hold null in it, and a document without the field counts as holding null. Give each document its own value of the indexed fields, or remove the duplicates, then run the command again; … Under migration plan, --backfill User.slug writes a slot to give each document its own value. The failed apply changed nothing.` True and complete.
- **Enum reason** (`w1`): `That document holds "gone" in "status", a value the new validator does not allow there.`
- **W1 wording** (`w1`, `s8`, `s8b`): `No statement (--rename, --delete, --convert, --backfill) covers this change, so the plan does not rewrite the documents. Write a dataTransform in migration.ts, before the validator change, that rewrites them to fit; … With db update, plan the change with migration plan instead.` Clear. Following it with a hand-written `dataTransform` (`s8b`) worked.
- **Failed cast** (scenario 2 under `db update`, `c7` under `db migrate`, Postgres `pg1`): a new next action, `Change the value the failure names so the database's cast accepts it, then re-run …`, with the exact command (`prisma db update --delete User.age` under `db update`). I followed it each time and the re-run finished.
