## Findings

1. ⚠️ **F1 — On MongoDB, a refusal for a dropped collection offers only `--delete`, and says nothing about the hand rename that keeps the documents.** Contract renames `Event` to `Log` (scenario 9). Command: `prisma db update` (also `migration plan`). Output:
   ```
   ✘ [CLI.CONSENT_REQUIRED] "Event" needs a statement, and the session is not interactive.
     why: Drop collection Event would lose the data of model "Event".
   → Pass --delete Event
   ```
   In a terminal the question offers only `(delete)` (seen for the reverse rename, `Log` back to `Event`: `Drop collection Log would lose the data of model "Log". (delete)`), and the only way out is Ctrl-C. A user who renamed the model is offered exactly one route, and it drops the documents. The route that keeps them, `renameCollection` by hand and then `db update` with no statement (verified: `(no operations)`, 2 documents kept in `Log`), appears only if the user thinks to try `--rename Event:Log` and reads that error. I expected the refusal to say: "If it was renamed, rename the collection by hand first (see `--rename`'s error)". This is not a blocker, because the `why` says the data is lost and `--delete` is the explicit consent to that. But by the script's literal rule ("an error whose advice loses data if followed") it is close to one.
2. ⚠️ **F2 — The `<new name>` placeholder for a field leads to a rename that fails.** Command: `prisma db update --rename Profile:User` with `Profile.nickname` dropped and `User.handle` added (scenario 8). The refusal says `→ Pass --rename 'User.nickname:<new name>'`, and the question says `(rename User.nickname:<new name> or delete)`. The natural reading is `rename User.nickname:handle`. Typed at the prompt it fails: `Cannot resolve statement "--rename User.nickname:handle". The destination contract has no model "handle" (models: User).` The form that works is `User.nickname:User.handle`. For a field the placeholder should be `User.<new name>`, or a bare field name should resolve within the model. The re-ask did work, and the full form planned two renames and kept the rows.
3. ⚠️ **F3 — `--confirm <database>` is ignored without a word.** Command: `prisma db update --confirm dev.db` and `--confirm ./dev.db --no-interactive` (SQLite, scenario 3), `--confirm template1` (Postgres, scenario 5), `--confirm s9` (MongoDB), and `migration plan --confirm postgres`. Each gives the same `CLI.CONSENT_REQUIRED` as a run without `--confirm`. Nothing was applied, so no data is at risk. But a script author whose run used to pass sees a refusal that never mentions the flag they passed. I expected a line such as "`--confirm` no longer consents to data loss; use the flags below". The app upgrade fragment does say this.
4. ⚠️ **F4 — A second run of `--delete` gives advice that points the wrong way.** Command: `prisma db update --delete Legacy`, run again after it applied (SQLite). Output: `✘ [CLI.CONSENT_UNUSED] --delete Legacy was given but nothing in this run asked about Legacy.` / `→ Remove the flag, or spell the subject the way the command names it.` The spelling is right; the table is already gone. Compare the rename re-run in the same scenario, which is now exemplary: `The origin contract already has "User" and has no "Profile", so this rename has already happened. … → Leave out --rename Profile:User.`
5. ⚠️ **F5 — A misspelled or wrongly shaped `--delete` is not reported while a question is unanswered.** Commands (SQLite, scenario 4): `--delete Legcy`, `--delete legacy`, `--delete Legacy.note`; Postgres: `migration plan … --rename Profile:User --delete Legcy`; scenario 7: `--delete Legacy` and `--delete legacy_rows` where the subject is `public.legacy_rows`. Each gives the plain `CLI.CONSENT_REQUIRED` for `Legacy` and never says that the flag the user passed matched nothing. The user can work it out by comparing the suggested flag with their own, but the script expected `CLI.CONSENT_UNUSED`. `CONSENT_UNUSED` appears only when every question is answered (`--delete Foo` with `--delete Legacy`, or `--delete Foo` on a plan with no loss). In a terminal it is worse: with `--delete Legcy` the CLI asks about `Legacy`, I answered `delete`, and only then did it fail with `CONSENT_UNUSED` (nothing applied, `Legacy` kept). The unused flag should be reported before the question, and next to the refusal.
6. ⚠️ **F6 — `CONSENT_UNUSED` does not name the subjects the plan does ask about; the dry-run equivalent does.** Apply: `--delete Foo` → `→ Remove the flag, or spell the subject the way the command names it.` Dry run: `--dry-run --delete Foo` → `MIGRATION.STATEMENT_ANSWERS_NO_QUESTION … → Leave them out, or name a subject the plan asks about: Legacy.` The dry-run wording is the one to copy. Note: the script expected `--delete` on a dry run to fail with `CONSENT_UNUSED`. It does not: `--dry-run --delete Legacy` succeeds, marks the question `(answered)` and suggests `prisma db update --delete Legacy`. This matches commit `b3d90528c0` and the app fragment, so the script is out of date here, not the CLI.
7. ⚠️ **F7 — Dropping a permissive row-level-security policy narrows access, but the CLI says it widens it.** Command: `prisma db update` after removing `policy_select tenant_read` (permissive, `using (tenant_id = 1)`, role `app_user`) while `@@rls` stays (scenario 5). Question: `Drop RLS policy "tenant_read_f8d5e783" on "user" would widen who can read and write its rows.` Before the apply, `SET ROLE app_user; SELECT count(*) FROM "user"` → `1`; after `--allow User` → `0`. With row-level security on, permissive policies grant access, so dropping one takes access away. Disabling row-level security does widen it (`0` → `2` rows after the `to2` step). Asking before a policy drop is defensible; the stated reason is wrong, and `--allow` reads as "allow wider access".
8. ⚠️ **F8 — When one model has two access questions, the question names only one operation.** Contract removes the policy and `@@rls` together. Dry run lists both under `An apply asks about`. The refusal and the prompt say only `Drop RLS policy … would widen …`, not `Disable row-level security`, which is the operation that actually widens access. One `--allow User` applied both (`allow model "User" (2 operations)`). The `why` should list every operation behind the subject. The interactive question also has no way to say no except Ctrl-C.
9. ⚠️ **F9 — On MongoDB, a new required field leaves every existing document unwritable, and nothing says so.** Command: `prisma db update` adding `size Int` to a populated `Item` (scenario 6). Output: `Update validator on Item (added: size)`, no question, no warning. Afterwards `updateOne({note:'a'},{$set:{note:'aa'}})` fails with `Document failed validation`, because no existing document has `size`. The same happens when `note String?` becomes `note String` with a `null` and a missing `note` in the collection. No data is lost, and the reclassification to `widening` is by design. But the old classification at least warned; now a user gets no hint that existing documents need a backfill. A line such as "3 existing documents do not satisfy the new validator" would help.
10. ⚠️ **F10 — The NOT NULL failure on Postgres is clear about the cause but its advice is about drift.** Command: `prisma db update` with `note String?` → `note String` and one NULL (scenario 6). Output:
    ```
    ✘ [MIGRATION.RUNNER_FAILED] Operation alterNullability.setNotNull.Item.note failed during precheck: ensure no NULL values in "note"
      why: Migration runner failed
    → Inspect the reported conflict, reconcile schema drift if needed, then re-run `prisma db update`
    ```
    Nothing changed (column still nullable, both rows intact), and after setting the NULL the same command applied. The `why` says nothing, and there is no drift. I expected: "N rows have NULL in `note`; set a value or keep the field optional." SQLite gives `NOT NULL constraint failed: _prisma_new_Item.note` with the same advice, also without data loss.
11. ⚠️ (minor) **F11 — The refusal's next steps are flags, not commands, and the alternatives are not grouped.** `nextActions` are `user-choice` entries such as `Pass --delete Legacy`, four for two subjects, with nothing marking which ones are alternatives for the same subject. `meta.unanswered[]` groups them correctly. A `run-command` with the user's command plus the flag would be easier to paste. The summary `2 subjects need a statement` uses project words ("subject", "statement") that a first-time user does not know.
12. ⚠️ (minor) **F12 — The no-snapshot refusal is one long paragraph.** Command: `prisma db update --db <url>` with no snapshot (scenario 7). The `why` runs to about 120 words with steps 1–3 inline. The steps are correct: I followed them (emit the old contract, `--advance-ref qa --dry-run` → `(no operations)`, apply, emit the new contract, `--advance-ref qa --rename Legacy:Old`) and the table was renamed with both rows kept. The `STATEMENT_ORIGIN_UNKNOWN` error gives the same steps as separate `→` lines, which reads far better.
13. ⚠️ (minor) **F13 — A dry run with `--db` suggests an apply without `--db`.** Command: `prisma db update --db <url> --advance-ref qa --dry-run`. Last line: `→ Apply the planned operations: prisma db update`. Followed literally, it runs against the config's database, not the one just previewed, and without the ref. The answered `--delete` flags are carried over (F6 note); `--db` and `--advance-ref` should be too.
14. ⚠️ **F14 — A type change is answered with `delete` and reported as a deleted field, even when it keeps every value.** Postgres `age Int` → `age String`: `Alter type of "User"."age" to text would lose the values of field "User.age"` → `Pass --delete User.age`, reported as `delete field "User.age"`. SQLite `qty Int` → `qty String` with `--delete Item.qty`: values `1`, `2` kept as text, report says `delete field`. The spec defers `--convert` to slice 3, so this is known, but the wording tells the user they are deleting data they are not.
15. ⚠️ (minor) **F15 — Extension fragment: one rule from the spec is missing.** The spec says the transient DROP of a policy replacement (drop then create a changed policy) is not listed in `accessWidening`. The extension fragment does not say this, so a third-party planner author would list it and make every policy edit ask. Every type and import path the fragment names exists in the built packages' `.d.mts` (checked: `MigrationSubject`, `MigrationOperationSubject`, `MigrationPlanSubjects`, `subjectsOfCalls`, `CallSubjects`, `FieldEventCall`, `storageNameOfOperation`, `AnswerPlanQuestions`, `PlanQuestion`, `PlanAnswer`, `AskedSubject`, `AlterColumnTypeCall`, `RecreateTableCall`).
16. ⚠️ (minor) **F16 — The skill says `CONSENT_UNUSED` covers a typo; a typo next to an unanswered question gives `CONSENT_REQUIRED` (F5).** `skills/prisma-8/references/migrations.md` line 75.
17. ⚠️ (minor) **F17 — The CLI ignores SIGTERM while a question is open.** Command: `prisma migration plan --name t --from 20261008T0244_initial` in a pseudo-terminal, left at the question, then SIGTERM. It was still running 5 s later and needed SIGKILL (in the first attempt it was still running after 20 s). Ctrl-C works (exit 3, `CLI.PROMPT_CANCELLED`, nothing written). A CI job with a TTY and a timeout would hang until killed. This may come from the engine's prompt, not this slice.

## Not covered, and observations outside this slice
