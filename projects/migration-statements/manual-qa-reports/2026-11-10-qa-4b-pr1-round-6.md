## Problems, ranked

### Data loss

None found.

### A state the user is warned about, but could be avoided

1. **When a plan touches two collections, a failed document check on the second leaves the first one's documents failing their updates.** The plan orders each collection's check right before its own rewrites, then all validator changes at the end: `Check … accounts`, `Fill … accounts`, `Check … users`, `Fill … users`, `Update validator on accounts`, `Update validator on users`. `h7` (through `db update`) and `h8` (through `migration plan` then `db migrate`), with no hand edits: a new required `plan String` on `Account` and `User`, and a new required `born DateTime` on `User` only. The accounts check passed and the fill wrote `plan: ""` into the `accounts` document. Then the users check failed on the missing `born`. The `accounts` validator was never changed, so its old validator (`additionalProperties: false`, no `plan`) now rejects every update to that document; I confirmed "Document failed validation". The message does warn: `Documents this apply already rewrote in collection accounts may no longer fit the collection's current validator, so updates to them fail until the migration finishes.` But two things could be better:
   - Running every collection's document check before any rewrite would avoid the state entirely. The single-collection case already works that way.
   - The same why says earlier `No rewrite of this plan changes what makes them fail, so nothing was rewritten.` That sentence is about `users`, but read with the later warning it contradicts itself.

   After I gave `born` a value, the re-run applied everything and verify was clean.

### Unclear text

2. **The applied count can be lower than the list** (carried over). `x8`, on an empty collection: `Applied 3 operation(s)` above four listed operations.

## Hand edits

All start from a collection of two documents and a plan that fills a new required `plan` (`h2` and `h4` also add a required `born DateTime`).

- **Tightening the const (`h1`).** A required `nick` added to `usersValidator` reached both operations. `db migrate` stopped at the early check before the fill, `That document has no "nick"`. Documents unchanged.
- **Loosening the const (`h2`).** Unedited, the check stopped on `born`; documents unchanged. With `born` removed from `required`, the check passed, the fill and validator applied, then the expected `SCHEMA_VERIFY_FAILED` (no "may no longer fit" warning, correctly, since the loosened validator is in place).
- **`collMod` deleted, check kept (`h3`).** The check ran against the const, the fill ran, then `SCHEMA_VERIFY_FAILED` with the warning that rewritten documents may fail updates; I confirmed they do.
- **Empty precheck in `ops.json` (`h4`).** After recomputing the hash: `MIGRATION.INVALID_OPERATION_ENTRY ... but has no check.` with `Run the migration.ts of that migration with node again`. Nothing ran.
- **Two validator changes on one collection (`h5`).** A second `collMod` using `usersValidator2` (which also requires `nick`) after the planned one. `db migrate` ran the check, the fill and the first `collMod`, and stopped at the second. The why now says `The validator in place is the one an earlier operation of this apply set: Update validator on users (added: plan).` and lists both the fill and that validator change as applied. Round 5's problem is fixed.
- **Two collections with equal validators (`h6`).** The plan writes one const per collection (`accountsValidator`, `usersValidator`) even though they are identical, and each check and `collMod` uses its own collection's const. I tightened only `usersValidator`: `ops.json` changed only the users check and the users `collMod`. `db migrate` stopped at the users check (`no "nick"`). The `accounts` check and fill had already run, which led me to problem 1. The unedited plan, re-planned, then applied (`5 of 6 operation(s); the other 1 had nothing to do`) and verify was clean.
