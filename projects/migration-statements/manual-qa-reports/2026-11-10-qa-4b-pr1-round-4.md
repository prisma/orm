## Problems, ranked

### Data loss

None found.

### Wrong advice, or a state the user is not warned about

1. **Deleting the `collMod` and keeping the check leaves documents the current validator rejects, and the failure does not say so.** `h3`: a plan that fills a new required `plan`. With the `collMod` deleted, the check ran against `usersValidator` and passed, the fill wrote `plan: ""` into both documents, and the apply stopped at `MIGRATION.SCHEMA_VERIFY_FAILED ... mismatch: users/validator`, with clear advice about hand edits. But the old validator (`additionalProperties: false`, no `plan`) is still in place, so both documents now fail every update ("Document failed validation", confirmed). The message says only "The operations that ran before the failure stay applied". This is the result of a hand edit the user chose, so it ranks low, but the same sentence the cast and data transform failures now carry ("a document … may no longer fit the collection's current validator, so updates to it fail") would help here.
2. **Advice to fix documents cannot work when the only cause is a field stored under a dotted name.** `x1`: the why now says `That document has "addr.zip", which the new validator cannot check: MongoDB reads a name containing "." as a path into embedded documents.` That is clear. But it is followed by the usual advice to change the documents and run the command again. A document holding that field can never fit the validator, so no document fix works; the fix is to store the field under a name without `.` (or use `checkDocuments: false` under `db migrate`). Low priority: `@map` with a `.` is older, already broken behaviour.

### Unclear text

3. **The docs do not describe the shared validator const.** Neither `skills/prisma-8/references/migrations.md`, the upgrade fragment nor the Migration System doc says that `migration.ts` declares each validator once (`const usersValidator = …`) and that both `checkDocuments(...)` and `collMod` read it, so editing the const changes both. A user editing the file will see it, but an agent reading the skill would not know.
4. **The applied count can be lower than the list** (carried over). `x8`, on an empty collection: `Applied 3 operation(s)` above four listed operations.

## Hand edits

All four start from a collection of two documents and a plan that fills a new required `plan` (`h2` and `h4` also add a required `born DateTime`). The planned `migration.ts` starts with `const usersValidator = { … }`, and both `checkDocuments({ collection: 'users', validator: usersValidator, rewrittenFields: ['plan'] })` and `collMod(..., { validator: { $jsonSchema: usersValidator } })` use it.

- **Tightening the const (`h1`).** I added a required `nick` to `usersValidator` and ran the file; `ops.json` then had `nick` in both the check and the `collMod`. `db migrate` stopped at the early check before the fill: `This validator change makes "nick" required. ... That document has no "nick"`, `no rewrite of this plan makes them fit`. Documents unchanged. The edit reached both operations.
- **Loosening the const (`h2`).** Unedited, the check stopped on `born`; documents unchanged. With `born` removed from `required` in the const, the check passed, the fill and the validator applied (live `required`: `_id`, `email`, `plan`), then the expected `SCHEMA_VERIFY_FAILED` because the validator no longer matches the contract.
- **`collMod` deleted, check kept (`h3`).** `node migration.ts` wrote `ops.json` with the check and the fill, no error. `db migrate` ran the check against the const (passed), ran the fill, then stopped at `SCHEMA_VERIFY_FAILED ... mismatch: users/validator`. The validator was not changed. Problem 1 describes the state this leaves.
- **Empty precheck in `ops.json` (`h4`).** I set the `checkDocuments` entry's `precheck` to `[]`. `db migrate` first refused with `MIGRATION.CONTRACT_SPACE_VIOLATION` (the hash no longer matched). After recomputing the hash, it refused with `✘ [MIGRATION.INVALID_OPERATION_ENTRY] Operation collection.users.checkDocuments checks the documents of collection users, but has no check.`, `why: A checkDocuments operation carries the check its migration.ts builds; without it the operation would check nothing.`, `→ Run the migration.ts of that migration with node again, so it writes ops.json with the check.` Nothing ran; documents unchanged.
