## Problems, ranked

### Data loss

None found.

### Wrong advice

None found. Round 2's problems are fixed:

- Running `migration.ts` with a `checkDocuments(...)` call and no validator change after it now fails with guidance (details below). The error reference covers it.
- A data transform that fails part way now says `Until a re-run finishes, a document the update already changed may no longer fit the collection's current validator, so updates to it fail.`
- A value object type change failure now says `That document holds a value of type string in "address.zip", which the new validator does not allow there.`

### Unclear text

1. **When the shown document fails only because of a field stored under a dotted name, the why gives no reason.** `x1`: the collection has a field stored as `"addr.zip"` (allowed by `@map`, older behaviour). A `db update` whose plan casts other fields stopped at the early check with only `One of them has _id ObjectId("…")` and the query: no "This validator change …" and no "That document …" sentence. Documents holding a top-level `"addr.zip"` key never fit the validator (older behaviour), so the check is right to stop. The user just is not told why. Low priority: such fields are already hard to use.
2. **The applied count can be lower than the list** (carried over). `x8`, on an empty collection: `Applied 3 operation(s)` above four listed operations.
3. **If the user ignores the `node migration.ts` failure, `db migrate` applies the last good `ops.json`.** `h3`: after deleting the validator change, `node migration.ts` failed and left `ops.json` as planned; `db migrate` then applied the original plan, including the validator change the user had deleted. The result matches the contract, so this is safe, and it is how `ops.json` works generally. A user might still be surprised that the edit they made had no effect.

## Hand-edits to a planned `migration.ts`

Each case starts from a collection of two documents and a plan that fills a new required `plan` (`h2` also adds a required `born DateTime`). The plan's early check is `checkDocuments({ collection: 'users', rewrittenFields: ['plan'] })`.

- **Tightening (`h1`).** I added a required `nick` to the `collMod` validator and ran the file. `db migrate` stopped at the early check before the fill: `This validator change makes "nick" required. ... That document has no "nick"`, `no rewrite of this plan makes them fit`. Documents unchanged. The check followed the edit.
- **Loosening (`h2`).** Unedited, the early check stopped on `born`, documents unchanged. I removed `born` from `required` and ran the file. The early check passed, the fill and the validator applied (live `required`: `_id`, `email`, `plan`), then `MIGRATION.SCHEMA_VERIFY_FAILED ... mismatch: users/validator`, as expected for a validator that no longer matches the contract. The check followed the edit.
- **Validator change deleted (`h3`).** I deleted the `collMod` and left `checkDocuments(...)` and the fill. `node migration.ts` now fails and writes nothing:

  > MIGRATION.INVALID_OPERATION_ENTRY: checkDocuments on collection users has no validator change of that collection after it in the same migration. The check reads the validator it checks the documents against from the first validator change of its collection after it in the same migration.ts. Remove the checkDocuments(...) call, or restore the validator change of collection users after it in migration.ts, then run the file with node.

  Clear, and caught at the right time. See problem 3 for what happens if the user runs `db migrate` anyway.

## Per scenario

### 1. `String` to `Int` through `migration plan`

Three documents: `"42"`, `"7"`, `"abc"`. `contract emit` warned that `Int` is deprecated (from main). Refused with `--convert User.age` and `--delete User.age`. `--convert` planned the check, `Data transform: User.age` and the validator; one slot. Unfilled: `MIGRATION.UNFILLED_PLACEHOLDER`. Filled with a `$convert` pipeline (`onError: 0`): applied; values `int` 42, 7, 0; further plan empty; `db verify --schema-only` clean; an update to every document succeeded. Pass.

### 2. `--delete` through `db update`

Only `--delete User.age` offered. The cast failed on `"abc"` and said documents already cast fail their updates until a re-run. After changing `"abc"` to `"13"`, the re-run cast both values to `int`; further update empty; verify clean. Pass.

### 3. `Int32` to `Int64`

### 4. New required fields

### 5. Optional field made required

### 6. `--backfill` through `migration plan`
