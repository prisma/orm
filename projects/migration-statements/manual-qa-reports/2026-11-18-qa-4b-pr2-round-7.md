## New problems, ranked

### Wrong advice

1. **Medium. When a model gets its first discriminator and a variant has a required field, the stop names `--backfill Bug.severity`, which the planner refuses.** Reproduce (`wip/qa-pr2/r7bg`, source `b7src`): `Task` without a discriminator, two documents `{ title }`. The new contract adds `type` as the discriminator and variants `Bug` (`severity String`, required) and `Epic`. `migration plan` plans one validator change; `db migrate` (and `db update`) stop with "This validator change makes "severity" and "type" required. … To give "severity" and "type" values you choose, plan the change with --backfill Bug.severity --backfill Task.type". The next step gives `prisma migration plan --from <hash> --name step --backfill Bug.severity --backfill Task.type`. Followed, in both orders: "Cannot resolve statement "--backfill Bug.severity" … the origin has no model "Bug" … A new model has no existing rows to backfill. Leave out --backfill Bug.severity." With only `--backfill Task.type` (`r7bf`) the apply stops again on `severity`, and the stop names `--backfill Bug.severity` alone, which is refused the same way. Nothing is written and no data is lost. The mongosh route in the same message works (`r7bg`: set `type` and `severity` with `bypassDocumentValidation`, then `db update` applied, after checks clean). Should be: `--backfill Bug.severity` is accepted when the documents get Bug's discriminator value from a backfill in the same plan, or the stop does not name it and says to set Bug's fields in the `Task.type` backfill's update.
2. **Low. A stop on a renamed value object key offers a `--backfill` route that the planner refuses.** Reproduce (`r7o1`, source `s1`): document `d` holds `home: { zip: '9' }` with no `street` (the old validator already rejected it) and `addresses: [null, …]`. `migration plan --rename Address.street:Address.line1`, then `db migrate` stops on `home.line1`. New in this round, the next step says "delete `migrations/app/<dir>` …, plan it again with `prisma migration plan --from <hash> --name step --backfill Address.line1`, adding any other statements you planned it with". With `--rename Address.street:Address.line1` added: "The field "Address.line1" is already required in the origin contract, so every existing value has it. Leave out --backfill Address.line1." Without it: the `Address.street` question comes back. The other next step, "Make the field optional in the contract source", does not fix it either: the plan stops again on the `null` element (`r7o1x`). Round 6 printed "Resolve the cause the failure names, then re-run", which was right. Fixing the document in mongosh and re-running worked under both commands. Should be: no `--backfill` route when the field is the target of a rename of a required field; keep "Resolve the cause the failure names".
3. **Low. "Make the field optional in the contract source" is offered for a discriminator, which cannot be optional.** Reproduce (`r7fo`): the first-discriminator stop (`r7fg`) and the new-discriminator stop (`r7k9`) both end with "Make the field optional in the contract source, and plan it again". Changing `type String` to `type String?` fails `contract emit`: "Discriminator field "type" on model "Task" must be required, but it is optional. Remove the "?"". Also, "To keep the field required" stays singular when the stop names two fields (`r7bg`). Should be: leave this step out when every field the stop names is a discriminator.

### Unclear text

4. **Low. The discriminator refusal with the base renamed names a field the origin does not have.** Reproduce (`r7jb`, source `r6jb`): "The documents hold their variant in "Job.type", which the plan removes: add --rename Task:Job --rename Job.type:Job.kind". The origin field is `Task.type`. The route works. Should be: "in "Task.type"".
5. **Low. A stop caused only by a `null` list element does not say what is wrong with the document.** Reproduce (`r7o1x`): as problem 2, with `line1 String?`. The stop says "This validator change changes what "addresses" and "home" accept. It has _id …. Find them all with …". When the same document also lacked `home.line1`, it added "and holds an element in "addresses" that is not an object". The query finds the document. Should be: say "It holds an element in "addresses" that is not an object" here too.

### Older text, outside this PR

6. **Low. The advice for a change of stored name only is false under `db update` on MongoDB.** Reproduce (`r7u1z`): following the stored-name chain refusal ("first rename the keys or fields to names nothing else uses; then rename them to their final names") with temporary `@map` names makes the second step a change of `@map` only. `db update` asks "User.fullName needs a statement" and offers only `--delete User.fullName`. `--rename User.fullName:User.fullName` says "With db update, rename it in the database yourself first, then run db update, which then finds nothing that loses data." Did that: `db update` still asks for `--delete User.fullName`. Answering it kept the data (the field it removes is already gone). This text is in `packages/1-framework/3-tooling/cli/src/control-api/statements/resolve-statements.ts` and this branch does not change it. Using temporary contract names instead (as `r7k3` does) avoids it.
7. **Low.** Two statement errors say "rows" on MongoDB: "A new model has no existing rows to backfill" and "every existing row has a value". Framework text, not changed by this branch.
