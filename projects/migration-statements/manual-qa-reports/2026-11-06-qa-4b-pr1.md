## Problems, ranked

### Data loss or data changed without the user expecting it

1. **`--delete` on `String` to `Boolean` turns `"false"` and `"no"` into `true`.** MongoDB's `$convert` makes every non-empty string `true`. I ran `db update --delete User.active` on documents holding `"false"`, `"true"` and `"no"`. All three became `true`. The question only says the cast "can change or lose its values". Nobody reading that expects `"false"` to become `true`. Postgres casts `'false'` and `'no'` to `false`, so this is also not "as on SQL". Suggest: treat string to bool as having no safe cast and offer only `--convert`, or name this in the question.

2. **A failed `db update` can leave documents that the current validator rejects, so the running app cannot update them.** Rewrites run before the document check. In `x1` I added a required `plan String` (filled with `""`) and a required `born DateTime` (no temporary value). The fill ran, then the document check stopped the apply. Every document now held `plan`, which the old validator (`additionalProperties: false`) does not allow. A plain `updateMany` to set `born` then failed with "Document failed validation", and so would every write the app makes to those documents. The same happens with a partial `--delete` cast (scenario 2: `"42"` became `42` while the validator still said `string`). The message says "The operations that ran before the failure stay applied", but not which ones, nor that the documents now fail the current validator. The temporary-value warnings ("Existing rows got "" ...") are not printed when the apply fails, so the user never learns that `plan` was set to `""`.

### Wrong or missing advice

3. **Fixing documents for a type change needs `bypassDocumentValidation`, and no message or doc says so.** Scenario 8: the advice is "Change them so they fit the new validator". The old validator is still in place and rejects the changed document, so the user's fix fails with "Document failed validation". It worked only with `{ bypassDocumentValidation: true }`. The same applies after problem 2. The error, the upgrade fragment and the skill reference should say it.

4. **`db update` advises editing a `migration.ts` that does not exist.** Every document check failure under `db update` says "or set checkDocuments to false on this operation in migration.ts". `db update` writes no file and always checks. The `nextActions` line, "Inspect the reported conflict, reconcile schema drift if needed, then re-run `prisma db update`", is generic and does not match the why.

5. **The W1 warning: no advice under `db update`, and no warning at all under `migration plan`.** `db update` prints `Field "Address.zip" of a value object changes type` with no `⚠` marker and nothing about adding a `dataTransform`. It prints after the apply step has already failed. `migration plan --from <origin>` for the same change prints no warning in text or `--json`. I checked the enum case too (`status String` to `status Status`): no warning from `migration plan`. That is the command where the user could add the `dataTransform`. The journey W1 covers only `db update`.

6. **The document check names the wrong cause when documents hold extra fields.** Adopting a Prisma 6 database (`s7a`, `s7c`): the check failed on a document holding `legacyScore`, which the closed validator rejects. The why said `This validator change makes "email" required. It has _id ObjectId("…")`. That document has an `email`. A user looks at the named field and finds nothing wrong. Extra fields are the most common reason a Prisma 6 database fails, so the message should say the new validator allows no fields the schema does not name.

7. **A required field under a unique index is refused by `db update` even on an empty collection.** `x3`: adding `handle String @unique` to a collection with no documents fails planning with "Cannot fill new required field ... a unique index covers it". A required `DateTime`, which has no temporary value either, is left to the document check, which passes on an empty collection. The unique case could do the same.

8. **The document check failure after making a field required does not mention `--backfill`.** Scenario 5: the message offers fixing documents or `checkDocuments: false`. `migration plan --backfill User.name` is the planned way and is not named. `migration plan` without `--backfill` plans the change silently.

9. **The `db migrate` cast failure's first advice is SQL-shaped.** `x7`: "`migration.ts` has no conversion for field "User.age": write one there". On MongoDB the file holds a `castField`; writing a conversion means replacing it with a `dataTransform` by hand, which nothing explains. The second advice (delete the directory and re-plan with `--convert`) is concrete and works.

10. **A scaffolded data transform whose update leaves values unconverted fails with a bare message.** `s1b`: I filled the slot with a `$convert` that keeps `"abc"`. `db migrate` said `Operation data_transform.User.age failed during postcheck` and `Fix the issue and re-run prisma db migrate --to <contract>`. No count, no `_id`, no query, and a literal `<contract>` the user cannot fill. The document check has all of these; the data transform check could reuse them.

### Unclear text

11. **`--delete User.age` reads as "delete the field".** The question lists `--convert User.age` and `--delete User.age` with no word on what each does. Only the why ("Cast field age ...") hints that `--delete` casts.
12. **"Existing rows got 0 in field ..."** MongoDB has documents, not rows. The advice says "instead" after the values are already written.
13. **A list is described as its element type.** `tags String[]` to `Int[]`: "Cast field tags in collection users from string to int". The cast itself was right (each element became an `int`).
14. **"makes "born" and "plan" required"** names `plan` after the fill already gave every document a `plan`. The docs say this lists what the change touches, not the cause, but it still sends the user to the wrong field.
15. **`Fix the issue and re-run prisma db migrate --to <contract>`** under `db migrate` (scenario 7): `--to <contract>` is not needed and the user does not know what to put there.
16. **"set checkDocuments to false on this operation in migration.ts"** does not give the path of the file or the operation's label. Under `db migrate` the error knows both.
17. **A variant's validator line reads `Update validator on tasks`** with no `(changed: …)` list, unlike root models.
18. **The placeholder slot does not say what shape it takes.** Both an update document (`{ $set: … }`) and an aggregation pipeline (`[{ $set: … }]`) worked. Neither the file, the skill reference nor the README says either is allowed.

## Per scenario

### 1. `User.age` `String` to `Int` through `migration plan`

Three documents: `"42"`, `"7"`, `"abc"`. `migration plan --from <initial>` refused:

> ✘ [CLI.CONSENT_REQUIRED] "User.age" needs a statement, and the session is not interactive. why: Cast field age in collection users from string to int would change the type of field "User.age" and can change or lose its values. → Run the command again with --convert User.age → Run the command again with --delete User.age

(Planning without `--from` failed with `MIGRATION.PLAN_ORIGIN_UNKNOWN`; that is older behaviour.) With `--convert User.age` the plan printed "Planned migration with placeholder(s)" and wrote one `dataTransform('User.age', …)` whose check and filter select `age` not of type `int`, with `placeholder('User.age:update')`, then `collMod` with `checkDocuments: true`. `ops.json` was `[]` until filled. Running `db migrate` unfilled refused with `MIGRATION.UNFILLED_PLACEHOLDER` and changed nothing. I filled it with `[{ $set: { age: { $convert: { input: '$age', to: 'int', onError: 0 } } } }]`, ran `node migration.ts`, and `db migrate` applied 2 operations. Every `age` was `$numberInt` (42, 7, 0). A further plan said "No changes detected". `db verify --schema-only`: "Schema matches contract". An update to every document succeeded. Pass.

### 2. `--delete` through `db update`

`db update` without a statement offered only `--delete User.age`, correct for a command with no file. `db update --delete User.age` failed:

> ✘ [MIGRATION.EXECUTION_FAILED] Operation field.users.age.cast(int) failed: a value of field "User.age" in collection users cannot be cast to int. why: MongoDB's $convert met a value ... Failed to parse number 'abc' ... Documents cast before that value stay cast, and a re-run casts the rest. → ... Plan the change with `prisma migration plan --convert User.age` ...

It names the field and what to do; the advice appears once. It does not give the `_id` of the failing document, nor say "or fix that value and re-run". After the failure `"42"` was already `42` under a `string` validator (problem 2). I changed `"abc"` to `"13"` and re-ran: both values became `int`, the validator changed, a further `db update` was empty and `db verify --schema-only` was clean. Pass, with problems 2 and 11.

### 3. `Int` to `Int64` through `db update`

No question. Output: `Cast field age in collection users from int to long`, then the validator. Both values read back as `$numberLong` (42, -7); `$type` gave `long`. Further `db update` empty, verify clean. Pass.

### New problems

**A. Wrong advice: the document check suggests `--backfill` for a field the plan refuses to backfill.** Prisma 6 adoption: the message says `To give "email" values you choose, plan the change with migration plan --backfill User.email`. Doing that fails with `MIGRATION.STATEMENT_UNRESOLVED`: `The field "User.email" is already required in the origin contract, so every existing row has a value. → Leave out --backfill User.email.` The origin is the Prisma 6 contract, which had no validator, so documents can lack `email` even though that contract says it is required. Either the check should not suggest `--backfill` here, or `--backfill` should accept it when the origin collection had no validator. The message also says "The old validator rejects a document changed to the new shape", which is not true when there is no old validator; harmless.

**B. Unhandled error: a new required unique field on a collection with documents.** Two documents, then `code String @unique` added through `db update`. The unique index is created before the document check, and its build fails because both documents have no `code`:

> ✘ [CLI.UNEXPECTED] Unexpected error. why: Unexpected error during db update: Index build failed: … E11000 duplicate key error collection: r4.users index: code_1 dup key: { code: null } → Check the error message and try again

Before the fix this was refused at planning with clear advice (`--backfill`). Now the user gets `CLI.UNEXPECTED`, and the document check, which would name the field and `--backfill`, never runs. The database was left unchanged apart from the index from the earlier step. With one document the index build would pass and the document check would catch it, so the failure depends on the document count. Suggest running the document check before index creates too, or keeping the planning refusal when the collection may hold documents.
