## Problems, ranked

### Data loss

None found.

### A state the user is not warned about

1. **The unique index is dropped when the failing collection has no rewrite of its own.** `m7` (`db update`) and `m8` (`migration plan` then `db migrate`): `Account.code` loses `@unique`, and `User` gains a required `born DateTime` with no temporary value, on collections with one document each. The plan is only `Drop index code_1 on accounts (code:1)` and `Update validator on users (added: born)`: there is no rewrite, so there is no early check. The drop ran, then the `users` validator change stopped on its own document check (`That document has no "born"`). Afterwards `accounts` had only `_id_`, and inserting a second `code: "A"` succeeded. So until the user fixes `users` and re-runs, the app can write duplicates that the index used to refuse. The message says only `The operations that ran before the failure stay applied`, without naming the drop.
   - The same happens on one collection (`m11`): `User.email` loses `@unique` and `User` gains a required `born DateTime`; the index is dropped, then the validator change stops.
   - When the failing collection does have a rewrite (`m9`: a new required `plan String`, filled, plus `born`), the plan starts with `Check that the documents in users can fit the new validator`, the check runs before `Drop index code_1`, and the index survives and still refuses the duplicate (`E11000 ... dup key: { code: "A" }`). So the change works when an early check exists; it does not cover a plan whose only document check is the validator change's own.
   - Suggested fix: when a plan drops an index (or does anything else before the validator changes), give every collection whose validator changes an early check, even with no rewrite. At least, name the operations that ran.

   In both `m7` and `m8`, after giving `born` a value the re-run applied the rest and verify was clean; the index stayed dropped, as the contract asks.
