## Findings

1. ⚠️ **F1 — A new required field silently gets a temporary value, and the plan output barely shows it.** Command: `prisma migration plan --name email --from <initial>` after adding `email String` to a table with 2 rows (scenario 6). Postgres output: `└─ Add column email to User`. The only hint is the DDL preview, `ADD COLUMN "email" text DEFAULT ('') NOT NULL`. SQLite output: `└─ Recreate table User`, and the DDL preview does not show the copy step at all, so `''` is not visible anywhere in the output. `db update` prints the same. Afterwards every old row has `email = ''`. A required `DateTime` gets `1970-01-01T00:00:00.000Z`, which an app can easily mistake for real data. This is the decided behaviour, but I expected a line such as `2 existing rows of "User" get '' in "email"; pass --backfill User.email to fill them yourself.`
2. ⚠️ **F2 — On SQLite the temporary value for a `Decimal` is an empty string.** Command: `prisma db update` adding `dec Decimal` (with other required fields) to a SQLite table with one row. `SELECT dec, typeof(dec)` → `""`, `text`. Read through the runtime client (`db.sql.User.select('dec')`) → `dec: ''`. Postgres gives `"0"` for the same field. An empty string is not a decimal. I expected `'0'`.
3. ⚠️ **F3 — On SQLite, a backfill that misses some rows fails with advice to use `--backfill`, which the user already did.** Command: `migration plan --name email --backfill User.email`, `run` filled with `` `UPDATE "User" SET email = 'x' WHERE id = 1` `` (one of two rows), `node migration.ts`, `db migrate`. Output:
   ```
   ✘ [MIGRATION.RUNNER_FAILED] "User" has 2 rows, so the new required column "email" cannot be added: it can be added to an empty table only.
     why: Operation recreateTable.User failed during execution: copy data from "User" to "_prisma_new_User": NOT NULL constraint failed: _prisma_new_User.email
   → The failed apply changed nothing. To keep the field required, copy any code you wrote in `…/20261012T1501_email/migration.ts`, delete `…`, and plan it again with `prisma migration plan --from 2d99… --backfill User.email` …
   ```
   Nothing changed. But the real cause is that 1 row still has no value after the backfill, and following the advice loops back to the same file. I expected: `1 row of "User" still has no value in "email" after the backfill; make the run step fill every row.` On Postgres the same mistake fails in the backfill's own check (`Verify backfill-User-email resolved all violations`, advice `Fix the issue and re-run …`), which is generic but points at the right step.
4. ⚠️ **F4 — For a new required unique field, the advice "give it a default" fails when followed.** Command: `prisma db update` adding `slug String @unique` to a Postgres table with 3 rows. Output: `"User" has 3 rows, so the new required column "slug" cannot be added … → Plan it with … --backfill User.slug … Or make the field optional, or give it a default.` With `@default("x")` added, `db update` fails: `Operation unique.User.User_slug_key failed during execution … could not create unique index "User_slug_key" → Inspect the reported conflict, reconcile schema drift if needed`. Nothing changed. For a unique field the default alternative should not be offered. The `--backfill` route works (scenario 8, both databases).
5. ⚠️ **F5 — `db migrate` on a migration whose placeholder is still unfilled gives a misleading error.** Command: `migration plan --name conv --convert User.age`, then `db migrate` straight away, without filling or running `migration.ts` (Postgres and SQLite). Output:
   ```
   ✘ [MIGRATION.RUNNER_FAILED] Database schema does not satisfy contract (1 failure)
     why: The resulting database schema does not satisfy the destination contract.
   → Fix the issue and re-run `prisma db migrate --to <contract>` — previously applied migrations are preserved.
   ```
   Nothing changed. The package has `ops.json` `[]` and a `migrationHash`, so it looks complete. This slice makes such packages more common. I expected: `migrations/app/…_conv has an unfilled placeholder (User.age:using); fill it and run node migration.ts.` Also seen when `node migration.ts` itself failed and I ran `db migrate` anyway.
6. ⚠️ **F6 — A hand-written `alterColumnType` with the old options fails with a JavaScript error.** Command: `node migrations/app/20261012T1459_hand/migration.ts` with `options: { qualifiedTargetType: 'int4', formatTypeExpected: 'integer', rawTargetTypeForLabel: 'int4', using: 'trim("age")::integer' }`. Output: `Cannot read properties of undefined (reading 'trim')`, exit 1. Nothing names the call or the new options. The upgrade fragment's detection (`qualifiedTargetType:`) would find the file, and an editor's type check would flag it. But someone who just runs the file gets no clue. The new form (`type: 'int4', using: …`) self-emitted, classed `data`, applied, and converted `' 12'` to `12`.
7. ⚠️ **F7 — Nothing tells a SQLite user what to write in the backfill `run` slot.** The written slot is `run: () => placeholder('User.email:run')`. The skill (`skills/prisma-8/references/migrations.md` lines 226–300) shows only the Postgres query-builder form; for SQLite it says only "`run` on SQLite". The app fragment says nothing either. The form that works, a closure returning a SQL string (`` () => `UPDATE "User" SET email = name || '@example.com' WHERE email IS NULL` ``), I found only in the journey test. With it, scenarios 7, 8 and 9 applied on SQLite. Smaller point on Postgres: `run` takes an array of closures, not a closure returning an array. My first try, `run: () => [..].map(...)`, failed at self-emit with `Cannot read properties of undefined (reading 'storageHash')`.
8. ⚠️ (minor) **F8 — The re-plan advice drops `--name` and is very long.** Example (scenario 4): `… delete \`/Users/…/s4pg/migrations/app/20261012T1452_age_to_int\`, and plan it again with \`prisma migration plan --from 4eb7… --convert User.age\` and the statements you planned it with before, except \`--delete User.age\`. Then write that code …` (about 90 words, two absolute paths). Followed as printed, it worked every time. But the new directory is named `…_migration`, and a second follow-up in the same minute fails with `MIGRATION.DIR_EXISTS` (clear message, nothing lost). Adding `--name <old slug>` to the printed command would avoid both.
9. ⚠️ (minor) **F9 — The plan says the statement has "no operations".** After `--convert` or `--backfill`, the output reads `Statements applied └─ convert field "User.age" (no operations)`. The docs say this is by design until the file is run. As a first-time user I read it as "the flag did nothing". Something like `(slot to fill in migration.ts)` would read better.
10. ⚠️ (minor) **F10 — The SQLite question does not say it is a type change.** Postgres: `Alter type of "User"."age" to int4 would lose the values of field "User.age".` SQLite: `Recreate table User would lose the values of field "User.age".` On SQLite the user has to guess why the table is rebuilt.
11. ⚠️ (minor) **F11 — The SQLite `migration.ts` for `--convert` does not read like hand-written code.** The slot `copyExpressions: { age: placeholder('User.age:using') }` sits at the end of a 40-line `recreateTable` call full of internal fields (`codecRef`, `schemaColumnNames`, `summary`, `postchecks`, `operationClass`). The Postgres file is short and reads well (`this.alterColumnType({ schema, table, column, type: 'int4', using: placeholder(…) })`).
12. ⚠️ (minor) **F12 — `--convert` and `--delete` on the same field give a misleading message.** Command: `migration plan --convert User.age --delete User.age`. Output: `[CLI.CONSENT_UNUSED] --delete User.age was given but nothing in this run asked about User.age. → Remove the flag, or spell the subject the way the command names it.` Something did ask; `--convert` answered it. Slice 2 already has the better wording for this case (`… was already answered by another flag. → Give one flag per question.`).
13. ⚠️ (minor) **F13 — `--delete` on a shorter `VarChar` cuts values instead of failing.** Command: `prisma db update --delete User.name` for `VarChar(20)` → `VarChar(3)` with `'alice'`. It applied, and the row is now `'ali'`. The user did consent to losing values, so this is not a blocker. But the skill and the fragment say "a value the cast cannot convert fails the apply", and a user may expect that here too. `VarChar(10)` → `VarChar(20)` planned with no question, as expected.
14. ⚠️ (minor) **F14 — `Int` → `String` is still asked as a loss.** Commands: `migration plan` after `years Int` → `years String` (Postgres and SQLite). Output: `Alter type of "User"."years" to text would lose the values of field "User.years". → --convert … → --delete …`. Every integer converts to text, so no value is lost. Same as slice 2 F14; now there is at least a route that does not say "delete".
15. ⚠️ (minor) **F15 — The advice names a baseline that has no placeholder.** In a project used only with `db update`, `migration plan --convert User.age` writes a baseline and a migration and prints `→ Replace each placeholder(...) call in migrations/app/…_baseline/migration.ts and migrations/app/…_migration/migration.ts`. The baseline has none.
16. ⚠️ (minor) **F16 — The NULL-row failure offers different alternatives on the two commands.** `db update`: `Set a value in those rows, or keep the field optional. Or plan it with … --backfill User.note`. `db migrate`: `Set a value in those rows and re-run \`prisma db migrate\`. Or … --backfill …` (no "keep the field optional"). Both counted correctly (`2 rows of "User" hold NULL in "note", so it cannot become required.`), and every route I followed (set the values and re-run, or `--backfill`) applied on both databases.

## Scenario notes

1. Postgres and SQLite: `CLI.CONSENT_REQUIRED`, `→ Run the command again with --convert User.age` / `--delete User.age`, exit 2, `migrations/` unchanged. JSON `meta.verbs: ["convert","delete"]`.
2. clack prompt `(convert User.age or delete)`; typing `convert` planned one slot on both databases. Postgres `migration.ts` reads well; SQLite see F11.
3. Postgres `using: 'trim("age")::integer'`, SQLite `'CAST(trim("age") AS INTEGER)'`, after setting `'abc'` to `' 7 '`. Both applied: `12`, `7` stored as integers. `db verify --schema-only` → `Database schema satisfies contract`. A further plan from the new migration → `No changes detected`.
4. Postgres: `invalid input syntax for type integer: "abc"`. SQLite: postcheck `The value 'abc' of column "age" on "User" is still stored as text, which INTEGER cannot hold.` Both through `migration plan` + `db migrate` and through `db update`. Rows and column types unchanged in all four. Each printed route ended in an applied conversion. In a `db update`-only project the advice has no `--from`, plans from the `db` ref with a baseline, and also worked.
5. `Alter type of "User"."name" to character varying(20)`, no question, applied, value kept.
6. Postgres: `addColumnWithTemporaryDefault({ …, temporaryDefault: "''" })`; column `NOT NULL`, no default left. SQLite: rebuild with `copyExpressions: { email: "''" }`; `NOT NULL`, no default. Both commands, both databases.
7. Postgres filled with the skill's builder pattern; SQLite with a SQL string (F7). Old rows got my values; column required.
8. Enum and unique fields: no temporary value, failure counts the rows (`"User" has 3 rows …`), nothing changed, the `--backfill` route applied on both databases.
10. Refused in 0.4 s with `MIGRATION.STATEMENT_NEEDS_MIGRATION_FILE`, nothing created. The printed `migration plan --from … --convert User.age` worked. Against `10.255.255.1` it was refused in 3.5 s with the same error, without `--from`.
12. Both fragments are clear. The `alterColumnType` fragment's before and after examples match what worked. The convert-backfill fragment is missing the SQLite `run` form (F7).
13. The skill leads to `--convert Model.field` and `using` in two places (lines 91 and 359) with the right syntax.
14. Also checked and fine: `--convert` on an unchanged field, a misspelled field, wrong case, `--backfill` on an already-required or still-optional field (each a clear `STATEMENT_UNRESOLVED`); `--convert` with `--rename` on both databases, with indexes on the renamed columns (indexes rebuilt and named correctly); a `;` in `using` or in a SQLite copy expression (`MIGRATION.SQL_EXPRESSION_INVALID`, clear).
