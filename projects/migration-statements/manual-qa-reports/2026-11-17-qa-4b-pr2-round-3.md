## New problems, ranked

### Wrong advice

1. **Medium. A discriminator rename together with a variant value change or a removed variant, planned without `--rename` of the discriminator, is refused instead of asked about, and the refusal's advice leads to a dead end.** Reproduce (`wip/qa-pr2/t10`): `Task` with `@@discriminator(type)`, variants `Bug` (`bug`) and `Epic` (`epic`); change to `kind String`, `@@discriminator(kind)`, `Bug` value `defect`. Run `prisma migration plan --name step --from <hash>` with no statement (the same through `db update`, and in `t8` with a removed variant instead of the value change). Seen:

   ```text
   ✘ [MIGRATION.PLANNING_FAILED] Migration planning failed
     why: Cannot plan the migration: the filter of one of its operations reads what another changes (Delete the documents of collection tasks whose kind is "bug"; Fill field kind in collection tasks where it is missing or null)
   → … Make the change in two migrations: first only "Fill field kind in collection tasks where it is missing or null" and apply that; then the rest.
   ```

   No question about `Task.type` appears, so the user never sees `--rename Task.type:Task.kind`. A user cannot plan "only" one operation; the closest is a contract that adds `kind` and keeps `type`. Done that way, migration 1 fills `kind` with `""` in every document. Migration 2 then asks about `Bug` (`--convert Bug`, whose filter `kind = "bug"` now matches nothing) and `Task.type` (`--rename 'Task.type:Task.<new name>'` or `--delete Task.type`). No offered answer keeps the variant values: answering `--convert Bug --delete Task.type` removed `type` from every document and the apply stopped at the validator because every `kind` is `""`. The variant of each document is lost. With `--rename Task.type:Task.kind` on the command line, every other statement is asked about correctly and the plan works (`t8`, `t7c`). With a discriminator rename alone (`t9`) the question offers `--rename Task.type:Task.kind`. Should be: ask about `Task.type` (offering `--rename Task.type:Task.kind`) before this refusal, or have the refusal say to pass `--rename Task.type:Task.kind`. I did not check whether this predates round 2.

### Unclear text

2. **Low. On MongoDB, the enum swap question under `db update` gives no `db update` route.** `t1`: with no migrations, the swap question says "make the change in two migrations: first move the stored values … to values the enum does not use, all in one migration". Postgres (`t1pg`) gives the two-run `db update` route for the same case. A MongoDB user who keeps the member names and moves only the values gets a second question that does give the two-run route, so they reach it in three runs instead of two. Should be: the MongoDB swap question under `db update` prints the same two-run route as Postgres.
3. **Low. The validator stop no longer names a missing key inside a value object.** `t3c` (`wip/qa-pr2/q1` documents: one document has `home: { zip: '9' }` after the rename): "This validator change makes "home.line1" required and changes what "addresses" and "home" accept. It has _id …". Nothing says this document lacks `home.line1`; round 2 said so for the same document. Top-level fields are still named ("That document has no "title"", `t7b`). The first sentence is enough to find the cause, so this is minor. Should be: "That document has no "home.line1"."
4. **Low. Two smaller wording points.** (a) Under `db update`, each member of the enum gets its own copy of the two-run route; with two members the two next actions are the same text with the members in a different order (`t1`, `t1pg`). One is enough. (b) Enum chain with no statement (`u12a`: `ACTIVE` takes `"archived"`, `ARCHIVED` becomes `RETIRED = "retired"`): the question asks only about `Status.ACTIVE` and offers only `--delete Status.ACTIVE`, with no way to keep its data and no mention of `--rename Status.ARCHIVED:Status.RETIRED`. Adding that rename gives the two-migration advice. This was the same in round 2.
