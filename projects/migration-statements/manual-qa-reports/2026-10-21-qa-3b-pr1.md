## Findings

1. ⚠️ **F1 — A namespace renamed in this run is still offered as `--delete` and as the same `--rename`, and the CLI accepts both together.** Rollback of a namespace rename: `migration plan --from <rename_ns> --to <rename_ns>^ --rename finance:billing`. Output:
   ```
   ✘ [CLI.CONSENT_REQUIRED] "finance.Bill" needs a statement, and the session is not interactive.
     why: Drop table "Bill" would lose the data of model "finance.Bill".
          --delete finance answers every question about namespace "finance", which the destination contract no longer has.
          If namespace "finance" was renamed, --rename finance:billing renames it instead.
   ```
   The user already gave `--rename finance:billing`. Following the other hint, `--rename finance:billing --delete finance`, is accepted and plans `ALTER SCHEMA … RENAME`, then `DROP TABLE "billing"."Bill"` and an empty `Invoice`. The same two hint lines appear in `db update --rename billing:finance` when a model inside also changes (journey contracts). I expected: no namespace hints for a namespace the run renames; the question should offer `--rename finance.Bill:billing.Invoice`; and `--rename X:Y` with `--delete X` refused as contradictory.
2. ⚠️ **F2 — The hints offer namespace renames that are always refused.** Removing `public` (journey `public-renamed`): `If namespace "public" was renamed, --rename public:app renames it instead.` That statement is refused (`"public" is the default schema of every Postgres database`). Moving every model from `billing` into `public`: `If namespace "billing" was renamed, --rename billing:public renames it instead.`, also refused. Each refusal's own advice then works, so nothing is lost, but the first hint is a dead end. The same `public` question also says `--delete public answers every question about namespace "public", which the destination contract no longer has`, while the spec says `public` is never a removed namespace. (`--delete public` there does drop `User` and keeps the schema.)
3. ⚠️ **F3 — In a terminal, the namespace answers printed in the prompt cannot be typed into it.** `db update` in a pty after renaming `billing` to `finance`:
   ```
   ◆  Drop table "Receipt" would lose the data of model "billing.Receipt".
   --delete billing answers every question about namespace "billing", which the destination contract no longer has.
   If namespace "billing" was renamed, --rename billing:finance renames it instead. (rename billing.Receipt:<new name> or delete)
   ```
   Typing `rename billing:finance` → `The rename's old name is not "billing.Receipt". Write it as billing.Receipt:<new name>.` Typing `delete billing` → `delete names "billing.Receipt": --delete billing.Receipt.` Nothing changed. The prompt should either accept them or say to quit and re-run with the flag.
4. ⚠️ **F4 — A view that depends on a table in the removed namespace fails the table drop with Postgres's message only.** `create view billing.v_paid as select id from billing.audit_log`, then `db update --delete billing --delete billing.audit_log`. The dry run is clean. The apply:
   ```
   ✘ [MIGRATION.RUNNER_FAILED] Operation dropTable.audit_log failed during execution: drop table "audit_log"
     why: cannot drop table billing.audit_log because other objects depend on it
   → Inspect the reported conflict, reconcile schema drift if needed, then re-run `prisma db update`
   ```
   Rolled back; rows kept. Same with a view over a declared model's table (`dropTable.Invoice`). The F04 fix names objects only for the schema drop. The view's name, and "drop or move it yourself", are missing here. The app fragment says a view makes the schema drop fail, which is not what happens in this case.
5. ⚠️ **F5 — One model with two access questions needs `--allow` twice, and after one the advice repeats it.** Removing `@@rls` and the policy from `Invoice`, `db update`: `2 subjects need a statement …: "Invoice", "Invoice"`, with `→ Run the command again with --allow Invoice` printed twice. `db update --allow Invoice`:
   ```
   ✘ [CLI.CONSENT_REQUIRED] "Invoice" needs a statement, and the session is not interactive.
     why: Drop RLS policy "invoice_read_53c2831c" on "Invoice" would change who can read and write its data.
   → Run the command again with --allow Invoice
   ```
   Only `--allow Invoice --allow Invoice` applied. Probably older than this PR, but the PR changed this question. The wording itself is right: "would widen" for disabling RLS, "would change" for dropping a policy; `--dry-run --json` has `accessChanges` and no `accessWidening`.
6. ⚠️ (minor) **F6 — A duplicate answer gets a self-contradicting message.** `db update --delete billing --delete billing.Invoice` (removed namespace):
   ```
   ✘ [CLI.CONSENT_UNUSED] --delete billing.Invoice was given but nothing in this run asked about billing.Invoice.
     why: The run asked about billing.Receipt, billing.Invoice.
   ```
   With the order reversed it says nothing asked about `billing`. Expected the slice 2 wording: `… was already answered by --delete billing. → Give one flag per question.` Nothing changed.
7. ⚠️ (minor) **F7 — After a move, access questions use the old model name and field questions the new one.** Moving `billing.Invoice` to `finance.Invoice` while dropping its policy asks `--allow billing.Invoice`; `--allow finance.Invoice` answers no question. In the same kind of run, a dropped field is asked as `finance.Invoice.number`. Both work as printed, but a user who just moved the model will guess the new name.
8. ⚠️ (minor) **F8 — "rename model "Invoice" to "Invoice"".** Origin only `namespace billing { Invoice }`, destination `public { Invoice }`, `db update --rename billing.Invoice:Invoice`. Statements applied: `└─ rename model "Invoice" to "Invoice" (1 operation)`. Reads as a no-op; it moved the table. Expected qualified names.
9. ⚠️ (minor) **F9 — A meaningless planner warning on most multi-namespace runs.** `⚠ Planner warnings - control policy suppressed: namespace "__unbound__" — namespace '__unbound__' has effective control 'external' but declared 'external'`. Also in `--json` `warnings[]`. The system design review referred this; it is still there.
10. ⚠️ (minor) **F10 — The access-rename app fragment's `jq` example prints `null`.** `upgrade-instructions/pending/access-changes-rename/app/instructions.md` says `jq '.accessChanges'`. `prisma db update --dry-run --json | jq '.accessChanges'` prints `null` on every line; the key is at `.envelope.result.accessChanges` on the last line.
11. ⚠️ (minor) **F11 — The namespace app fragment does not mention renaming a namespace.** `namespace-statements/app/instructions.md` tells a user whose `namespace` block disappeared to `--delete <namespace>` or move models one by one. A user who renamed the block, and reads only this, deletes their data. One sentence on `--rename billing:finance` would fix it. The extension fragment is clear and matches the code.
12. ⚠️ (minor) **F12 — The dry run hides the namespace answers.** `db update --dry-run` for a removed or renamed namespace lists `An apply asks about … --delete billing.Receipt` per model, with no `--delete billing` and no `--rename billing:finance`. Its last line, `→ Apply the planned operations: prisma db update`, is refused when run. The last part is probably older than this PR.
13. ⚠️ (minor) **F13 — Script author view of `--json`.** `appliedStatements[].statement` for a namespace has `from: "billing"`, a string, while a model has `from: { namespaceId, model }`. `dataLoss[].answered: true` does not say which flag answered it, and `CLI.CONSENT_REQUIRED` `nextActions` and `meta.unanswered` never contain `--delete billing`. The last two are the deferred review item S04.
14. ⚠️ (minor) **F14 — Leftover generic wording.** The blocked schema drop still ends `→ Inspect the reported conflict, reconcile schema drift if needed`. The F06 refusal's why line says `the schema being planned from already has a namespace "finance"`. In the removed-namespace question the `--delete billing` line sits between the first and second model's lines, and says it answers "every question" even when an undeclared table's question is not answered by it.

Not testable from the CLI: the spec's "one-name statement that is both a namespace and a model" edge case. PSL refuses a model and a namespace of the same name (`PSL_DUPLICATE_DECLARATION: Duplicate declaration of "billing"`). Names with quotes are not valid PSL identifiers; the code review covered them through TypeScript.
