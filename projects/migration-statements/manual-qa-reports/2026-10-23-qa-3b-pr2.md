## Findings

1. ⚠️ **F1 (medium) — A member-only rename through `db update` is not recorded, so later questions use the old member name.** Postgres, `Status { OPEN, CANCELLED = "cancelled" }` in the database. Contract `VOIDED = "cancelled"`; `db update --rename Status.CANCELLED:Status.VOIDED` prints `rename enum value … (no operations)` and `Advanced ref "db"`. Then remove `VOIDED` and run `db update`:
   ```
   ✘ [CLI.CONSENT_REQUIRED] "public.Status.CANCELLED" needs a statement …
   ```
   `--delete Status.VOIDED` → `answers no question; the questions are about public.Status.CANCELLED`. The storage hash does not change, so `migrations/snapshots/<hash>/contract.json` keeps `CANCELLED`. The arrows still work, so nothing is lost. But it also breaks the two-step route a user would try for F2: `--rename Status.DONE:Status.OLDDONE` applies, then `--rename Status.OLDDONE:Status.DONE` is refused with `this rename has already happened. For db update, the database is already at the new name`, which is false.
2. ⚠️ **F2 (medium) — Under `db update` with no migrations, a member that keeps its name with a new stored value has only the lossy answer.** Contract `DONE = "done"` → `DONE = "finished"`, rows hold `done`:
   ```
   why: … db update cannot keep that data, and no migration ends at the contract the database is at, so `prisma migration plan` cannot plan the change from it.
   → Run the command again with --delete Status.DONE
   ```
   The only arrow sets `done` to NULL and takes it out of lists. Nothing says how to keep the data. With migrations present, the safe route is in the `why` text and the arrow is still `--delete`; a reader who follows arrows loses data.
3. ⚠️ **F3 (medium) — A rename that shifts values is refused, and its advice leads to deleting.** SQLite `Int` enum `{ Low = 0, Higher = 3, Max = 4 }` → `{ Low = 0, A = 4, B = 5 }`, `db update --rename Prio.Higher:Prio.A --rename Prio.Max:Prio.B`:
   ```
   why: Cannot rename enum value "Prio.Higher" to "Prio.A": the origin enum already stores "4", as enum value "Prio.Max"
   → A rename changes "3" to "4" in every row that holds it, which merges its data with the data of "Prio.Max". Leave out this statement. To merge them on purpose, plan the change with migration plan and write this.replaceStoredValue(...) in the migration.ts it writes.
   ```
   Nothing merges: `Max` moves to 5 in the same run. "Leave out this statement" makes the next run ask about `Prio.Higher`, whose only working answer is `--delete`. The working route (two runs: rename `Max` first) is not mentioned. The integers are quoted (`"4"`, `"3"`), unlike the F08 fix. "plan the change with migration plan" has no command (no `--from`, no invocation).
4. ⚠️ **F4 (medium) — Swapping two members' stored values is planned silently.** Origin `ACTIVE = "active"`, `OLD = "old"`; destination `ACTIVE = "old"`, `OLD = "active"`. `migration plan` with no statement plans only the check drop and add. No question. Every row that was `ACTIVE` now reads as `OLD` and the other way round. This is the "kept name, new stored value" case, which the spec says is asked; it is not asked because each stored value still exists under another member. `--rename` for the swap is refused with the three-plan advice written for models.
5. ⚠️ **F5 (low) — "Run that migration.ts with the `node` command `migration plan` prints", but `migration plan` prints none.** Every kept-data advice says this. `migration plan` prints a `node` command only when the file has placeholders; none of these runs did. I guessed `node migration.ts` in the directory. The `db migrate` variant prints the command (`run \`node migrations/app/…/migration.ts\``), so the fix is to print it in the others too.
6. ⚠️ **F6 (low) — The required-column failure reports one column at a time.** `task.status` and `note.state` both required, both hold `archived`. `db migrate` names `note.state`; after following the advice it fails again on `task.status`. Known and deferred (system design S06); confirmed here.
7. ⚠️ **F7 (low) — The `db update` "rename to a new member" action drops the user's other statements.** `db update --rename Prio.High:Prio.Higher --delete Prio.Top` failed on `Prio.Top`. The action printed `prisma db update --rename 'Prio.Top:Prio.<new member>'`. Run as printed, it asks about `Prio.High` again. The `db migrate` version says "adding any other statements you planned it with"; the `db update` version does not. Also: "db update cannot keep that data in a migration.ts" reads oddly, since `db update` never writes one.
8. ⚠️ **F8 (low) — Wrong statements say what was searched but not what to type.** `--rename Prio.OLD:Prio.RETIRED` (no such enum): `the origin contract has no enum "Prio"` with no list of enums. `--rename status.OLD:status.RETIRED` (wrong case): no hint that `Status` exists. `--rename Status.OLD:RETIRED`: `The destination contract has no model "RETIRED"`, with no hint to write `Status.RETIRED`. Each why also lists the `namespace.Model` and `Model.field` readings, which is noise for an enum. The arrow is the generic "The old name must exist in the origin contract …" in all of them. `--rename Status.OLD:Status.RETIRED --delete Status.OLD` gives `CONSENT_UNUSED … spell the subject the way the command names it`, which does not say the two flags contradict.
9. ⚠️ (minor) **F9 — The question names one column.** `why: Remove value "archived" from column "tags" of "task" would lose enum value "Status.ARCHIVED" …` when three columns in two tables hold it. A user may think only `tags` is affected. The rename offer is `Status.<new name>` even when the destination has exactly one new member (`RETIRED`).
10. ⚠️ (minor) **F10 — The dry run lists the same answer once per column, and leaves deletes out of `Statements applied`.** `An apply asks about` repeats `--delete Status.ARCHIVED` for each column. `db update --dry-run` lists only renames under `Statements applied`; the apply then lists `delete enum value "Status.ARCHIVED"`.
11. ⚠️ (minor) **F11 — `db update --dry-run --json` leaves the delete out of `appliedStatements`; `migration plan --json` includes it.** Same statements (`--delete Prio.Higher --rename Status.RETIRED:Status.GONE`): plan has two entries (`verb: "delete"`, `operationIndexes: [6, 7, 8]`), dry run has only the rename. A script that reads `appliedStatements` gets different answers.
12. ⚠️ (minor) **F12 — `meta.rowsHoldingValue.enumValue` carries `"namespaceId": "__unbound__"` on SQLite.** `appliedStatements` coordinates in the same project omit `namespaceId`, as the README says they do. The failure meta does not.
13. ⚠️ (minor) **F13 — The extension fragment leaves out two new fields.** `upgrade-instructions/pending/enum-value-statements/extension/instructions.md` covers the `enumValue` statement and subject. It does not mention `MigrationRunnerFailureMeta.rowsHoldingValue` or `MigrationDataLoss.keepDataEdit`, which the PR text lists as extension changes. A target author does not learn to report them. The app fragment is clear and matches what I saw; it does not mention the merge refusal (F3) or `--from`.
14. ⚠️ (out of scope, pre-existing) **F14 — `db migrate` silently applied an older migration with the same endpoints.** In one project I planned back to an earlier contract, so a new migration `dropretired` had the same from and to hashes as an older, unapplied-path migration `byhand`. `db migrate` applied `byhand` (its hand-edited calls ran), left `dropretired` unapplied, and `migration status` said `Up to date`. Nothing warned when `migration plan` wrote a second edge between the same two contracts. Not this PR, but it ran hand-written data edits the user did not choose.

Not testable from the CLI: an enum and a model of the same name (`PSL` refuses the duplicate declaration), and an enum inside a `namespace` block (`PSL_ENUM_NAMESPACE_NOT_SUPPORTED`). `public.Status.OLD:public.Status.RETIRED` works.
