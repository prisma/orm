## Problems, ranked

### Data loss

None found. No run lost or changed a value the user had not agreed to.

### Wrong advice, or a state the user is not warned about

1. **A `--delete` cast that fails part way leaves documents the old validator rejects.** Scenario 2: `--delete User.age` failed on `"abc"` after it had already cast `"42"` to `42`. The validator still said `string`, so a plain update to that document failed with "Document failed validation" until the re-run finished. The same happened with a variant cast (`x2`). The message says "Documents cast before that value stay cast", but not that those documents now fail every update. A running app writing to them gets errors until the user fixes the bad value and re-runs. The early document check cannot know that `$convert` will fail on a value, so this is a known limit, not something the check could catch. Suggest adding one sentence: until the command finishes, documents already cast fail their updates.
2. **The advice says the old validator rejects the fixed document when it does not.** Scenario 5 (optional field made required) and the Prisma 6 skill text both say an update that fixes a document must skip validation. In scenario 5, setting `name` to a string is accepted by the old validator (which allows `name` as an optional string). A Prisma 6 database has no validator at all. A plain update worked in both. The bypass form also works, so following the advice never fails, but the reason given is wrong for these cases. The `db update` and `db migrate` error text for the Prisma 6 case no longer says this; only the skill reference (`skills/prisma-8/references/migrations.md`, the "Adopting a Prisma 6 MongoDB database" item) still does.
3. **The skill reference says MongoDB refuses a field whose stored name contains `.`, but nothing refuses it.** See problem 4.

### Unclear text

4. **A type change on a field stored with a dot in its name is neither asked about nor refused.** `x4`: `zip String @map("addr.zip")` changed to `Int`. `contract emit` and `db update` accepted the field. The type change asked no question; `--delete User.zip` failed with `CLI.CONSENT_UNUSED`, saying nothing asked about it. The document check then stopped the apply, with a correct cause (`holds a value of type string in "addr.zip"`). No data harm. But the user has no statement to answer it with, and the skill reference says such a field is refused with advice. Such a field is hard to use at all (a document holding a top-level `"addr.zip"` key fails the validator even when it fits, which is older behaviour), so this is low priority.
5. **The applied-operation count can be lower than the list.** `x5`, on an empty collection: `Applied 3 operation(s)` above a list of four (check, fill, index, validator). On a collection with documents the counts matched.

## Per scenario

### 1. `User.age` `String` to `Int` through `migration plan`

Three documents: `"42"`, `"7"`, `"abc"` (an ordered insert also left the same three again). `migration plan --from <initial>` refused with `--convert User.age` and `--delete User.age`. With `--convert` it planned `Check that the documents in users can fit the new validator`, `Data transform: User.age` and the validator. The file's `checkDocuments(...)` names `rewrittenFields: ['age']`; the data transform has its check and filter written, and `placeholder('User.age:update')`. `db migrate` before filling refused with `MIGRATION.UNFILLED_PLACEHOLDER`, changing nothing. After filling with a `$convert` pipeline (`onError: 0`) and running the file, `db migrate` applied 3 operations; every `age` was an `int` (42, 7, 0). A further plan: "No changes detected". `db verify --schema-only`: "Schema matches contract". An update to every document succeeded.

### 2. `--delete` through `db update`

Without a statement: `--delete User.age` only (no file, so no `--convert`). With it:

> ✘ [MIGRATION.EXECUTION_FAILED] Operation field.users.age.cast(int) failed: a value of field "User.age" in collection users cannot be cast to int. why: MongoDB's $convert met a value ... Failed to parse number 'abc' ... Documents cast before that value stay cast, and a re-run casts the rest.

The advice to plan with `--convert` appears once. Problem 1 applies. After I changed `"abc"` to `"13"` with a plain update, the re-run listed the check, the cast and the validator; both values were `int`; a further `db update` was empty; verify clean. Pass.

### 3. `Int` to `Int64` through `db update`

Nothing asked. The check, `Cast field age in collection users from int to long`, and the validator. Values read back as `$numberLong` (42, -7). Further update empty, verify clean. Pass.

### 4. New required fields through `db update`

Stored: `""`, `$numberLong 0`, `false`, `$numberInt 0`, `$numberDouble 0.0`, `[]`. One temporary-value line per field. Further update empty, verify clean. Pass.

### 5. Optional field made required through `db update`

Four documents: one with `name`, two without, one with `null`. Stopped: `3 documents ... do not fit the new validator`, `That document has no "name"`, the query, `To give "name" values you choose, plan the change with migration plan --backfill User.name`, the bypass update form, and `db update writes no migration.ts, so there fix the documents first`. The printed filter found exactly the three. After a plain update the re-run applied; verify clean. Pass (problem 2 is about this message's reason).

### 6. `--backfill` through `migration plan`
