## Findings

### F1 ⚠️ A field rename or removal on a time-series collection is not refused; `db update` fails with an unexpected error

TypeScript contract, model `Reading` on time-series collection `readings` (`timeField: 'ts'`, `metaField: 'meta'`), field `value` renamed to `reading`.

```text
$ prisma db update --no-interactive --rename Reading.value:Reading.reading
✘ [CLI.UNEXPECTED] Unexpected error
  why: Unexpected error during db update: Cannot perform an update or delete on a time-series collection when querying on a field that is not the metaField 'meta'
→ Check the error message and try again

$ prisma db update --no-interactive --delete Reading.value
✘ [CLI.UNEXPECTED] Unexpected error
  why: Unexpected error during db update: Cannot perform an update or delete on a time-series collection when querying on a field that is not the metaField 'meta'
```

Without a flag the command asks about `Reading.value`. So no answer works, and the user cannot remove a field from a time-series model at all. Before this slice that removal went through silently. No documents changed.

Expected: a planning refusal with a reason, as for the collection rename (`collection "readings" is a time-series collection`). The app fragment and `skills/prisma-8/references/migrations.md` both say statements refuse a time-series collection. This may overlap the pending decision about TypeScript contracts without a validator, but that decision is about `migrate`; this failure is in `db update`.

### F2 ⚠️ A rename precheck failure does not say what is wrong, and the earlier index drop stays applied

A document holds both `name` and `fullName` (written outside Prisma). Unique index on `name`.

```text
$ prisma db update --no-interactive --rename Profile.name:Profile.fullName
✘ [MIGRATION.RUNNER_FAILED] Operation field.profiles.name.rename(fullName) failed during precheck
  why: Migration runner failed
→ Inspect the reported conflict, reconcile schema drift if needed, then re-run `prisma db update`
```

The data is safe: no value was overwritten. But the message does not say that a document already holds `fullName`, or which one. The JSON adds only `runnerErrorCode: MIGRATION.PRECHECK_FAILED`. The unique index `name_1` was dropped before the precheck failed and is still gone.

Expected: the reason ("1 document in `profiles` already holds `fullName`") and what to do.

### F3 ⚠️ A repeated `db update` reports stale statements one at a time

After a successful `db update --rename Profile:User --rename User.name:User.fullName --delete User.nickname`, the same command again:

```text
✘ [MIGRATION.STATEMENT_UNRESOLVED] Cannot resolve statement "--rename Profile:User"
  why: The origin contract already has "User" and has no "Profile", so this rename has already happened. ...
→ Leave out --rename Profile:User.
```

Without it, the next run names `--rename User.name:User.fullName`; without that, `CLI.CONSENT_UNUSED` names `--delete User.nickname`. Three runs to learn the three flags to drop. Each message is clear. Expected: all stale statements in one error.

### F4 ⚠️ Dotted field name: the rename refusal's advice is incomplete

PSL accepts `nick String? @map("a.b")`. The ORM cannot write it (`Document failed validation`), so data only gets there from outside Prisma. With a document holding `"a.b": "bobby"` and the map changed to `"c"`:

```text
$ prisma db update --no-interactive --rename Profile.a.b:Profile.c
✘ [MIGRATION.PLANNING_FAILED] Migration planning failed
  why: Cannot rename field "Profile.a.b" to "Profile.c": the stored field name "a.b" cannot be rewritten
→ MongoDB reads a name containing "." as a path into embedded documents, so a statement cannot move its values. Rename it in the database yourself, or leave out this statement.
```

If you leave the statement out, the plan updates the validator (`removed: a.b`) without asking. The values stay in the documents, so those documents then fail every update. "Rename it in the database yourself" gives no steps, and `$rename` cannot target a literal dotted name. Low impact because Prisma cannot write such a field.

### F5 ⚠️ Following the time-series rename advice drops MongoDB's automatic index

```text
→ MongoDB cannot rename a time-series collection. Leave out this statement. To keep the documents, first create collection "samples" yourself with the same time-series options and copy them into it; the plan then drops "readings" once --delete names the model.
```

Followed as printed: created `samples` with the same options, copied 2 documents, ran `db update --delete Reading`. Documents kept. The plan also ran `Drop index on samples (meta:1, ts:1)`. MongoDB creates that index automatically for a time-series collection with a `metaField`. Not data loss, but slower queries after following the advice.

### F6 ⚠️ The question for a base field moved to a variant shows a raw MongoDB filter

```text
◆  Remove field note from collection tasks where {"kind":{"$nin":["bug"]}} would lose the values of field "Task.note". (rename Task.note:Task.<new name> or delete)
```

The same text is in the plan list and in scenario 5 (`where {"kind":"bug"}`). The result is correct: `Feature` documents lose `note` (or get `remark`), `Bug` documents keep it. Expected plain words, for example "in documents that are not `Bug`".

### F7 ⚠️ Changing only a model's `@@map` offers only `--delete`

`model Profile { … @@map("profiles") }` changed to `@@map("people")`:

```text
✘ [CLI.CONSENT_REQUIRED] "Profile" needs a statement, and the session is not interactive.
  why: Drop collection profiles would lose the data of model "Profile".
→ Run the command again with --delete Profile
```

Followed as printed, this drops the documents (with the user's consent). The way to keep them is in the skill (item 8: hand-edit `renameCollection(...)` into `migration.ts`). I did that: plan with `--delete Profile`, replace the operations with `renameCollection('profiles', 'people')`, self-emit, `db migrate`. Documents kept. Expected: the CLI says how to keep the documents, as the skill does.

### F8 ⚠️ The no-snapshot "why" packs three numbered steps into one line

```text
  why: Remove field nickname from collection profiles would lose the data in "profiles.nickname", named by its storage name because the origin contract is unknown; --delete loses that data. If it was renamed, keep its data instead: store the snapshot of the contract the database is at, then run this command again and answer with --rename. 1. Put the contract source back ... 2. Run `prisma db update --advance-ref <name> --dry-run` ... 3. Put the new contract source back ...
```

The steps are correct (I followed them and `--rename Profile.nickname:Profile.alias` moved the values). They are hard to read as one paragraph of about 900 characters.

### F9 ⚠️ A plain `system.x` collection gets an unexpected error

The rename onto `system.x` is refused clearly. But `db update --delete Profile` for the same change fails with:

```text
✘ [CLI.UNEXPECTED] Unexpected error
  why: Unexpected error during db update: Invalid system namespace: s8h.system.x
```

No documents lost: the create fails before the drop. Probably outside this slice.

## Notes outside the slice

- `db migrate` did not advance the `db` ref (`advancedRef: null`), so the next `migration plan` failed with `MIGRATION.PLAN_ORIGIN_UNKNOWN` until `migration ref set db <dir>`. `db update` advances it.
- Without a `package.json` that lists `@prisma/orm-mongo`, `migration.ts` imports `@internal/target-mongo/migration` and cannot self-emit. With one it imports `@prisma/orm-mongo/target/migration`. This came from my scratch setup, not from the slice.
