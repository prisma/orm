## New problems, ranked

### Wrong advice

1. **Low. When a removed variant's discriminator value is taken by another variant, the plan-wide refusal offers renames that cannot resolve.** Reproduce (`wip/qa-pr2/u1a`): `Task` with variants `Bug` (`bug`, field `severity`) and `Epic` (`epic`); remove `Bug` and give `Epic` the value `bug`. `prisma migration plan --name step --from <hash>` with no statement, or with `--delete Bug`, or with `--delete Bug --delete Bug.severity --delete Epic`. Seen: "The plan holds changes that no --rename or --convert statement carries: field "Bug.severity", which the plan removes; model "Bug", whose documents the plan deletes; model "Epic", whose documents the plan deletes. To keep their data, plan again with: --rename 'Bug.severity:Bug.<new name>'; --rename 'Bug:<new name>'; --convert Epic." The destination has no model `Bug`, so `--rename Bug.severity:Bug.level` fails with "The destination contract has no model "Bug"", and `--rename 'Bug:<new name>'` can only work if the user adds a model. The plain question for a removed variant does not ask about its fields at all (`g1`: only "Story" is asked). Nothing is written and no data is lost; `--convert Epic` leads to a refusal whose two-migration route works (`h2`). Should be: leave fields of a removed model out of the list, as the plain question does.

### Unclear text

2. **Low. Under `db update`, the enum chain question still gives the two-migration route before the `db update` one.** `q5c` (`u12a` with `--rename Status.ARCHIVED:Status.RETIRED`, `db update`): the why says "To keep that data, make the change in two migrations: … in a second. MongoDB applies … db update cannot keep that data in one run, and --delete Status.ACTIVE removes it." and then gives the two-run route. The route works. The swap question was fixed this way in round 4 problem 3(b); the chain question was not. Should be: under `db update`, give only the two-run route, as the swap question now does.
3. **Low. Smaller points.**
   - (a) The discriminator refusal says "add --rename Task.type:Task.kind to keep it, and plan again" under `db update` too (`a2`, `f1`), where the user runs `db update` again, not a plan. It also does not acknowledge a `--delete Task.type` the user passed (`c1`, `c8`); it just repeats the rename.
   - (b) When the old discriminator is removed, the refusal offers only the rename, though `--backfill Task.kind --delete Task.type` also works under `migration plan` (`d4`: I filled the slot with `[{ $set: { kind: '$type' } }]` and every variant was kept). When the old field is kept (`t9k`), it offers `--backfill Task.kind` under `db update` too, which `db update` then refuses and sends to `migration plan --from <hash>`; two steps, but it works.
   - (c) `--backfill Task.kind` alone with a variant value change (`c4`) is refused with "Cannot delete the documents of variant "Bug"", though the user asked nothing about `Bug`. The advice (add the rename) is right.
   - (d) With a variant value change and a variant field removed (`k1`), the field question says "Remove field severity … in documents whose type is "defect"" before any `--convert`; with `--delete Bug` it still asks about `Bug.severity`, and then plans a removal that has nothing to do (`k1x`). Harmless.
