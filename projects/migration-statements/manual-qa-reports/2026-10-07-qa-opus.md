## Findings

1. 🛑 **F1 — The `--db` error offers "run the command without statements", which drops the table and its rows.** Command: `prisma db update --db <path> --rename Profile:User` (scenario 4). Output ends with `→ Or run the command without statements`. Following it: `prisma db update --db <path> --dry-run` plans `⚠ Drop table Profile` (and `Recreate table Post`). Only the consent prompt stands between this advice and lost rows, which is the exact failure this project exists to remove. The advice should say that the plan drops the table and its rows, or not be offered. Rated a blocker because it is the CLI's own advice leading to data loss; downgrade if a consent prompt is judged enough.
2. ⚠️ **F2 — The `--db` error does not say why the old contract is unknown, and its `--advance-ref` advice reads as "add it now", which does not help.** Same command. The `why` names the hash and directory but not the cause (the earlier `db update --db` run kept no snapshot because no ref was advanced). Re-running with `--advance-ref db` now fails identically. `→ Plan from an explicit origin: prisma migration plan --from <contract>` does not apply: there is no migration or snapshot to name. The route that works, and that I verified, is not described: restore the old contract, `contract emit`, `db update --db <path> --advance-ref <name>` (a no-op that stores the snapshot), restore the new contract, emit, then `db update --db <path> --rename … --advance-ref <name>`. The app upgrade instructions do say "pass `--advance-ref <name>` on the run before the rename"; the error should say the same.
3. ⚠️ **F3 — The MongoDB field-rename advice does not work, and a user following it ends with half-moved documents.** Command: `prisma db update --rename User.name:User.fullName` on a Mongo project whose `name` is `@unique`. Advice: run `db.getCollection("User").updateMany({}, { $rename: { "name": "fullName" } })`. On a clean database that command fails with `Document failed validation` (`additionalProperties: [ 'fullName' ]`, `missingProperties: [ 'name' ]`) because of the validator Prisma installed. With validation bypassed it fails with `E11000 duplicate key … index: name_1 dup key: { name: null }` after moving one document. Applying the plan first instead fails with `E11000 … index: fullName_1 dup key: { fullName: null }` after dropping `name_1`. No document was lost, but the end state is `[{"handle":"al","fullName":"alice"},{"name":"bob",…},{"name":"carol",…}]` with no index on either field. The advice also does not say whether to move documents before or after applying the plan (the collection advice does say "before"). The model-rename advice worked (see scenario 7).
4. ⚠️ **F4 — A refused statement still writes the auto-baseline package.** On an empty migrations directory with a `db` ref, `prisma migration plan --name r --rename User.name:User.fullName` on MongoDB fails with `MIGRATION.PLANNING_FAILED` ("nothing was planned") yet leaves `migrations/app/20261007T1015_baseline/{migration.ts,migration.json,ops.json}`. Same on SQLite with the scenario 5 refusal: `prisma migration plan --name tidy --rename Profile.name:Profile.fullName` → `PLANNING_FAILED`, and `migrations/app/20261007T1015_baseline` appears. The error does not mention it. The script says a statement that cannot be applied "fails before anything is written". An unresolvable statement (`--rename Profile:Nope`) does fail before the baseline is written.
5. ⚠️ **F5 — Re-running a rename that already happened gives advice that points the wrong way.** Command: `prisma db update --rename Profile:User --rename User.name:User.fullName`, run a second time (scenario 2). Output: `✘ [MIGRATION.STATEMENT_UNRESOLVED] Cannot resolve statement "--rename Profile:User"` / `why: The origin contract has no model "Profile" (models: __unbound__.Post, __unbound__.User).` / `→ Correct the names in the statement`. A reader can work out from the model list that the rename is done, but the message does not say that the database is already at the new names, and the advice tells them to change names that are correct. It should say the database already has `User`, so drop the statement.
6. ⚠️ **F6 — The internal namespace `__unbound__` appears in user-facing messages for SQLite and MongoDB.** Examples: `(models: __unbound__.Post, __unbound__.User)`, `The field "handle" already exists on the origin model "__unbound__.Profile"`, `An earlier statement already renames "__unbound__.Profile".`, `the origin contract has no namespace "Account" (namespaces: __unbound__)`, and `"namespaceId":"__unbound__"` in the JSON `refusedStatement` and `appliedStatements`. These projects have no namespaces; the names should print without one.
7. ⚠️ **F7 — Several statement errors say what is wrong but not what to type.** The advice line is the generic `→ Correct the statement` or `→ Correct the names in the statement` in each of these (scenario 3 and exploratory):
   - `--rename Profile` → `The statement has no ":" between the old and new name.` No example of the form.
   - `--rename Profile:User.fullName` → `The statement names a model on one side and a field on the other.` No example of either correct form.
   - `--rename User:Profile` (backwards) → `The origin contract has no model "User" (models: public.Post, public.Profile).` Both names exist, one in each contract; a hint that the order is `old:new` would fix it at once.
   - Swapping two fields, `--rename Profile.name:Profile.handle --rename Profile.handle:Profile.name` → `The field "handle" already exists on the origin model …`. The names are correct; swaps are not supported, and nothing says so or offers a route.
   - Field statement before its model statement, `--rename Account.name:Account.fullName --rename Profile:Account` → the `why` ends `no earlier statement renames a model to it`, which hints at the cause, but the advice still says to correct the names rather than to put the model statement first.
   - Identity statements, `--rename Profile:Profile` and `--rename User.name:User.name` → `… already exists in the origin contract, so it cannot be the new name`. Correct but confusing for a statement that renames nothing.
   - By contrast the field-on-old-model error (`--rename Profile.name:User.fullName`) is exemplary: it quotes the input, explains, and gives the exact two statements to type.
8. ⚠️ **F8 — The `@@map` refusal says what to do but not how.** Command: `prisma migration plan --name tidy --from 20261007T1005_initial --rename User.name:User.fullName` (scenario 5). Advice: `rename the table by hand first, with ...this.renameTable({ schema: "public", table: "users", to: "app_users" }) in its own migration.ts, then plan the field rename on top of it.` It does not say that this needs an intermediate contract with only the `@@map` change, emitted, and `prisma migration new --name … --from <hash>` to get a `migration.ts`. With those steps the advice works and keeps the rows (verified below).
9. ⚠️ **F9 — When a plan with a statement also has placeholders, the human output drops the statement report and the JSON is inconsistent.** Command: `prisma migration plan --name ns7 --from 20261007T1002_initial --rename Profile:User` with the field rename left unstated. Human output shows only `⚠ Planned migration with placeholder(s)` and the next steps: no operation list and no `Statements applied` block, so nothing tells the user that column `name` is dropped. JSON: `operations` is `[]` while `appliedStatements` lists one statement with 3 `operationIds` that appear in no `operations` entry.
10. ⚠️ **F10 — The extension upgrade instructions leave a planner author unsure what to do with non-empty `statements`.** File: `upgrade-instructions/pending/migration-statement-renames/extension/instructions.md`. It says to pass `statements: []` at call sites and that `MongoMigrationPlanner` refuses non-empty statements, but not what a third-party planner that does not implement renames must do when it receives some: ignore them, or return a `statementRefused` conflict with `refusedStatement` set. It then says of `refusedStatement` that "nothing needs to set it", which suggests ignoring is fine. It also does not give import paths for `ResolvedMigrationStatement`, `AppliedMigrationStatement` and `PlanOrigin` (only `planOriginOf`). The `planner-success-applied-statements` detection skips a whole file once `appliedStatements` appears anywhere in it, and misses files that return `{ kind: 'success' }` without naming a `MigrationPlanner*` type; neither miss is called out. The misses for `plan(options)` are called out well.
11. ⚠️ **F11 — The skill's MongoDB workaround does not match the CLI's, and the new error codes are not in the skill's code table.** `skills/prisma-8/references/migrations.md` § "What Prisma 8 doesn't do yet" says for MongoDB renames "Workaround: hand-edit `migration.ts`, or use a keep / backfill / drop pattern". The Mongo factory list in the same file has no rename operation, and the CLI's own advice is to rename in `mongosh`. The "Diagnostic codes you route on" table has no `MIGRATION.STATEMENT_INVALID`, `MIGRATION.STATEMENT_UNRESOLVED` or `MIGRATION.STATEMENT_ORIGIN_UNKNOWN`. Minor.

## 7. MongoDB — ⚠️

`wip/qa/s7`, `MongoMemoryReplSet`. `model Profile { id ObjectId @id @map("_id"); name String @unique; handle String }`, `db update`, 3 documents.

```
$ (model renamed to User) prisma db update --rename Profile:User
✘ [MIGRATION.PLANNING_FAILED] Migration planning failed
  why: MongoDB does not apply rename statements in this release, so nothing was planned: rename model "Profile" to "User"
→ MongoDB cannot carry out rename statements in this release. Without the statement, a plan drops collection "Profile" with its documents and creates collection "User". To keep the documents, rename the collection by hand on each database before a plan made without the statement is applied there, for example with db.getCollection("Profile").renameCollection("User") in mongosh. A migration written by migration plan without the statement still drops "Profile" wherever it is applied, so check its operations first.
[exit 2]
```

JSON `meta.conflicts[0].kind` is `statementRefused` with `refusedStatement` set. Nothing written; `Profile` still holds 3 documents. The advice states what would happen without the statement. Following it (rename the collection, then `db update` with no statement): `--dry-run` shows `(no operations)`, the update reports `✔ Database already matches contract`, and `User` holds the 3 documents with index `name_1`. Field rename (`name` → `fullName`, unique):

```

→ MongoDB cannot carry out rename statements in this release. Without the statement, the documents in collection "User" keep their values under "name", and nothing moves them to "fullName".
```
