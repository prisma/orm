## Problems, ranked

### Data loss

None found. Every rewrite left `null`, missing values, empty lists, `null` elements and non-object elements as they were, and every stop left the documents recoverable.

### Wrong advice

1. **A plan-wide refusal hides its reason and its two-migration advice from the terminal; the advice it does show starts with a step that asks a question it does not mention.** The reason and "Make the change in two migrations: …" exist only in `meta.conflicts[].why` of the `--json` envelope. The human output of both `migration plan` and `db update` prints only the hand-written route. Reproduce (`wip/qa-pr2/r10`): PSL with `Task` discriminated by `type`, variants `Bug` (`bug`) and `Epic` (`epic`); change to only `Epic` with value `bug`; `prisma migration plan --name step --from <hash> --delete Bug --convert Epic`. Seen:

   ```text
   ✘ [MIGRATION.PLANNING_FAILED] Migration planning failed
     why: Cannot convert variant "Epic": the migration writes a value that another of its operations reads (Delete the documents of collection tasks whose type is "bug"; Replace value "epic" with "bug" in field type of collection tasks)
   → To write the rewrites by hand, plan the change without --convert Epic with `prisma migration plan --from ee38…`, add the rewrites the message describes to the migration.ts it writes, run `node <migration directory>/migration.ts` for the directory it writes, and apply it with `prisma db migrate`
   ```

   The same for a chain of stored field names (`wip/qa-pr2/r7`: `name @map("nm")`, `nick @map("nk")` changed to `fullName @map("nk")`, `alias @map("al")`, with `--rename User.name:User.fullName --rename User.nick:User.alias`). Following the shown advice in `r7`: planning without the statements asks again (`CLI.CONSENT_REQUIRED` for `User.name`), so the user must answer `--delete User.name`, a data-losing answer, then replace `fillField` and `unsetField` with two `renameField` calls they must know to write, in the reverse of the order the message lists them (listed order would rename `nm` onto the existing `nk`). Done that way it kept the data. The two-migration route (rename `nick` first, apply, then rename `name`) worked at once in `r7b`, and for variants it is what the spec and journey V4 promise. Should be: the human output prints the conflict's why, including "Make the change in two migrations …", as the first next action, and the hand-written route, if kept, says to answer `--delete` and in which order to write the renames.

### Plan that cannot apply

2. **A new field that reuses the stored name a rename frees gets no fill and no question; the apply then stops at the document check.** Reproduce (`wip/qa-pr2/r8`): before `name String @map("nm")`, `nick String @map("nk")`; after `fullName String @map("fn")`, `nick String @map("nk")`, `code String @map("nm")`; one document `{ nm: 'Ann', nk: 'annie' }`; `prisma migration plan --name step --from <hash> --rename User.name:User.fullName`. Seen: "Planned 2 operation(s)": "Rename field nm to fn" and "Update validator on users (added: fn)". No fill of `nm`, no question, no refusal. `db migrate` then stops: "This validator change makes "fn" required. … That document has no "nm"." Nothing is lost and the stop's advice works, but the plan was wrong, and the stop names `fn` (which the document has) as what the change requires. With `code Int @map("nm")` (`r9`) the same: "changed: nm" and no type change question. Should be: the plan-wide rule refuses it (the spec names "a fill of a field or key that a rename moves away"), or the plan fills `nm` and says so.

### Unclear text

3. **The question for a removed embedded model field does not name the likely new name.** For a value object (`Address.street` to `Address.line1`) it offers `--rename Address.street:Address.line1`. For an embedded model (`Line.sku` to `Line.code`, TypeScript contract, `wip/qa-pr2/s5`) it offers `--rename 'Line.sku:Line.<new name>'` and does not mention the temporary value `--delete` would give `code`. The advice works once the name is filled in.
4. **The variant question does not say what changed or what `--convert` does.** `Bug` changing its value from `bug` to `defect` (`wip/qa-pr2/s9`) asks: "why: Delete the documents of collection tasks whose type is "bug" would lose the data of model "Bug"." then `--convert Bug` and `--delete Bug`. Nothing says the value changed, nor that `--convert` moves the documents to `defect`. Both answers did what their names suggest.
5. **The enum swap advice reads as per-member steps; done for one member only, the second plan is refused again.** For `ACTIVE`/`ARCHIVED` trading values (`wip/qa-pr2/r1`) each member gets "first change the stored value of enum value "Status.ACTIVE" to one the enum does not use and apply it, then change it to "archived"". I moved only `ACTIVE` in the first migration; the second plan was refused with the same advice, and it took three migrations. The journey's route (move both in the first migration) takes two. Should be: "first change the stored values of both "Status.ACTIVE" and "Status.ARCHIVED" to values the enum does not use, apply that, then change them to their final values." The edits the question prints for `--delete` worked exactly as written.
6. **A field or key chain gets the generic "still exists" refusal, with no route.** `--rename User.nick:User.alias --rename User.name:User.nick` (`r4`) and the same for value object keys (`r5`): "The field "nick" still exists on the destination model "User", so it was not renamed. → The old name must exist in the origin contract and not in the destination contract …". True, but it does not say to rename in two migrations. Swaps get a clear three-plan route (`r3`). This message predates PR 2 (the statement checks of slice 1), so it may be out of scope.
7. **In the interactive question, typing the word `rename` is rejected with an error about a flag the user did not type.** `db update` in a terminal for `Address.street` to `Address.line1` (`wip/qa-pr2/i3`) shows "(rename Address.street:Address.line1 or delete)". Typing `rename` re-asks with: "Invalid statement "--rename Address.street". The statement has no ":" between the old and new name." Typing `rename Address.street:Address.line1` worked, as did `delete` for an enum value (`i1`) and `convert` for a variant (`i2`). Should be: accept `rename` when the question already names the new name, or say "type rename Address.street:Address.line1". The prompt also says "With --delete Address.street, …" where the user answers `delete`. The question code is shared with SQL, so this may predate PR 2.

## Not reachable

- **Fields of a variant of an embedded model.** A TypeScript contract where `User` embeds many `Item`, and `Item` has a variant `Photo`, fails at `contract emit`: "[CONTRACT.RELATION_INVALID] Relation "User.items" embeds model "Item", which has variants. … an embedded model cannot have variants." PSL has no embedded models. So the new refusals and warnings for these fields cannot be met by a user today; only unit tests reach them.
- **Boolean enum swap advice.** `enum Flag { ON = true  OFF = false  @@type("mongo/bool@1") }` fails at `contract emit`: "domain.namespaces.__unbound__.enum.Flag.members[1].value must be a number, a string, an object, an array, false, null or true (was missing)". The member whose value is `false` loses its value. PR 2 does not touch authoring, so this predates it, but it means no PSL user can reach the boolean advice. Worth a ticket of its own.

## Is PR 2 ready from a user's point of view

Almost. Every statement does what it says on real documents, every stop is recoverable, re-runs are safe, and `migration.ts` always reproduces `ops.json`. Problem 1 should be fixed first: the refusals that decision 8 adds are where a user most needs the two-migration advice, and the terminal does not show it. Problem 2 is a narrow case (a new field taking a stored name a rename frees, only through `@map`) whose apply stops safely; fix it or record it in `deferred.md`. Problems 3 to 7 are wording.
