## Problems, ranked

### Data loss

None found.

### Wrong advice, or a state the user is not warned about

None found in this round. All four problems from the final report are fixed:

- A part-way `--delete` cast now says `Until it does, a document already cast holds a type the collection's current validator does not allow, so updates to it fail.`
- The bypass advice now says the old validator "may" reject a fixed document, and the Prisma 6 skill item says a plain update works since the collection has no validator. Both matched what I saw.
- A type change of a field stored as `addr.zip` is refused at planning, naming the field and why.

### Unclear text

1. **Deleting the validator change but leaving the `checkDocuments(...)` call gives a bare error.** `node migration.ts` accepted the file. `db migrate` then stopped with `✘ [MIGRATION.INVALID_OPERATION_ENTRY] checkDocuments on collection users has no validator change of that collection after it to read the validator from.` It has no next action, no docs link and no migration path. Nothing ran and nothing changed, so it is safe. A user would want "remove the `checkDocuments(...)` call or restore the `collMod` in `migrations/app/<dir>/migration.ts`, then run the file with `node`". Catching it when `migration.ts` runs would be earlier still.
2. **The error reference does not describe that failure.** The `MIGRATION.INVALID_OPERATION_ENTRY` entry in `docs/reference/error-reference.md` does not mention `checkDocuments`.
3. **A data transform update that fails part way does not warn about the state it leaves.** `x3`: my `--convert` update failed on one value after converting two others to `bool`. The message says `Documents it updated before that value stay updated` and to fix the update, but not that those documents now fail their updates (I confirmed: "Document failed validation"). The `--delete` cast message now says this; the data transform one could say the same.
4. **The applied-operation count can be lower than the list** (carried over). `x8`, on an empty collection: `Applied 3 operation(s)` above four listed operations.
5. **A value object type change does not say why the shown document fails.** Scenario 8: the why says `changes what "address" accepts` and gives the `_id`, but no "That document holds …" sentence, which the other cases now have.

## Hand-edits to a planned `migration.ts`

The early check is now `checkDocuments({ collection: 'users', rewrittenFields: ['plan'] })` with no validator inside, and reads the validator from the `collMod` after it.

- **Tightening the validator (`h1`).** A plan that fills a new required `plan`. I added a required `nick` to the `collMod` validator by hand and ran the file. `db migrate` stopped at the early check, before the fill: `This validator change makes "nick" required. ... That document has no "nick"`, `no rewrite of this plan makes them fit, so nothing was rewritten`. The documents were unchanged. No `--backfill` advice for `nick`, correctly, since the contract has no `nick`. The early check followed the edit. Following its advice (remove the `checkDocuments(...)` call, set `checkDocuments: false`, run the file) applied the fill and the validator, then stopped at `MIGRATION.SCHEMA_VERIFY_FAILED ... mismatch: users/validator`, as expected for a validator that no longer matches the contract.
- **Loosening the validator (`h2`).** A plan that fills `plan` and adds a required `born DateTime`. Unedited, the early check stopped before the fill; documents unchanged. I removed `born` from `required` by hand and ran the file. The early check passed, the fill and the validator applied (the live `required` is `_id`, `email`, `plan`), then the same expected `SCHEMA_VERIFY_FAILED`. A second `db migrate` changed nothing and gave clear advice about hand edits. The early check followed the edit.
- **Validator change deleted (`h3`).** I deleted the `collMod` and left `checkDocuments(...)` and the fill. `node migration.ts` wrote `ops.json` without complaint. `db migrate` refused with `MIGRATION.INVALID_OPERATION_ENTRY` before running anything; the documents were unchanged. Safe, but see problem 1.

## Per scenario

### 1. `User.age` `String` to `Int` through `migration plan`

Three documents: `"42"`, `"7"`, `"abc"`. Refused with `--convert User.age` and `--delete User.age`. `--convert` planned the check, `Data transform: User.age` and the validator; one slot, `placeholder('User.age:update')`. `db migrate` unfilled: `MIGRATION.UNFILLED_PLACEHOLDER`. Filled with a `$convert` pipeline (`onError: 0`): applied 3 operations; every `age` an `int` (42, 7, 0); further plan "No changes detected"; `db verify --schema-only` clean; an update to every document succeeded. Pass.

### 2. `--delete` through `db update`

Without a statement only `--delete User.age` is offered. With it, the cast failed on `"abc"`, with the new sentence that documents already cast fail their updates until a re-run. The advice to plan with `--convert` appears once. After changing `"abc"` to `"13"`, the re-run cast both values to `int`; further `db update` empty; verify clean. Pass.

### 3. `Int` to `Int64` through `db update`

Nothing asked. The check, `Cast field age ... from int to long`, the validator. Values are `$numberLong` (42, -7). Further update empty; verify clean. Pass.

### 4. New required fields through `db update`

`plan String`, `score Int64`, `ok Boolean`, `n Int`, `f Float`, `tags String[]` on two documents, one holding `plan: null`. Six fills and the validator. Stored `""` (also where it was `null`), `$numberLong 0`, `false`, `$numberInt 0`, `$numberDouble 0.0`, `[]`. One temporary-value line per field. Further update empty; verify clean. Pass.

### 5. Optional field made required through `db update`

Four documents: one with `name`, two without, one `null`. Stopped: `3 documents`, `That document has no "name"`, the query, the `--backfill User.name` command, the bypass form ("may reject"), and `db update writes no migration.ts, so there fix the documents first`. The query found exactly the three. A plain update fixed them; the re-run applied; verify clean. Pass.

### 6. `--backfill` through `migration plan`

The check, `Data transform: User.name`, the validator; one slot. Filled with `{ $set: { name: 'Anonymous' } }`. Applied; every document has `name`; further plan empty; verify clean. Pass.

### 7. Adopting a Prisma 6 database

`User` documents: one with an extra `legacyScore`, two that fit, one without `email`; no validator. `prisma6Schema`, `contract emit`, `db sign`, the Prisma 8 schema, `migration plan --name adopt`.

- `db migrate` stopped: `That document has "legacyScore", a field the new validator does not name`, `Change them with a dataTransform in migration.ts, or with an update in mongosh`, and the `checkDocuments` route.
- `checkDocuments: false`, `node migration.ts`, `db migrate`: applied; all four documents kept; verify clean.
- Separately, plain updates (give the last document an `email`, remove `legacyScore`) and a re-run: applied; verify clean.
- `db update` on a collection with no validator gave the same cause; after removing the extra field it applied.

Pass.
