## New problems, ranked

### Plan that cannot apply

1. **Medium. Answering `--delete` for a discriminator that a new discriminator replaces never works, and the refusal does not say so.** The question and the plan-wide refusal both offer `--delete Task.type` next to `--rename Task.type:Task.kind`.
   - Discriminator rename alone (`wip/qa-pr2/z9d`, from `t9`): `prisma db update --delete Task.type`. The plan fills `kind` with `""`, removes `type`, then stops at the validator: "That document holds "" in "kind", a value the new validator does not allow there." Documents left: `{ title: "b1", severity: "high", kind: "" }`, `{ title: "e1", scope: "all", kind: "" }`. No variant accepts `""`, so this plan can never apply, and the variant of each document is gone once it stops. The user did pick a delete, but the question did not say that the new required discriminator gets a temporary value no variant accepts. The value object question does say this for its own case ("If you answer delete, the existing objects get a temporary value in the new required field …").
   - With a variant change too (`v1c`, from `t10`): `--delete Task.type --convert Bug` plans "convert variant "Bug" (1 operation)", but that replacement matches nothing because `kind` does not exist yet; `db migrate` then stops the same way with every `kind` `""`. `--delete Task.type --delete Bug` gets the same refusal again, word for word, still saying "The plan holds changes that no statement answers yet: field "Task.type" … model "Bug" …" although both were answered. `projects/migration-statements/deferred.md` ("Ask before refusing") says a user who answers `--delete` gets the same refusal and that "the overlap refusal says so and then gives its two-migration advice". It does not say so: the text has neither sentence.
   - Should be: do not offer `--delete` for a discriminator whose replacement must be filled (or refuse it, saying only `--rename` keeps the variants); and make the refusal true when the answers are already given, as `deferred.md` describes. The keep-data route (`--rename Task.type:Task.kind`) is offered first everywhere and works, so a user who follows the first answer is safe. This may predate PR 2 for the discriminator-alone case.

### Unclear text

2. **Low. The plan-wide refusal's first sentence is hard to read.** "An operation selects its documents by its filter when it runs, so it must run after the operations that write what its filter reads and before those that empty it, and these operations need both." (`v1`, `z7`). It is true, but a user cannot act on it, and it comes before the part they need ("The plan holds changes that no statement answers yet … Answer them and plan again: …"). Should be: lead with the unanswered changes and the answers; keep the reason short and after them.
3. **Low. Smaller wording points.**
   - (a) The two-run route says "Then rename those members back to ACTIVE and ARCHIVED with their new stored values". "New" can be read as the temporary values from the first run. Should be: "with their final stored values" (`v3`, `pg4a`).
   - (b) Under `db update`, the enum swap question's why still says "make the change in two migrations … in a second" before the `db update` route (`v3`). The route that follows is right; the why could name the `db update` route or drop the migrations sentence there.
   - (c) The plan-wide refusal offers only `--delete Story` for a removed variant (`v2`), while the plain question offers `--rename 'Story:<new name>'` too (`z7`). Minor; the delete is likely what a removal means.
   - (d) The required enum value stop's why says both "Nothing was removed." and "The failed apply changed nothing." (`w8`). One is enough.
