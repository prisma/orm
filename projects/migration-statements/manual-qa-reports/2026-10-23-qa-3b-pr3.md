## Defects

1. ⚠️ **F1 (medium) — Following the upgrade instructions leaves a stale `db` ref, and the next `migration plan` writes a second migration with the same endpoints.** Step 1 runs `prisma db sign`, which writes `migrations/app/refs/db.json` (the old demo had none). Step 3's `prisma db migrate` does not advance that ref. Steps:
   1. Old `prisma-8-demo` (merge base `f543fb4173`), old CLI: `prisma db migrate`.
   2. Current CLI: run the script, `prisma db sign --db "$DATABASE_URL"` (`Advanced ref "db" → ecd77e4…`), `prisma contract emit`, `prisma migration plan --name value-object-checks`, `prisma db migrate`.
   3. `prisma migration plan` again, with no change:
      ```
      ⚠ The default origin ref 'db' points at ecd77e4…, which already has a migration leading to e1916bd…. Planning from it forks the migration graph; pass --from to choose the origin explicitly.
      ✔ Planned 2 operation(s)
      migrations/app/20261023T1839_migration
      ```
   The new migration adds the same two checks as the applied one. `migration status` then shows two edges `ecd77e4 → e1916bd`, one pending. The same happened on `mongo-demo` with the next real change. The `postgres-value-object-checks` section also says "A project with no `db` ref names the origin … `--from`", which never applies when the steps are followed in order, because step 1 just wrote a ref. The fix belongs in the instructions: `db migrate --advance-ref db` in step 3, or `db sign --no-advance-ref` in step 1 with `--from` in step 3. The fork itself is the older behaviour of `db migrate` and refs.
2. ⚠️ **F2 (medium) — Adding a required member to a value object that rows already hold has no route that keeps the data, and the advice is a dead end.** Postgres, `Address` held by `user.address` (required) and `user.previous` (nullable list), three rows.
   1. Add `country String` to `Address`. `contract emit`, `migration plan --from <last>`: four operations (two check drops, two check adds), no question, no warning.
   2. `prisma db migrate`:
      ```
      ✘ [MIGRATION.EXECUTION_FAILED] Operation checkConstraint.user.user_address_shape_5c02601b failed during execution: add check constraint "user_address_shape_5c02601b"
        why: check constraint "user_address_shape_5c02601b" of relation "user" is violated by some row. The failed apply changed nothing.
      → Fix the issue and re-run `prisma db migrate --to <contract>`
      ```
      Checks and marker unchanged, as promised.
   3. Fix the rows first: `UPDATE "public"."user" SET address = address || '{"country":"NO"}'` is refused by the old check `user_address_shape_9a7e984c`, which forbids the unknown key `country`.
   So the user can neither fix the rows before the apply nor apply without fixing them. What worked: hand-write a raw operation (an `UPDATE` for each column) in `migration.ts` between the drops and the adds, run `node migration.ts`, `db migrate`. Nothing tells the user this. The same holds for `db update` (scenario 3), where there is no `migration.ts`: the only route was to drop the old checks by hand in SQL, update the rows, then `db update`. Renaming a member hits the same wall; the spec gives rename and delete statements to PR 4, but not adding a required member.
3. ⚠️ **F3 (low) — The failure for a check that rows break does not say which rows or how to find them.** It names the check, which is good. It does not name the column, the count of rows, or the query the upgrade instructions give. `db update` says `Inspect the reported conflict, reconcile schema drift if needed`, which reads as if the schema drifted. `db migrate` says `--to <contract>`, a placeholder the user does not need. The docs link uses `error-reference#MIGRATION.EXECUTION_FAILED`, while other errors use `error-reference/CODE`. The advice text is not new in this PR, but derived checks make this failure far more common.
4. ⚠️ **F4 (low) — The upgrade instructions never say when to upgrade the Prisma packages.** They say "Before you upgrade, apply every pending migration … with the release you are upgrading from", then run the script, then `db sign`. A reader can infer that the package upgrade goes between the two, but it is not written. I did it there and it worked.
5. ⚠️ **F6 (low, not this PR) — The old `mongo-demo` migration history does not reach its own contract.** At the merge base, old CLI, empty database: `prisma db migrate` fails with `MIGRATION.SCHEMA_VERIFY_FAILED … missing: posts/index:summary:1; missing: posts/validator` on `20260626T1916_add_posts_indexes`. I used old `db update` to bring the database to the last migration's hash before the upgrade. Not caused by this PR.

## Other findings

6. **F5 (minor) — The no-operation summary uses the internal kind name.** `What changed: valueObject "public.Home".` A user writes `type Home`, so `value object "public.Home"` would read better. `db update` on the same change says `✔ Database already matches contract` and `(no operations)` while it moves the marker, and does not say what changed.
7. **F7 (low, not this PR) — MongoDB: making a member required is planned and applied without a question, and existing documents that lack it stay.** `region String?` → `region String` with a document that has no `region`: one `collMod`, applied, `db verify --strict` clean. MongoDB does not check existing documents on `collMod`, so the stored document no longer fits the validator. Same as before this PR.
8. **F8 (minor) — ADR 309 names the check `<table>_<column>_shape`.** The built name is `<table>_<column>_shape_<hash>`, as the upgrade instructions say. The ADR's "Enforcement on Postgres" paragraph should say the same.
9. **F9 (not this PR) — The SQL ORM cannot create a variant through the variant's own model.** `orm.Bug.create(...)` (single-table) fails with `null value in column "type"`; `orm.Feature.create(...)` (own table) fails with `ORM.COLUMN_UNKNOWN Unknown column "title" in table "feature"`. `orm.Task.variant('bug').create(...)` works. The merge-base code gives the same two errors.
10. **F10 (not checked against main) — A `BigInt` member cannot be written through the ORM.** `RUNTIME.ENCODE_FAILED … Do not know how to serialize a BigInt`. The check expects a JSON number for `pg/int8@1`, and a plain number is accepted. A `Bytes` member is written as `{"0":1,"1":2,"2":3}` and the check expects an object, so they agree.
