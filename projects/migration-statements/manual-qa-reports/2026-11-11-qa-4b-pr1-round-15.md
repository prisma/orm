## Problems, ranked

### Data loss

None found.

### Wrong advice

1. **On Postgres, `--delete` is offered for a type change the database has no cast for.** `p6`: `flag Boolean` to `DateTime`. The question offered `--convert User.flag` and `--delete User.flag`, saying `--delete keeps the field and lets the database cast its values, which can change or lose some.` Postgres has no cast from `boolean` to `timestamptz`, so `--delete` plans an `alterColumnType` that fails on every run, whatever the data: `cannot cast type boolean to timestamp with time zone. The failed apply changed nothing.` The failure's advice is then correct (see below). On MongoDB the planner already offers only `--convert` when there is no cast. Whether Postgres can know this at plan time is a design question; the user here is told `--delete` will cast when it cannot. I did not try other target pairs.

### Unclear text

2. **Without the `--convert` pointer, "replace that cast with your own conversion of the values there" does not say where the conversion goes.** On Postgres the planned call is `this.alterColumnType({ …, type: 'int4' })` with no `using`; on SQLite it is `this.recreateTable({ …, retypedColumns: ['age'] })` with no `copyExpressions`; on MongoDB it is `castField(...)`. The user has to know to add `using:` (Postgres), add `copyExpressions` (SQLite), or swap in a `dataTransform` (MongoDB). The third next action (delete and re-plan with `--convert`) writes the slot, so the user still has a guided route; the first action alone is now less self-contained than in round 14.

## Postgres no-cast case (`p6`, `p7`)

`db migrate` after `--delete User.flag`:

> ✘ [MIGRATION.EXECUTION_FAILED] Operation alterType.user.flag failed during execution: alter type of "flag" to timestamptz(3)
> why: cannot cast type boolean to timestamp with time zone. The failed apply changed nothing.
> → The database has no cast from the old type of field "User.flag" to its new type. `migrations/app/<dir>/migration.ts` changes field "User.flag" with a cast the database does not have between these types: replace it with your own conversion of the values there, run `node …/migration.ts`, and re-run `prisma db migrate`
> → Delete `migrations/app/<dir>` …, plan it again with `prisma migration plan --from c547a266… --name flag --convert User.flag`, …

The "change the value" action is correctly left out, since no value would help. Both routes worked:

- **Own conversion (`p6`)**: added `using: CASE WHEN "flag" THEN now() ELSE 'epoch'::timestamptz END` to the `alterColumnType` call, ran the file, re-ran `db migrate`: applied; `true` became now, `false` became 1970-01-01; verify clean.
- **Delete and re-plan (`p7`)**: the printed `migration plan --from … --name flag --convert User.flag` wrote a `using` slot; filled with the same expression; applied; verify clean.
