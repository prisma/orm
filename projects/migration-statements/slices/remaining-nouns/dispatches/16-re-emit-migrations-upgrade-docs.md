# Dispatch 16 — re-emit, example migrations, the upgrade script, and docs

**Plan:** [`../plan-pr3.md`](../plan-pr3.md) · **ADR:** ADR 309 · **Grounding:** `wip/pr3-grounding.md` § C and risks 6–8 · **Builds on:** dispatches 11, 14 and 15, and the merge of main (`4aaa36d9bc`) · **Branch:** `tml-3537-value-objects-storage`

## Outcome

The whole repository is on the new contract shape, users can move their projects to it, and the docs describe it.

### 1. Re-emit

- Every committed `contract.json`, `contract.d.ts` and `expected.contract.json` is re-emitted with the repository's own scripts (`pnpm fixtures:emit`), and `pnpm fixtures:check` is clean afterwards.
- Generated test fixtures are regenerated by their generator, never by hand. In particular, `packages/2-mongo-family/3-tooling/emitter/test/generate-orm-fixture.ts` writes both `mongo-contract/test/fixtures/orm-contract.d.ts` and `9-family/test/fixtures/orm-contract.d.ts`. A dispatch 13 hand edit put the first copy out of step with the second. Also regenerate `mongo-orm/test/fixtures/stored-names-contract.*`.
- Hand-written test contracts with `valueObjects` in the domain (grounding C: about 77 test files) move to storage.
- These tests are red today and must be green afterwards:
  - every sql-orm-client test that loads the generated fixtures;
  - mongo-orm `collection.stored-names.test.ts` and `stored-names.test-d.ts`;
  - target-postgres `full-text-index-contract-load.test.ts`;
  - family-mongo `mongo-contract-view` and `mongo-migration`;
  - the `authored-contract-roundtrip` cases for value objects, polymorphism and "refuses a to-one relation";
  - the `retail-store` build and the typecheck of every example.

### 2. Example migrations

- Each `examples/prisma-8-demo` migration that introduces a value object or a variant gains the operations that create the new checks (plan decision 7; Will, 2026-10-23). That means the value object check, the discriminator membership check, and the discriminator value set.
- `scripts/regen-example-migrations.mjs` re-serializes `ops.json` from `migration.ts`, so the operations go into `migration.ts`. Write them as a user would by hand, with the same factory calls the planner renders.
- Check on PGlite: `db migrate` runs the whole chain from empty, and then `db verify` with strict schema verification is clean.
- Do the same for every other example with a Postgres migration chain that holds value objects or variants. The Mongo examples (`mongo-demo`, `retail-store`) need no new operations, since Mongo gets no new checks; confirm with `db verify` on mongodb-memory-server.

### 3. Upgrade instructions and script

- Add fragments for the app and for extensions, following the `record-upgrade-instructions` skill (`skills-contrib/record-upgrade-instructions/SKILL.md`). The precedent is the rc.14 to rc.15 `data-type-in-contract` fragment and script under `skills/prisma-8/upgrading/{app,extension}/upgrades/8.0.0-rc.14-to-8.0.0-rc.15/`. Use the upgrade folder for the current release line; the skill says how to name it.
- **The app script** rewrites a user's committed contract snapshots into the new shape. That changes their storage hashes. So the script must also rename each snapshot directory and update every manifest and `migration.json` that names it, keeping the migration graph whole. If that cannot be done safely, it must leave the old snapshots readable instead. Decide from the precedent, and say which you chose and why.
- Run the script on a copy of a project with a real migration history, inside `wip/`. A good candidate is the `prisma-8-demo` chain as it was at `origin/main`. Afterwards, `migration status` and `db migrate` on a fresh PGlite database must work. Commit a test for the script if the precedent has one.
- **The app fragment says:**
  - Re-emit the contract. An old `contract.json` is refused with the re-emit message.
  - Run the script for the committed snapshots.
  - `ValueObjectTypesFromDomain`, which was public through `@prisma/orm-mongo/contract/types`, is now `ValueObjectTypesFromStorage`. A committed `contract.d.ts` that imports it compiles again once re-emitted.
  - On Postgres, the next migration adds a check to every value object column and every discriminator column of a managed table. Rows that do not fit fail the apply. That includes rows with extra keys, which the SQL ORM never refused. Say how to find such rows first, with a query using the same predicate.
- **The extension fragment says:**
  - `contractModelToMongoResultShape` and `contractFieldToMongoFieldShape` take `storage` instead of `valueObjects`.
  - `compileMongoQuery`'s fifth argument is the storage.
  - `MongoValueObjects` is removed.
  - The removed Postgres exports `PostgresCheckKind`, `PostgresCheckExpressionInput` and `PostgresCheckExpressionCandidate` are replaced by `CheckExpressionInput` and `CheckExpressionCandidate` from the family's check expression module.
  - This replaces the advice in the rc.14 release notes (`docs/releases/v8.0.0-rc.14.md:65-76`, `CHANGELOG.md:887-898`).
- `check:upgrade-coverage --mode pr --prev $(git merge-base HEAD origin/main) --head HEAD` passes. Dispatch 15 saw it fail on diffs in `examples/prisma-8-demo-mysql` that the dispatch did not touch. Find out why, and fix it or explain it.

## Rules

- Never run `pnpm test:integration`, `pnpm test:e2e` or `pnpm test:all`. Run only named files inside `test/integration`, with `pnpm test <file>`. Run journeys with `pnpm test:journeys <file>`.
- Use `mise exec --` for node and pnpm. Never `npx`. Do not write to `/tmp` or any system temp directory. Save slow output under `wip/` and read the file. Never use bare `git stash`.
- Prose in Markdown is never hard-wrapped. ADRs carry no ticket ids, dispatch ids or slice names.
- No comments where the code can say it. No bare `as` casts in production code, including the upgrade script. No `any`.
- Commit with `git commit -s --trailer "Signed-off-by: Will Madden <madden@prisma.io>"`. No AI attribution lines. Stage files explicitly. Commit re-emitted files apart from hand-written changes.
- Do not push. Do not open a PR.
