## Predictions and falsification

1. **Low-load request work unchanged:** earlier release frees a lease but does not remove full materialization or response work. Predict substantially lower hold with similar HTTP p50/p95, CPU per completion and response bytes, negligible acquisition wait/backlog. A consistent substantial HTTP/CPU decrease would contradict the unchanged-work explanation.
2. **Overload app-side service limit:** predict high app ELU together with CPU near one core, increasing event-loop delay/backlog, and client-query intervals substantially larger than independently logged PostgreSQL durations. Low ELU/CPU with large server durations would contradict a simple app-side explanation. ELU alone is not CPU evidence; server duration can include output blocking, and client intervals include pg parsing, readiness callback delivery, network and scheduling.
3. **Observer/shared-host tail noise:** repeat low-load tests with `OBSERVE=0`, no preload, no added app metrics and no PG activity sampler. Predict noisy p95/p99 differences may shrink/change sign. Stable patched tail regression across disabled repeats weakens the observer explanation; no-observer tests cannot eliminate time-varying host noise.
4. **Serialization/transfer contribution (diagnostic only):** scratch variant awaits the identical `.limit(100).include("comments").all()` then returns parent/comment counts, verifying 100/1000 after materialization. Compare includes80 full vs small responses. Reduced CPU/backlog suggests response-path contribution, not codec attribution. No improvement weakens serialization/transfer as the dominant explanation. Keep this separate from product latency evidence.

## Ordered bounded design

- Fixed pool10, same PostgreSQL15 database (100 posts/1000 comments), same Node24 executable, fresh app per trial, 2-second concurrency10 warmup, 15-second open-loop arrivals then complete drain. Lists100/500 and includes10/80, three repeats per build. Pair orders alternate baseline→patched, patched→baseline, baseline→patched; endpoint order rotates between repeats.
- Instrumented primary matrix: 24 trials with original lease/wait probes and 200ms occupancy, 500ms PG activity plus per-second app ELU, monotonic CPU deltas and event-loop delay at fixed 10ms resolution. HTTP runner records completed response bytes/counts and backlog. Aggregate intervals wholly inside arrival windows are selected for load-only summaries; lease distributions include drain and exclude warmup.
- Observer-disabled low load: 12 trials (lists100/includes10 × two builds × three repeats), interleaved with the corresponding observed low-load tests. `OBSERVE=0` must disable all injected app observation and PG sampling, not merely lease timing.
- Small-response includes80: six diagnostic trials, paired with the full primary trial for each build/repeat. Same full ORM result is awaited and verified before returning the tiny body; no SQL projection or codec change.
- Server logging: only four additional diagnostic trials per build/endpoint-rate combination selected as lists100/500 and includes10/80 (eight total), session-only startup `options=-c log_min_duration_statement=0`; no global setting changes. Primary trials have logging disabled. Compare diagnostic logging-on to primary repeat ranges, not pooled product results. Archive exact server log byte windows and backend PID/time evidence. Parse/Bind/Execute are separate extended-protocol phases, never count each as a request; correlate Execute counts to leases/HTTP within timestamps. PostgreSQL output `ClientWrite` is not pure execution CPU.
- Cap policy: preserve every attempted trial, report any skipped arrivals due to the existing 2000-outstanding cap. If capped, shorten a separately labeled retry to 10 seconds; never silently omit the capped evidence.
- Calibrate aggregate observer using idle, synchronous CPU busy and synchronous sleep intervals; verify units (CPU microseconds / monotonic wall microseconds, 1.0 = one core; event-loop delay ns / 1e6). Calibrate server log simple/extended query counts before diagnostic trials.
- No concurrent benchmark workloads, builds or tests. Preflight detected an unrelated `attribute-autocomplete` Turbo validation pipeline; wait for it to finish before trials, record preflight and per-trial process evidence. Host remains shared with OS/editor/background processes and other uncontrolled external work; do not kill those.

## Interpretation and uncertainty

Report per-repeat HTTP/hold/wait p50/p95/p99, backlog, ELU, CPU, event-loop delay and server durations rather than only pooled percentiles. Three repeats are descriptive ranges, not confidence intervals; low-load includes has 150 requests per trial, so p99 is exploratory (about two tail observations). Event-loop delay includes the timer resolution floor, not pure added delay. Per-second p95 delay summaries are not pooled request latency. CPU includes process threads; no stacks, GC, codec-specific attribution, flamegraphs, larger pools or production edits.

Official interpretation references: [Node24 perf_hooks](https://nodejs.org/docs/latest-v24.x/api/perf_hooks.html), [PostgreSQL15 logging](https://www.postgresql.org/docs/15/runtime-config-logging.html), [PostgreSQL15 activity/waits](https://www.postgresql.org/docs/15/monitoring-stats.html), [Node event-loop blocking and JSON](https://nodejs.org/learn/asynchronous-work/dont-block-the-event-loop). Installed pg8.22 query/result/client implementation parses and accumulates rows before readiness callback completion, so the server/client gap alone cannot isolate ORM codecs.
