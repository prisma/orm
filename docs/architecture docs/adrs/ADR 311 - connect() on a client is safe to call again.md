# ADR 311 — `connect()` on a client is safe to call again

**Status:** Accepted
**Date:** 2026-10-29
**Amends:** [ADR 263 — A serverless Postgres connection has the same query interface as a `postgres()` client](ADR%20263%20-%20A%20serverless%20Postgres%20connection%20has%20the%20same%20query%20interface%20as%20a%20postgres%20client.md)
**Builds on:** [ADR 159 — Runtime Driver Lifecycle](ADR%20159%20-%20Driver%20Terminology%20and%20Lifecycle.md)

---

## At a glance

```ts
const db = postgres({ contract, url: process.env['DATABASE_URL']! });

await db.orm.public.User.first(); // the first query binds the client
await db.connect();               // resolves with the same runtime
```

## Terms

- **Client:** the object that `postgres()`, `sqlite()`, `mysql()` or `mongo()` returns.
- **Options:** the argument to `connect(options)`, such as `{ url }`. It says which database the client uses. It is not the options passed to `postgres(...)`.
- **Bound:** the client's driver has been given its database, by `connect()` or by the first query. ADR 159 calls this binding. A bound `postgres()` or `mysql()` client has not necessarily reached the database yet; it does so on the first query, as ADR 263 records.
- **Binding:** a `connect()` or a first query has started to bind the client and has not finished.

## Decision

`connect()` without options never fails because the client is already bound:

| Client state | `connect()` | `connect(options)` |
| --- | --- | --- |
| not bound | binds the client's driver | binds the client's driver to `options` |
| binding | waits for the binding to finish, then resolves with the runtime or rejects with the binding's error | rejects with `DRIVER.ALREADY_CONNECTED` |
| bound | resolves with the runtime | rejects with `DRIVER.ALREADY_CONNECTED` |
| closed, including closed while a `connect()` waits | rejects with `DRIVER.NOT_CONNECTED` | rejects with `DRIVER.NOT_CONNECTED` |

`connect(undefined)` is `connect()`. The client never compares options: options passed to a client that is binding or bound reject, even when they name the same database. The runtime that `connect()` resolves with is the one the client's queries run on.

This decision does not change what happens after a binding has failed. `sqlite()`, `mysql()` and `mongo()` try again on the next `connect()`. `postgres()` keeps the failure and rejects every later call with it.

A driver's `connect(binding)` keeps its rule from ADR 159: it binds a driver once. The client decides when to call it, so a repeated `connect()` on the client does not reach the driver. `connect` on a serverless Postgres client is unchanged: it opens a new connection on every call.

This replaces one row of the table in ADR 263's section "`connect` on a client and on a serverless client". For a client, "How often" was "at most once; it fails with `DRIVER.ALREADY_CONNECTED` if the client is already bound or binding". It is now "any number of times without options; with options, only before the client is bound". The cost ADR 263 lists as "`connect` has two meanings" still holds.

## Why

A client binds itself on its first query, so calling `connect()` is optional. An application creates one client and shares it between its modules. If a repeated `connect()` failed, a module that called it would have to be sure that no other module had sent a query yet, and nothing tells it that. A starter project generated by [`create-prisma`](https://www.npmjs.com/package/create-prisma) 0.14.4 shows the failure: its seed function calls `connect()`, so its `/users` route fails whenever another route has queried first.

Tools that connect on first use make a repeated `connect` harmless. Prisma 7's `$connect()` waits for a connection in progress and returns once connected. The MongoDB Node driver's `MongoClient.connect()` does the same. Tools that throw on a repeat, such as TypeORM's `DataSource.initialize()` and node-postgres's `pg.Client.connect()`, require the call before any query, so a repeat is a mistake in the caller's own code.

Options still reject because a client cannot change its database once it is bound. If `connect({ url: other })` resolved, the caller would believe it was using `other` while every query went to the first database. The error's code stays `DRIVER.ALREADY_CONNECTED`, so code that branches on it keeps working, and its `why` names the options.

## Consequences

- Code that needs the client's runtime can call `connect()` wherever it is, without knowing whether another module has queried.
- `connect()` on a bound client is not a check that the database is reachable. On `postgres()` and `mysql()` it never was: they reach the database on the first query.
- A `connect()` without options that a caller placed after the first query no longer fails, so nothing points out that it is unnecessary.
- Passing options to a client that is binding or bound still fails.

## Alternatives considered

### Compare the options, and resolve when they match

`connect({ url })` with the URL the client already uses would resolve. Two URLs that name the same database can be written differently, and a pool or a `pg.Client` passed as an option can only be compared by identity. The rule would depend on how the options were written. Rejecting any options is simpler and loses nothing: a caller that only wants the runtime calls `connect()`.

### Keep the rule and document it

The rule would stay, and the documentation would tell users to call `connect()` only before the first query, or not at all. The problem of coordinating modules would remain, and the starter shows that following the documentation is not enough to avoid it.
