# CI Integration

Continuous integration answers one question about a branch that changes the schema: are the migration artifacts sound, and what will deploying them do? Prisma 8 answers that question entirely offline. Every artifact CI needs — the contract, the migrations, their bookend contract snapshots, and the refs — lives in the repository, so the verification half of CI requires no database at all. A database appears only at deploy time, and then only the real target.

**Responsibilities:**

- Verify that emitted contract artifacts match their authoring source
- Verify migration artifact and graph integrity offline (`migration check`)
- Preview what a deploy will execute (`migration status --from <contract>`)
- Verify a live database against its contract at deploy time (`db verify`)
- Emit stable exit codes and structured diagnostics suitable for CI and agents

**Non-goals:** sandbox or rehearsal execution of migrations in the core CLI. The CLI has no shadow database (see the next section) and no CI mode that mutates any database other than the deploy target itself. Rehearsal against a fork of a real database is an extension-provided preflight, described in the next section.

## The CI signal

A typical pipeline for a branch that adds a migration:

```bash
# Verification — offline, no database
prisma contract emit            # re-emit; artifact drift from source fails the build
prisma migration check          # whole-graph integrity: hashes, edges, snapshots, refs
prisma migration status --from production --json   # preview the deploy path

# Deploy — the only step that touches a database
prisma migrate --to production --db "$DATABASE_URL"
prisma db verify --db "$DATABASE_URL"
```

Notice that the verification commands read only the filesystem. The preview step answers "what will run on merge?" from the on-disk graph alone, so it works in pipelines that have no database credentials — PR review bots included.

## No shadow database

Other migration tools verify migrations by replaying them. They provision a temporary "shadow" database, run the migration history against it, introspect the result, and diff that against the desired state. The shadow database exists because a pile of SQL scripts carries no record of the state it produces — the only way to learn that state is to execute the scripts somewhere.

Prisma 8 migrations do carry that record. Every migration names its `from` and `to` contracts by storage hash, and those contracts are stored as content-addressed snapshots in the repository (`migrations/snapshots/<hash>/contract.json`). Diffing is a pure function over two on-disk contracts: the planner reads snapshots, never a database. The information a shadow database would reconstruct by replay is already an explicit, versioned artifact.

This is an architectural boundary of the CLI, not a gap: **diffing is fully offline against on-disk snapshots, and the CLI never provisions or replays against a shadow database.**

Rehearsing a migration against a real copy of a database, a *preflight*, is a database-extension capability rather than a core verb. A database extension may implement a preflight hook: it takes the attested `ops.json`, executes it against a fork of a target database, and reports timing and errors. The CLI exposes preflight only when the configured database extension provides that hook. Prisma Postgres will ship one that forks the production database; any other database can implement the same interface. An earlier design put preflight in the core CLI as a `migration preflight` verb backed by a shadow database or a hosted service. That design is superseded by the extension-hook model: [ADR 029 — Shadow DB preflight semantics](../adrs/ADR%20029%20-%20Shadow%20DB%20preflight%20semantics.md) and [ADR 051 — PPg preflight-as-a-service contract](../adrs/ADR%20051%20-%20PPg%20preflight-as-a-service%20contract.md) record it.

Confidence that a migration behaves as promised comes from the artifacts and from apply-time enforcement instead:

- `migration check` proves the artifacts are internally consistent before merge (see below)
- Every operation declares pre/post invariants; the runner enforces them during the real apply and halts with a structured error on violation (see [Migration System](7.%20Migration%20System.md))
- The runner verifies the marker matches the migration's `from` hash before applying, and the destination hash after — a migration that doesn't produce its promised state cannot advance the marker

## Contract emission trust

Emitted artifacts (`contract.json`, `contract.d.ts`) are committed, and CI must not trust that the committed copies match the authoring source. The CI step re-emits from source (or canonicalizes and re-hashes) and fails on any difference. Development environments may auto-emit on change; CI always emits explicitly. See [ADR 008 — Dev Auto Emit CI Explicit Emit](../adrs/ADR%20008%20-%20Dev%20Auto%20Emit%20CI%20Explicit%20Emit.md) and [ADR 100 — CI contract emission trust model](../adrs/ADR%20100%20-%20CI%20contract%20emission%20trust%20model.md). All tooling downstream of emission operates on the canonical JSON, never on authoring source ([ADR 097 — Tooling runs on canonical JSON only](../adrs/ADR%20097%20-%20Tooling%20runs%20on%20canonical%20JSON%20only.md)).

## Artifact integrity: `migration check`

`migration check` is the merge blocker. With no argument it verifies the whole graph: every migration's `migrationHash` matches its content, every edge's recorded `from`/`to` hashes line up with neighbouring contracts, snapshot store entries carry the hashes they are keyed by, no orphan nodes, no dangling refs, and contract spaces stay disjoint. It is read-only and filesystem-only — a hash-level artifact check; whether applying a migration physically produces the recorded schema is enforced at apply time, as above.

Exit codes are stable — `0` pass, `2` structured failure, `4` integrity failures — and each failure carries a `PN-MIG-CHECK-*` code with a remedy. The full code table lives in [Migration System § Integrity checks](7.%20Migration%20System.md#integrity-checks-migration-check).

## Deploy preview: `migration status`

`migration status --to <ref>` reads the live marker and lists the path to the target: migrations, operations, ref changes. With `--from <contract>` it answers the same question offline from a named starting contract — the form CI and PR review use. This is the go/no-go signal before `migrate --to` runs.

## Deploy-time verification: `db verify`

After `migrate --to` completes, `db verify` compares the marker and the introspected live schema against the contract and reports structured drift kinds. It is the live complement to the offline checks: the offline verbs prove the artifacts are right; `db verify` proves the database ended up where the artifacts promised. Drift taxonomy and recovery strategies are in [ADR 123 — Drift Detection, Recovery & Reconciliation](../adrs/ADR%20123%20-%20Drift%20Detection,%20Recovery%20&%20Reconciliation.md).
