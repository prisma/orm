# CLI

The Prisma 8 CLI is the user-facing entry point into the framework's tooling plane. It wraps contract emission, database init/verify/sign, and on-disk migration management behind a `@prisma/cli-engine` command family (the `orm` family) and a programmatic control API for embedders. The family is mounted by the unified `prisma` CLI (the prisma-cli repository); this workspace also keeps a local `prisma` bin on `@internal/cli` that mounts the same commands for examples and tests. This doc describes the CLI as a subsystem: how it is distributed, what its command surface looks like, how its non-trivial flows (notably `init`) are structured, what it exposes programmatically, and where it sits in the package layering.

This doc is **architectural**. UX, copy, flag conventions, exit-code semantics, and JSON output rules live in the [CLI Style Guide](../../CLI%20Style%20Guide.md). Cross-link, do not duplicate.

## Responsibilities

- Run developer-driven control-plane commands: emit contracts, initialise/verify/sign databases, plan and apply on-disk migrations, scaffold new projects.
- Provide a stable programmatic surface (`@internal/cli/*`) so build tools, CI scripts, and extension authors can drive the same operations without spawning a subprocess.
- Bridge between author-time artefacts (`contract.json`, `contract.d.ts`, migration packages) and runtime targets via the framework's control API.

**Non-goals:** query execution (Runtime), capability lowering (Adapters). The CLI invokes those subsystems; it does not own them.

## Distribution model

One package, no published bin:

| Package | Purpose | Public surface |
|---|---|---|
| [`@internal/cli`](../../../packages/1-framework/3-tooling/cli/package.json) | Workspace CLI source-of-truth (private; published bundled into `@prisma/orm-toolchain`) | Published as `@prisma/orm-toolchain/cli` (the `orm` command family plus workspace helpers), `./config-types`, `./init-output`, `./migration-cli`, `./control-api`, `./control-api/testing` — pinned by the `subpaths` list in [`shells.ts`](../../../packages/0-shared/publish-surface/src/shells.ts) |

The published toolchain ships **no bin**. The only user-facing binary is the unified `prisma` CLI (the prisma-cli repository), which imports `ormCommandFamily` from `@prisma/orm-toolchain/cli` and mounts it in its own `@prisma/cli-engine` shell. Inside this workspace, `@internal/cli`'s own `bin` field keeps a local `prisma` command (pointing at `dist/bin.mjs`, the engine entry) so examples and spawn-based tests can run the family without the unified shell; that bin never reaches the published tarball.

## Command surface

The commands are engine commands, defined one module per command under [`src/orm/`](../../../packages/1-framework/3-tooling/cli/src/orm/) and collected into the `orm` command family in [`src/orm/family.ts`](../../../packages/1-framework/3-tooling/cli/src/orm/family.ts) (commands, config section, docs base URL, retired-invocation redirects). The local bin's shell in [`src/orm/cli.ts`](../../../packages/1-framework/3-tooling/cli/src/orm/cli.ts) mounts them at the same paths the unified `prisma` CLI uses.

Current shape:

- `prisma orm init` — greenfield project scaffold (top-level; see [Init flow architecture](#init-flow-architecture))
- `prisma contract emit | infer` — produce `contract.json` + `contract.d.ts` from PSL or TS authoring
- `prisma db init | update | schema | verify | sign` — adopt, update, inspect, verify, and sign a target database against a contract
- `prisma migration new | plan | check | show | status | log | list | graph` — author and inspect on-disk migration packages
- `prisma migrate` — execute pending migrations against a live database
- `prisma ref set | list | delete` — manage named refs

Each command module exports an engine command (`defineCommand`); the shell that mounts the family owns the tree, so nothing in a command says where it mounts. Embedders compose the whole family (`ormCommandFamily`) rather than individual commands.

Style — flag naming, exit codes, JSON shape, help routing — is the [CLI Style Guide](../../CLI%20Style%20Guide.md)'s domain. This doc only describes *that* the surface exists and *where* it is implemented.

## Init flow architecture

`init` is the most involved command and the only one with a non-trivial internal pipeline. Orchestration lives in [`src/orm/init.ts`](../../../packages/1-framework/3-tooling/cli/src/orm/init.ts) and its `init-*` siblings (scaffold, inputs, packages, emit, blocks, diagnostics); the shared single-purpose helpers live under [`src/commands/init/`](../../../packages/1-framework/3-tooling/cli/src/commands/init/) so each concern is testable in isolation:

| Module | Concern |
|---|---|
| `src/orm/init-inputs.ts` | Resolve target (Postgres / Mongo) and schema location from flags; produce a fully-resolved input record |
| `detect-package-manager.ts` | Detect the project's package manager from lockfiles, `package.json#packageManager`, and falls back to npm |
| `detect-pnpm-catalog.ts` | Detect a pnpm workspace catalog so installed deps land in the catalog rather than as literal versions |
| `reinit-cleanup.ts` | Remove generated files when re-initialising over an existing config (`--force` required) |
| `templates/` | Static templates for `prisma.config.ts`, `prisma/contract.prisma`, `prisma/db.ts`, `.env.example`, `prisma-8.md`, `.agents/skills/prisma-8/SKILL.md` |
| `hygiene-*.ts` | Idempotent updates to `.gitignore`, `.gitattributes`, and `package.json` scripts |
| `probe-db.ts` | Optional connectivity probe before declaring success |
| `output.ts` | Arktype schema for the `--json` success document (re-exported from `@internal/cli/init-output`) |
| `errors.ts` | Init-specific PN error codes |
| `src/orm/init.ts` | Orchestration and the engine `init` command |

The high-level pipeline is: resolve inputs → detect re-init / clean up under `--force` → write templates → update hygiene files → install deps via the detected package manager → emit the contract programmatically through the control API → optionally probe the database → render the success document. Each step is structured so a `--no-install` invocation can short-circuit dependency installation and contract emission while still scaffolding source files.

The user-facing details (which files land, what the prompts say, when `--force` is required, the celebratory after-init output) are owned by the [CLI Style Guide § Init Flow](../../CLI%20Style%20Guide.md#init-flow). This doc records the *internal decomposition* so contributors know where to make changes.

## Programmatic API

`@internal/cli` exposes a small set of subpath entrypoints for embedders:

- **`@internal/cli`** — the `orm` command family (`ormCommandFamily`, `ormConfigSection`) and workspace helpers (`loadContractFromTs`, `loadOrmConfig`)
- **`@internal/cli/config-types`** — `PrismaNextConfig`, `ContractConfig`, `defineConfig` (re-exported from `@internal/config/config-types`)
- **`@internal/cli/control-api`** — the programmatic control plane: `createControlClient`, standalone `executeContractEmit` / `executeDbInit` / `executeDbUpdate` / `executeDbVerify`, `enrichContract`, and the full set of option/result/failure types backing each operation
- **`@internal/cli/init-output`** — the arktype schema for `init --json` success documents

The programmatic surface mirrors the CLI command surface but is independently testable and does not require spawning a process. Build tools, CI scripts, and IDE integrations should prefer it over shelling out, both for performance and because it returns typed result/failure documents instead of parsing stdout.

In-workspace consumers depend on `@internal/cli` directly; external programmatic consumers use the same subpaths republished by `@prisma/orm-toolchain` (`/cli`, `/cli/config-types`, `/cli/control-api`).

## Layering and plane

In the workspace's domain/layer/plane model (see [`architecture.config.json`](../../../architecture.config.json) and [Package Layering](../Package-Layering.md)):

- **Domain:** `framework` (target-agnostic)
- **Layer:** `tooling` (3-tooling)
- **Plane:** `migration`

This places the CLI above `core/` and `authoring/` (which it imports from) and below `runtime/` and `adapters/` (which it does **not** import directly — the control API mediates target-specific work). Concretely, `@internal/cli` may depend on `@internal/contract`, `@internal/config`, `@internal/emitter`, `@internal/framework-components`, `@internal/migration-tools`, `@internal/psl-printer`, `@internal/utils`, and `@internal/errors`. It must not import target-family or runtime packages directly; target-specific behaviour reaches the CLI through the control API and target/adapter facades configured in `prisma.config.ts`.
