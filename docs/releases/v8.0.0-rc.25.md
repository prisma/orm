# v8.0.0-rc.25

A database can now record how it may change and what data it protects, and the CLI refuses a migration or update that breaks those rules. MariaDB gets a client of its own, and MySQL gains the ORM's aggregates. `Int`, `BigInt`, `Float`, `Decimal`, `String`, `Boolean`, `Bytes` and `Json` are convenience types on every database. SQL clients run nested transactions with `tx.transaction(callback)`, and an ORM write inside a transaction is atomic. On PostgreSQL and SQLite, a changed `@@map`, `@map` or enum stored value is planned as a rename. Nested writes gain `onConflict`, variants of a polymorphic model, a `disconnect` that applies its criteria, and `update` and `delete` of one related row. `prisma orm init --target` takes any target package by name.

The upgrade recipes for this hop: the [app recipe](https://github.com/prisma/orm/blob/v8.0.0-rc.25/skills/prisma-8/upgrading/app/upgrades/8.0.0-rc.24-to-8.0.0-rc.25/) and the [extension recipe](https://github.com/prisma/orm/blob/v8.0.0-rc.25/skills/prisma-8/upgrading/extension/upgrades/8.0.0-rc.24-to-8.0.0-rc.25/). Each breaking change below names the change ids to look for in them. The examples write the ORM client as `db.orm.public.<Model>`, the PostgreSQL form; on SQLite, MySQL and MariaDB it is `db.orm.<Model>`. After upgrading, run `prisma contract emit` once: the generated `contract.d.ts` now imports from one module of the target package, SQL contracts record two new capabilities, and MySQL and MariaDB contracts gain aggregate types.

## Breaking changes

- **`pg` and `@types/pg` are peer dependencies.** `@prisma/orm-postgres`, `@prisma/orm-target-postgres` and `@prisma/orm-extension-supabase` no longer install their own copy of `pg` and `@types/pg`. Add `"pg": "^8.22.0"` to your dependencies and `"@types/pg": "^8.20.0"` to your dev dependencies before you install the upgrade. This fixes a `Pool` from your own `pg` not being accepted by the client when the two `@types/pg` versions differed. See `pg-is-a-peer-dependency` in the [app recipe](https://github.com/prisma/orm/blob/v8.0.0-rc.25/skills/prisma-8/upgrading/app/upgrades/8.0.0-rc.24-to-8.0.0-rc.25/) and the [extension recipe](https://github.com/prisma/orm/blob/v8.0.0-rc.25/skills/prisma-8/upgrading/extension/upgrades/8.0.0-rc.24-to-8.0.0-rc.25/), and `extension-importing-pg-peers-it` in the extension recipe. ([#31060](https://github.com/prisma/orm/pull/31060))
- **`temporal-polyfill` must be 1.0.8 or later.** Every database package that requires `temporal-polyfill` as a peer dependency now requires `^1.0.8`, where it required `^1.0.4`. A project or extension package that pins an older 1.0.x version updates it. See `temporal-polyfill-peer-range-moves-to-1-0-8` in the [app recipe](https://github.com/prisma/orm/blob/v8.0.0-rc.25/skills/prisma-8/upgrading/app/upgrades/8.0.0-rc.24-to-8.0.0-rc.25/) and the [extension recipe](https://github.com/prisma/orm/blob/v8.0.0-rc.25/skills/prisma-8/upgrading/extension/upgrades/8.0.0-rc.24-to-8.0.0-rc.25/). ([#31045](https://github.com/prisma/orm/pull/31045))
- **PostgreSQL connections no longer set `lc_monetary=C`.** This lets a pooled Prisma Postgres URL connect. If you use `money` columns, run `SHOW lc_monetary` as the application's role, outside Prisma. If it is not `C`, `POSIX` or `en_US`, run `ALTER ROLE <role> SET lc_monetary = 'C'` before you deploy the upgrade; otherwise a `money` read fails with `RUNTIME.LC_MONETARY_NOT_C`. Under a locale with no or three fraction digits, writes made before the change are stored wrong, so make the change first. See `postgres-lc-monetary-not-set` in the [app recipe](https://github.com/prisma/orm/blob/v8.0.0-rc.25/skills/prisma-8/upgrading/app/upgrades/8.0.0-rc.24-to-8.0.0-rc.25/). ([#31081](https://github.com/prisma/orm/pull/31081))
- **The config type is `PrismaConfig`.** The type `defineConfig` returns is renamed from `PrismaNextConfig` to `PrismaConfig`, with no alias. The language server's diagnostic `PRISMA_NEXT_INTERPRETATION_FAILED` is now `PRISMA_INTERPRETATION_FAILED`. See `config-type-renamed-to-prisma-config` in the [app recipe](https://github.com/prisma/orm/blob/v8.0.0-rc.25/skills/prisma-8/upgrading/app/upgrades/8.0.0-rc.24-to-8.0.0-rc.25/) and the [extension recipe](https://github.com/prisma/orm/blob/v8.0.0-rc.25/skills/prisma-8/upgrading/extension/upgrades/8.0.0-rc.24-to-8.0.0-rc.25/). ([#31062](https://github.com/prisma/orm/pull/31062))

- **On PostgreSQL and SQLite, a changed stored name is planned as a rename.** When a model, field or enum member keeps its name and only its `@@map`, `@map` or stored value changes, `migration plan` and `db update` now rename the table or column, or replace the stored value, without asking. A script that passed `--delete` for such a change now fails with `CLI.CONSENT_UNUSED`; remove the flag. To get an empty table under the new name, remove the model in one migration and add it back in the next. Swaps, chains and takeovers of table and column names are refused with `MIGRATION.PLANNING_FAILED`, and so are enum members that swap stored values or take the stored value of a removed member; make them in two migrations: the first moves every name involved to a name nothing uses, and the second moves them to the final names. Chains of enum stored values are planned. A table that still has the lowered name an earlier release gave a model with no `@@map` is renamed to the model name; add `@@map` to keep the old name. MySQL and MongoDB plan these changes as before. See `sql-stored-name-change-is-a-rename`, `sql-stored-name-delete-is-unused`, `sql-stored-name-empty-table`, `sql-stored-name-swaps-refused` and `sql-lowered-table-names-renamed` in the [app recipe](https://github.com/prisma/orm/blob/v8.0.0-rc.25/skills/prisma-8/upgrading/app/upgrades/8.0.0-rc.24-to-8.0.0-rc.25/). Extension authors who call the SQL family's statement planning see `schema-tables-same-name`, `plan-statements-plans-stored-name-renames`, `subjects-of-calls-storage-renames` and `stored-value-keep-data-edit-removed` in the [extension recipe](https://github.com/prisma/orm/blob/v8.0.0-rc.25/skills/prisma-8/upgrading/extension/upgrades/8.0.0-rc.24-to-8.0.0-rc.25/). ([#31088](https://github.com/prisma/orm/pull/31088))

- **On SQLite, `Decimal` and `BigIntNumber` change codec, and integers are checked.** A `Decimal` field now uses its own codec, `sqlite/decimal@1`, and refuses text that is not a decimal. `BigIntNumber` is a deprecated alias of `IntegerNumber`; write `BigInt(as: number)`. Both change the contract's storage hash, so re-emit and sign the database: with migrations, `migration plan --from <latest migration>` then `db migrate`; without, `db update`. No column changes. An `Int` field now refuses to write, and fails to read, a number that is not an integer within ±(2^53 − 1). The column helpers `integerColumn`, `bigintColumn` and `jsonColumn` are renamed `integerNumberColumn`, `integerBigIntColumn` and `plainJsonColumn`. The recipe has queries that find rows the new checks refuse. See `sqlite-decimal-codec`, `ts-sqlite-decimal-codec`, `sqlite-bigintnumber-deprecated`, `sqlite-integer-safe-range` and `ts-renamed-sqlite-column-helpers` in the [app recipe](https://github.com/prisma/orm/blob/v8.0.0-rc.25/skills/prisma-8/upgrading/app/upgrades/8.0.0-rc.24-to-8.0.0-rc.25/) and the [extension recipe](https://github.com/prisma/orm/blob/v8.0.0-rc.25/skills/prisma-8/upgrading/extension/upgrades/8.0.0-rc.24-to-8.0.0-rc.25/). ([#31086](https://github.com/prisma/orm/pull/31086))
- **Re-emit MySQL and MariaDB contracts.** The MySQL target now supplies the ORM's aggregates and has codecs for the new convenience types. Errors from MySQL's shared code no longer carry `meta.target`; read `db.stack.target.targetId` instead. Extension authors: the MySQL driver factories take the target's runtime metadata and its CHECK error numbers, and a hand-written MySQL codec descriptor needs `wrapParameter`. See `re-emit-mysql-contract-for-aggregates`, `mysql-errors-drop-meta-target` and `mysql-reemit-contract` in the [app recipe](https://github.com/prisma/orm/blob/v8.0.0-rc.25/skills/prisma-8/upgrading/app/upgrades/8.0.0-rc.24-to-8.0.0-rc.25/), and `mysql-driver-factories-take-the-target` and `mysql-codec-descriptor-wrap-parameter` in the [extension recipe](https://github.com/prisma/orm/blob/v8.0.0-rc.25/skills/prisma-8/upgrading/extension/upgrades/8.0.0-rc.24-to-8.0.0-rc.25/). A table whose only unique key has a nullable column now has no row identity, so `update()`, `delete()` and writes followed by `.include(...)` on it fail with `ORM.ROW_IDENTITY_MISSING`. Give such a table a primary key, or make the key's fields required. Extension authors with an SQL adapter report the three include capabilities. - **SQL builder comparisons check values against the column's type.** In `fns.eq`, `ne`, `gt`, `gte`, `lt`, `lte`, `in` and `notIn`, a value compared with an enum column, or any column whose type is narrower than its codec's, must have the column's type. - **Nested relation mutation errors use the general ORM codes.** `ORM.RELATION_MUTATION_INVALID` is now `ORM.ARGUMENT_INVALID`, and `ORM.RELATION_MUTATION_UNSUPPORTED` is now `ORM.OPERATION_UNSUPPORTED`; `meta` is unchanged. `createAll` and `createAndCount` with `onConflict: 'skip'` now refuse, before any statement runs, a row that gives no value for any key the option watches, and a table with no key at all, with `ORM.ARGUMENT_INVALID`. - **`disconnect` in `update()` data changed in three ways.** On a relation whose foreign key is required, `r.disconnect()` is now a type error and is refused with `ORM.OPERATION_UNSUPPORTED` (`meta.reason: 'required-foreign-key'`) before any statement runs; use `connect` to another row, or delete. On a many-to-one relation, `r.disconnect(criteria)` now unlinks only when the linked row matches the criteria; it used to ignore them. `r.disconnect([])` now disconnects nothing; it used to act as `r.disconnect()`. - **Inside a transaction, other work on `tx` is refused while an ORM write of several statements runs.** Such a write, for example a create with a nested relation, now runs in a savepoint. Work sent on the same `tx` while it runs, such as a second call in `Promise.all`, rejects with `RUNTIME.TRANSACTION_SUSPENDED`. Await the write before sending the other work. When such a write hits an error that ends the whole transaction, such as a deadlock on MySQL or MariaDB, it now rejects with `RUNTIME.TRANSACTION_ROLLBACK_FAILED` and carries the database's error as `cause`; code that retries on a deadlock reads it from there. See `orm-write-inside-transaction-suspends-tx` in the [app recipe](https://github.com/prisma/orm/blob/v8.0.0-rc.25/skills/prisma-8/upgrading/app/upgrades/8.0.0-rc.24-to-8.0.0-rc.25/) and the [extension recipe](https://github.com/prisma/orm/blob/v8.0.0-rc.25/skills/prisma-8/upgrading/extension/upgrades/8.0.0-rc.24-to-8.0.0-rc.25/). - **`update()` data refuses a foreign key together with a callback on its relation.** Data that sets a foreign key the record holds, such as `authorId`, and also has a callback on that relation, such as `author`, is refused with `ORM.ARGUMENT_INVALID` (`meta.problem: 'foreign-key-with-relation-mutation'`) before any statement runs. It used to run, and a `create`, `connect` or `disconnect` callback overwrote the foreign key. Keep one of the two, or make two calls. See `foreign-key-with-relation-callback-refused` in the [app recipe](https://github.com/prisma/orm/blob/v8.0.0-rc.25/skills/prisma-8/upgrading/app/upgrades/8.0.0-rc.24-to-8.0.0-rc.25/) and the [extension recipe](https://github.com/prisma/orm/blob/v8.0.0-rc.25/skills/prisma-8/upgrading/extension/upgrades/8.0.0-rc.24-to-8.0.0-rc.25/). ([#31100](https://github.com/prisma/orm/pull/31100))
- **`__proto__` is refused as a name, and a JSON default with a `__proto__` key changes the storage hash.** A contract now refuses a namespace, model, table, column, field, enum, value object, collection or root named `__proto__` with `CONTRACT.NAME_UNUSABLE_AS_KEY` (`PSL_STORED_NAME_UNSUPPORTED` in a MongoDB schema); before, the entry was dropped or the contract came out wrong. Exceptions: in a MongoDB PSL contract, an enum named `__proto__` is not refused but left out of the contract without an error, together with every field typed by it; and a MongoDB contract does not refuse a field or relation of that name, which the client leaves out of the rows it reads. Choose another name. A SQL builder `select` alias `__proto__` is refused with `RUNTIME.AST_INVALID`. A JSON column default that has a `__proto__` key now keeps that key in `contract.json`; re-emit, then plan and apply a migration. See `update-data-refuses-discriminator` in the [app recipe](https://github.com/prisma/orm/blob/v8.0.0-rc.25/skills/prisma-8/upgrading/app/upgrades/8.0.0-rc.24-to-8.0.0-rc.25/). ## Features

- A database can record a change policy and a data protection policy. A ref file declares them under `policies`: `change` lists `migrate` (`db migrate`), `reconcile` (`db update`, `db sign`) or both, and `dataProtection` sets `dataLoss` and `accessWidening` to `…-forbidden`, `…-with-consent` or `…-permitted`. `db migrate --to <ref>` and `db update --to <ref>` refuse a ref whose policies differ from the database's with `MIGRATION.POLICY_MISMATCH`, unless `--permit-policy-change` consents to writing them. A command the change policy does not allow fails with `MIGRATION.CHANGE_POLICY_FORBIDS`. A database with no recorded policy behaves as before. ([#30926](https://github.com/prisma/orm/pull/30926))
- Data protection is enforced. Where a setting is `forbidden`, `db update` and `db migrate` refuse an operation that loses data, or one that the target counts as changing who can read or write data, with `MIGRATION.DATA_PROTECTION_FORBIDS`, before anything runs; `--delete`, `--allow` and a typed answer cannot permit it, and `--rename` still applies. `migration plan --to <ref>` refuses to write a migration the ref's policy forbids. Where a setting is `permitted`, `db update` asks nothing about it. The refusal's advice names the policy that refused, says how to plan the change again without losing data, and tells you not to edit an extension's migrations. On PostgreSQL, only two operations count as access changes: disabling row-level security, and dropping a row-level-security policy. Creating a policy does not count, even a permissive one that grants access. Nor does a policy that the same plan or migration drops and creates again, under the same name or generated-name prefix, whatever its new roles, command, `USING`, `WITH CHECK` or permissive setting say, so a replacement that widens access is not refused. A `rawSql` operation is not read either, so SQL in a hand-written migration that disables row-level security or drops a policy is not refused. SQLite, MySQL, MariaDB and MongoDB count no operation as an access change, so `accessWidening: access-widening-forbidden` refuses nothing on them. ([#31087](https://github.com/prisma/orm/pull/31087), [#31131](https://github.com/prisma/orm/pull/31131))
- MariaDB has a client: `mariadb()` from `@prisma/orm-mariadb/runtime` runs ORM reads and writes, takes every option `mysql()` takes, and accepts `mariadb://` and `mysql://` URLs. `@prisma/orm-mariadb/contract-builder` writes MariaDB contracts in TypeScript. On a database that cannot run the ORM's one-query include, such as MariaDB, the ORM loads each include with one query per relation. ([#31058](https://github.com/prisma/orm/pull/31058), [#31082](https://github.com/prisma/orm/pull/31082), [#31091](https://github.com/prisma/orm/pull/31091))
- The ORM's aggregates, `count`, `sum`, `avg`, `min` and `max`, run on MySQL and MariaDB in `aggregate()`, `groupBy()`, `combine()` and scalar includes. ([#31082](https://github.com/prisma/orm/pull/31082))
- `Int`, `BigInt`, `Float`, `Decimal`, `String`, `Boolean`, `Bytes` and `Json` are convenience types on PostgreSQL, MongoDB, SQLite, MySQL and MariaDB. Each chooses one explicit type, and takes options such as `BigInt(as: number)` and `String(storage: text)`. MySQL and MariaDB gain `Float`, `Decimal`, `Boolean`, `Bytes` and `Json`; SQLite gains `Boolean`; MongoDB gains `BigInt`, `Decimal` and `Bytes`. A SQLite `BigInt` field now reads the full 64-bit range. ([#31067](https://github.com/prisma/orm/pull/31067), [#31086](https://github.com/prisma/orm/pull/31086), [#31109](https://github.com/prisma/orm/pull/31109))
- On PostgreSQL, `Json(storage: jsonb)` gives a `jsonb` column; `Json` still gives `json`. `contract infer` and `contract print` write a `jsonb` column as `Json(storage: jsonb)`. ([#31065](https://github.com/prisma/orm/pull/31065))
- SQL clients run nested transactions. Inside `db.transaction(callback)`, `tx.transaction(callback)` runs in a savepoint, to any depth, on PostgreSQL, MySQL, MariaDB, SQLite and Supabase. When the inner callback throws, only its work is rolled back and `tx` stays usable, unless the error ended the whole transaction, as a deadlock does on MySQL and MariaDB; then `tx.transaction(...)` rejects with `RUNTIME.TRANSACTION_ROLLBACK_FAILED`, with the callback's error as `cause`, and `tx` refuses further statements with `RUNTIME.TRANSACTION_CLOSED`. The inner callback receives the same kind of `tx`, with `orm`, `sql` and the other members. While it runs, the outer `tx` refuses statements with `RUNTIME.TRANSACTION_SUSPENDED`. ([#31053](https://github.com/prisma/orm/pull/31053), [#31106](https://github.com/prisma/orm/pull/31106), [#31120](https://github.com/prisma/orm/pull/31120))
- A nested `create` takes `{ onConflict, conflictOn? }`. `onConflict: 'connect'` inserts a row that does not collide and links an existing one that does, on every relation layout. `onConflict: 'skip'` leaves a colliding row as it is, on one-to-many relations. ([#31031](https://github.com/prisma/orm/pull/31031), [#31070](https://github.com/prisma/orm/pull/31070))
- A relation callback can act on one variant of a polymorphic model: `r.variant(value)` has `create`, `connect`, `disconnect`, `where`, `updateAll` and `deleteAll`, each limited to rows of that variant. `create` writes a complete row, including a variant stored in its own table. ([#31029](https://github.com/prisma/orm/pull/31029), [#31034](https://github.com/prisma/orm/pull/31034), [#31095](https://github.com/prisma/orm/pull/31095))
- A relation callback in `update()` data can update or delete one related row. On a to-many relation, `r.where(filter).update(data)` and `r.where(filter).delete()` change the first related row the filter matches. On a to-one relation, `r.update(data)` and `r.delete()` change the linked row, narrowed by `where()` if given. When no related row matches, nothing changes. `delete` is refused on a relation whose foreign key, held by the record, is required. ([#31096](https://github.com/prisma/orm/pull/31096), [#31100](https://github.com/prisma/orm/pull/31100))
- An ORM write of several statements inside `db.transaction(callback)` is atomic: it runs in a savepoint, so a write that fails leaves none of its rows, and on PostgreSQL it no longer aborts the transaction. ([#31121](https://github.com/prisma/orm/pull/31121))
- `poolOptions.max` sets the most connections the pool of `postgres()` and `supabase()` opens; the default stays 10. Set `max: 1` behind a server-side pooler, such as a pooled Prisma Postgres URL. ([#31138](https://github.com/prisma/orm/pull/31138))
- The control API's `DbUpdateSuccess` has `migrationPlan`: the `--from` and `--to` of a `migration plan` that moves the database to the run's target. Its types, `MigrationPlanArguments`, `MigrationPlanArgument` and `MigrationPlanTargetArgument`, are exported, and `databaseStorageHash` is deprecated in its favour. `DbUpdateOptions` takes an optional `emittedContractHash`. ([#31174](https://github.com/prisma/orm/pull/31174))
- A MongoDB ORM read can be prepared once and run many times: the `db.prepare` callback can return `db.orm.<collection>…prepared.all()`, `.first()` or `.firstOrThrow()`, with placeholders in `where`, `limit` and `offset`. ([#31054](https://github.com/prisma/orm/pull/31054))
- A pgvector column can hold vectors of any length: `pgvector.Vector` in PSL, or `vector()` in TypeScript, is PostgreSQL's `vector` type without a dimension, read as `number[]`. ([#30664](https://github.com/prisma/orm/pull/30664))
- `prisma orm init` installs the target package first and writes the project from that package's `init` entrypoint, so the files come from the version you install. The files it writes are unchanged. It reports `CLI.INIT_TARGET_PACKAGE_NOT_INSTALLED`, `CLI.INIT_CONTRIBUTION_UNAVAILABLE` and `CLI.INIT_AUTHORING_UNSUPPORTED` when a package cannot set up a project. Extension authors: a package that adds a target can export an `init` entrypoint typed `InitContribution` from `@prisma/orm-toolchain/cli/init-contribution`; see `target-package-exports-an-init-contribution` in the [extension recipe](https://github.com/prisma/orm/blob/v8.0.0-rc.25/skills/prisma-8/upgrading/extension/upgrades/8.0.0-rc.24-to-8.0.0-rc.25/). ([#31093](https://github.com/prisma/orm/pull/31093))
- `prisma orm init --target` takes the name of any target package that exports an `init` entrypoint and lists the `prisma-orm-extension` keyword, beside the short names `postgres` and `mongodb`. `--target @prisma/orm-sqlite` and `--target @prisma/orm-mysql` set up SQLite and MySQL projects, and the picker has an entry for another package. The `--json` result gains `package`, and its `target` is the package name for a package with no short name; a script that accepts only `postgres` and `mongodb` there needs a change. See `init-target-takes-a-package-name` in the [app recipe](https://github.com/prisma/orm/blob/v8.0.0-rc.25/skills/prisma-8/upgrading/app/upgrades/8.0.0-rc.24-to-8.0.0-rc.25/) and `init-reaches-a-target-package-by-name` in the [extension recipe](https://github.com/prisma/orm/blob/v8.0.0-rc.25/skills/prisma-8/upgrading/extension/upgrades/8.0.0-rc.24-to-8.0.0-rc.25/). ([#31128](https://github.com/prisma/orm/pull/31128))
- A target package built outside this repository can emit a contract whose `contract.d.ts` compiles, because generated files import from the module the target package names. ([#31078](https://github.com/prisma/orm/pull/31078))
- PSL accepts `/* … */` block comments, as Prisma 6 and 7 do. ([#30795](https://github.com/prisma/orm/pull/30795))
- `MutationUpdateInput`, the type `update()` takes, is exported from the `orm-client` entry, such as `@prisma/orm-postgres/orm-client`, as the docs say. ([#30611](https://github.com/prisma/orm/pull/30611))

- On a collection such as `db.orm.auth.User`, `select`, `distinct`, `distinctOn`, `cursor`, `whereUnique` and `conflictOn` use the fields of that namespace's model when another namespace has a model with the same name. ([#30810](https://github.com/prisma/orm/pull/30810))
- `ilike` and `fullTextMatches` in the SQL builder accept a nullable text column. ([#30598](https://github.com/prisma/orm/pull/30598))

- A `where` with tens of thousands of `in` values or `or` branches is built in milliseconds instead of seconds. ([#30870](https://github.com/prisma/orm/pull/30870))
- The SQL runtime computes a statement's fingerprint only when `telemetry()` is read, instead of after every statement. ([#30949](https://github.com/prisma/orm/pull/30949))
- Contract globs such as `./schema/*.prisma` work on Windows. ([#30872](https://github.com/prisma/orm/pull/30872))
- On MySQL, an ORM update or delete whose filter reads the table it writes now fails with `RUNTIME.AST_UNSUPPORTED` and says what to do, instead of the server's error 1093; code that matched error 1093 matches `RUNTIME.AST_UNSUPPORTED`. A contract file whose export is not a contract fails with `CONTRACT.EXPORT_INVALID`, naming the file, instead of crashing. ([#31091](https://github.com/prisma/orm/pull/31091))
- Most `prisma migration plan` commands that the CLI prints now work. Errors, `migration status`, and the advice of `db update`, `db init`, `db sign` and `db migrate` now print the `--from` and `--to` the plan needs for where the database is, and repeat the flags you gave, such as `--config` and `--permit-policy-change`. ## Known problems

Neither problem is new in this release, and neither is fixed in it.

- Inside `db.transaction(async (tx) => ...)`, send every query through `tx`. On a PostgreSQL client with a single connection (a connection from `postgresServerless().connect()`, or `postgres()` given one `pg.Client`), a query sent through `db` while the transaction is open runs inside that transaction, and some calls, such as an `update()` of one row, wait and never finish. On a client with `poolOptions: { max: 1 }`, a query through `db` waits for the transaction's connection and fails after `connectionTimeoutMillis`, 20 seconds by default. A client whose pool has more than one connection runs the query outside the transaction.
- A PostgreSQL database whose `prisma_contract.ledger` table was created by a release from before June 2026 lacks the `space`, `migration_name` and `migration_hash` columns that `db migrate` writes. Nothing adds them, so `db migrate` fails on such a database.
